# Changes

What changes from one release of mutastic's Java edition to the next, written as changes land. The
newest come first. A release's notes on GitHub are its section here. What each release may change
is on the [Compatibility](https://docs.mutastic.io/reference/compatibility/) page; the Rust
edition's changes are in [its own changelog](https://github.com/mutastic/mutastic-rs/blob/main/CHANGELOG.md).

## Unreleased

What's merged since the last release waits in [`changes/`](changes/), one file for each entry,
until the next release gathers it here.

## 1.4.0 (26 Nov 2026)

### Scoring changes

- **Property tests draw the same inputs in every run.** A property test draws its inputs at random,
  so a mutant only some of them catch was caught in one run and missed in the next. mutastic now
  gives every test JVM of a run one seed, `0` unless the test task sets the framework's own system
  property: QuickTheories' `QT_SEED` and Kotest's `kotest.proptest.default.seed`. A mutant only some
  draws catch can change status once, to what seed `0` draws, and then stays. A mutant's run turns
  their shrinking off, as the first counterexample already catches it, so a mutant whose property
  ran out of time while shrinking is now caught by the property's failure. junit-quickcheck can't
  be seeded from outside its tests: a run whose tests use a framework like that ends with a note on
  stderr, `note: property tests in junit-quickcheck run with their own seeds, which mutastic can't
  set: …`. See [Property
  tests](https://docs.mutastic.io/concepts/results/#property-tests).
- **Maven runs test with assertions on, as Surefire does.** Surefire runs tests with `-ea` unless
  `enableAssertions` is false, but mutastic's test workers ran without it. So a test that checks an
  `assert` failed with no mutant in, and the run stopped, and code that only an `assert` calls had
  mutants no test could catch. Now the workers run with assertions on unless the build turns them
  off, as Gradle's runs already did. A score can rise where an `assert` catches a mutant.
- **A likely flaky test's catches don't count, and the next runs check it harder.** A test was named
  likely flaky (`! likely flaky:`) when a mutant it caught changed result with the code unchanged,
  or a catch of it didn't repeat, but its catches still counted in that run, so a run could pass
  its threshold on them. Now, in the run that names it, each mutant it reached runs again without
  it. `last-runs/flaky-watch.tsv` remembers it, and later runs confirm each catch it makes 3 more
  times (`! watched:`), until its catches have held for 3 full runs. A score can fall where a flaky
  test's catches were counted. See [Flaky
  tests](https://docs.mutastic.io/concepts/flaky-tests/#when-a-test-is-named-likely-flaky).
- **A test that fails only on a class defined twice no longer catches the mutant.** mutastic's
  worker runs tests in class loaders of its own, and a library that keeps what it generated by the
  thread's context class loader, as Spring 5 keeps its CGLIB proxies, defined it again in a later
  run: the JVM refused it (`LinkageError: … attempted duplicate class definition`), the test
  failed, and the mutant counted as caught. Such a failure judged nothing, so it's no catch: the
  mutant's other covering tests decide it, and its card names the test (`duplicateClassBy` in the
  events). On a Spring Boot 2.6 project with MyBatis, caught went from 287 to 248, 33 mutants
  naming such a test, and none of its tests is taken for flaky any more.

### Additions

- **`--at` runs, or lists, the mutants on a line.** Checking one line took listing the mutants,
  finding their ids and passing them to `--only`, though a person fixing a line, an agent on one
  function or an editor has a file and a line, not ids. `mutastic run --at=<file>:<line>`, or
  `<file>:<from>-<to>`, runs the mutants whose cards point at those lines, under the run's
  operators, and says each one's fate after a line that counts them:
  `lines 17–20 of Pricing.java: 6 mutants, 5 caught, 1 missed`. `mutastic mutants --at` lists them.
  Lines with none are an error naming the nearest that have one, never a run of none. In a build of
  several modules the file picks its module. From the build plugins it's `-Pmutastic.at` and
  `-Dmutastic.at`. See https://docs.mutastic.io/guides/scoping/#one-line.
- **A card names the input a property caught a mutant with.** When a QuickTheories, Kotest or
  junit-quickcheck property catches a mutant, `verify`, `explain` and the card say which input it
  failed on, ``caught by ListsTest#reversesTwice with `[0]` ``, and `mutant-finished` has it as
  `caughtInput`, as `mutation.json` has `mutastic.caughtInput`. In a run of every mutant it's the
  first input that failed, unshrunk; a run of mutants named by id runs the catching property once
  more with shrinking on, for the smallest. `run-started` says which property-testing frameworks the
  tests use in `propertyTests`, with the seed their inputs were drawn from and the frameworks
  mutastic couldn't seed.
- **Arguments for the build tool.** What follows `--` goes to Gradle or Maven on each build call,
  and never to the tests: `mutastic run :app -- -Dorg.gradle.java.installations.paths=/jdk-21`. Each
  command a run offers keeps it. `MUTASTIC_BUILD_ARGS`, or `build:`'s `args:` in `mutastic.yaml`,
  gives the same to every run, and no command repeats those, so a secret goes there. An argument
  that fights how mutastic drives the build is refused, with the reason. See
  [Arguments for the build](https://docs.mutastic.io/guides/configuration/#arguments-for-the-build).

### Changes

- **`--at` is in both editions.** The Rust edition takes `--at=PATH:LINE[-LINE]` on `run` and
  `mutants` as the Java edition does, so the contract no longer records it as a gap.
- **The Install page gives the Gradle plugin's minimum, Gradle 8.0.** The plugin calls Gradle 8's
  API, so on Gradle 7 it fails before its tasks are made. The `mutastic` command runs Gradle 7.3 and
  later: see [Install](https://docs.mutastic.io/getting-started/install/).
- **A likely-flaky test's catches don't count, in both editions.** The Rust edition drops them,
  watches the test and confirms its catches 3 times as the Java edition does, so the docs on flaky
  tests and results now cover both, and the contract no longer records it as a gap.

### Fixes

- **The agent format's docs say what it prints at 100%.**
  [Output](https://docs.mutastic.io/concepts/output/) said the `rules:` and `decline:` lines
  always follow the verdict. With nothing missed and nothing unreached, they don't, and nor does
  the fence: only `vs last run:`, `reports:` and any notes follow it, and the page now says so.
- **A Gradle 7 build without a toolchain is read, not refused as one that doesn't build.** Gradle 7
  gives the test task a launcher only when the build has a toolchain, and mutastic's setup asked
  the launcher alone, so it failed with "Cannot query the value of task ':test' property
  'javaLauncher'". It now takes the task's `executable`, the JDK Gradle runs on unless the build
  sets another. The minimum, Gradle 7.3, is on the
  [Install](https://docs.mutastic.io/getting-started/install/#which-gradle-and-maven-run) page.
- **A build on Maven before 3.9.6 is read, not refused as having no Java code.** Maven 3.6.3 to
  3.9.5 passed over mutastic's extension without a word, since it was built for a newer JDK than
  the Sisu in that Maven reads, so every module read as having no Java code. It's now built for
  JDK 11, and runs on Maven 3.6.3 or later, the minimum the
  [Install](https://docs.mutastic.io/getting-started/install/#which-gradle-and-maven-run) page now
  gives.
- **Tests that can't start say why, not that a test called `System.exit`.** TestNG older than
  6.14.3, or JUnit 3 alone, stopped the coverage pass with `tests-stopped` and "A test that calls
  System.exit, or crashes the JVM, stops it". The exception that stopped them is now the headline,
  with what to change: upgrade TestNG to 6.14.3, or junit:junit to 4.13.2. The code is `no-tests`,
  exit 2, as nothing ran. See [Errors](https://docs.mutastic.io/reference/errors/#no-tests).
- **The Gradle plugin reads a test task that has no launcher.** Its `mutasticWriteSetup` asked
  the test task's launcher alone, so a build that clears it failed in that task. It now takes the
  task's `executable`, the JDK Gradle runs on unless the build sets another, as the `mutastic`
  command's setup does.
- **A Gradle 8 build that declares no JUnit Platform launcher runs.** Gradle 8 runs the platform
  with a launcher of its own, so many builds never declare `junit-platform-launcher`, and
  mutastic's test worker then didn't start: "internal error", exit 4. mutastic now adds the build's
  own launcher, from its repositories, at the version of its `junit-platform-engine`, as Maven
  runs already did. Where that can't be resolved, mutastic says to declare it, rather than add one
  of another version, which the platform doesn't run on.
- **Tests on a JDK older than 17 are refused, naming the JDK.** A JDK 8 or 11 test toolchain
  stopped mutastic's test worker, which runs on 17 or later, and read as "internal error: the test
  worker didn't start", exit 4. mutastic now says which JDK the tests run on before any starts, as
  `build-jdk`, exit 2. A JDK 8 named by its JRE's `java`, or by a release file that says
  `1.8.0_392`, is read as 8, where it was read as mutastic's own JDK. See
  [Errors](https://docs.mutastic.io/reference/errors/#build-jdk).
- **A multi-release build's Java 11 classes load in the tests, and their mutants run.** A Maven build
  that compiles classes into `META-INF/versions/11` and puts that directory on the tests' classpath
  with Surefire's `additionalClasspathElements`, as jsoup's does, had every test that reached them
  fail without any mutant, as mutastic never read that setting. They're now loaded with the
  module's own classes, in the order Surefire gives, and their sources come from the directory the
  build compiles them from (`src/main/java11`). Another module's multi-release jar gives the classes
  the JDK the tests run on would load from it, as the JVM's class path does.
- **A mutant whose class the JVM would reject is skipped as unviable, and the run goes on.** One
  such mutant stopped the whole run with an internal error, as mutastic's own operators were
  trusted to make classes that load. It's now withdrawn with the verifier's reason, `unviable: Bad
  type on operand stack in …`, out of the score, as a plugin's that wouldn't load already was. The
  one found, `mutastic/logical-connector`, took Kotlin's `style?.align ?: Start` for an `&&` or
  `||`: its two tests each keep the value they test, so swapping them can't load, and it's no longer
  taken for one. See [Skipped mutants](https://docs.mutastic.io/concepts/results/#skipped-mutants).
- **A parameterized test that takes a class of the tests runs against each mutant.** A test in a
  package the code also uses runs as a fresh copy, and so does a test class of that package that
  it takes, as a `@MethodSource` test takes a record of its cases. mutastic selected the test by
  the type the build gave it, which the copy doesn't take: no test ran, every mutant it reached
  counted as caught, and running it on its own after the mutants called it flaky, so its catches
  were dropped and the run failed. It's now selected by the copy's type. A test mutastic can't
  select again is said to be mutastic's own error, naming the test, and never a test that fails on
  its own.
- **A test sees its package's annotations, and its stack, as it does in the build.** A test that
  read a package's annotations (jsoup checks for JSpecify's `@NullMarked`) found none, and one that
  reported its caller from a stack frame found `mutastic-production//` in front of the class's
  name, so both failed without any mutant. The worker's class loaders now give a package's
  `package-info` to the JDK when it asks, and have no names, as the build's class path loader has
  none a frame shows.
- **`--exclude-tests` takes a test as a run names it, and says when a name matches none.** A run
  names a test with its parameter types, `com.example.PricingTest#bigOrders(com.example.Cart,
  int)`, and that name, given to `--exclude-tests` or `exclude-tests:`, was taken, left nothing out
  and said nothing. Now every form a run prints is taken: a test class by its name or full name,
  `Class#method` with every overload, and one overload by its parameter types, full or by name
  alone; a comma between them no longer splits the option. One rule matches them everywhere a run
  leaves tests out: the coverage pass, each mutant's tests and the flaky watch alike. A name that
  matches no test leaves nothing out, and the run says so, `! left out nothing: PricingTest#bigOrder
  names no test of pricing. There's one called PricingTest#bigOrders.`, in every format, with
  `matched: false` and the close name as `maybe` in `run-finished`. See
  [Leaving a test out](https://docs.mutastic.io/guides/configuration/#leaving-a-test-out).
- **A test that keeps state in a static no longer catches mutants it can't.** A test class the
  worker shares between runs, such as one the project names for a JDK service, kept its statics
  from one mutant's run to the next, so a test that counts its runs, or remembers what the code
  said, failed against mutants it never fails against in the build, and they counted as caught.
  A catch by a test whose run can see state a test-source class keeps in its statics now runs
  again in a fresh loader, where every static starts clean, and counts only if it fails there too;
  with `--kill-matrix`, so does each catcher after the first.
- **A library that looks a class up by its own loader finds the project's.** The worker kept the
  project's libraries on the JDK's class path, below which it loads the project, so a test whose
  library resolves the project's classes itself failed without any mutant in: spring-core's
  `SerializationUtils.deserialize`, as in spring-petclinic's `VetTests#serialization`, and
  `Class.forName` in a library. The worker's system class loader now defines the libraries, finds
  the project behind them, and gives each class its jar and signers as the build does;
  `java.class.path` lists them too. A signed jar whose class doesn't match its signature is
  refused, as the JDK refuses it.
- **Spring 5's proxies are made once in a run, as in the build.** Each mutant's run had a thread
  context class loader of its own, and Spring 5 keeps the CGLIB proxy it made of a class by that
  loader, so a later run made it again and the JVM refused it as defined twice: tests that pass in
  the build failed there, and judged nothing. The worker now has one context class loader for its
  life, which finds every class and resource through the current run's own, so Spring finds the
  proxy it made, and a class asked for by name is always the current run's. On a Spring Boot 2.6
  project with MyBatis, no class is defined twice and 267 mutants are caught, where 248 were once
  those failures stopped counting.
- **A test worker that doesn't start says why.** It was always `internal error: … the test worker
  didn't start`, pointing at a log that CI had often deleted by then. A worker that ended before it
  was ready now gives its status and its log's last lines (`Its test worker ended with status 1
  before it was ready: Unrecognized VM option …`), and one still starting after 30 seconds says that
  a busy machine can cause it and to run again or with fewer workers. Either is a run that can't
  go on, exit 2, not mutastic's internal error.
- **Classes with a `$` of their own, or no SourceFile, are named as the source names them.** A
  class named `$Cache`, or one compiled with no SourceFile attribute (`-g:lines`, or bytecode a
  tool wrote), printed as `com/example/cache/.java` and `.Cache.size()`, and its suggested test
  called `.Cache.size(9)`, which isn't Java. The name is now cut only at a `$` between two other
  characters, a class without a SourceFile is found in its top-level class's file by what its
  class file says of its nesting, and a suggested test is offered only when every class it names
  is written as the source declares it. `mutants` also leaves out what a run skips as generated:
  on realworld-micronaut, Micronaut 4's `@Generated` `$…$Definition` classes were 3551 of the
  4211 mutants it listed.
- **A JDK toolchain the build can't find is said plainly, with the run that fixes it.** A build
  whose toolchain asks for a JDK Gradle finds none of, with auto-provisioning off or a download that
  failed, or one Maven's `~/.m2/toolchains.xml` doesn't list, read as `build-failed`, quoting the
  build tool. mutastic now says which JDK the build needs, its version and vendor as the build named
  them, as `build-jdk`, and offers the run again with the argument that says where one is, after
  `--`: `-Dorg.gradle.java.installations.paths` for Gradle, `--toolchains` for Maven. See
  [Troubleshooting](https://docs.mutastic.io/guides/troubleshooting/#the-builds-jdk-toolchain-isnt-there).
- **Classes compiled without line numbers are refused, by name, not scored 0%.** Coverage is
  recorded by line, so a class compiled with `-g:none` (or Maven's `<debug>false</debug>`) had
  every mutant on line 1 and reached by no test, though its tests ran it. `run` and `mutants` now
  stop with exit 2, naming the classes and how to compile them with line numbers, as javac does by
  default. Counting the tests that enter a method instead would say a test reaches a mutant on a
  branch it never takes.

### Internal

- **The build's everyday commands are one word each, with [just](https://just.systems).** `just`
  lists them; `just check` is everything a pull request needs to pass, as `./gradlew build` is, and
  `just ci` is what CI runs. The words mean the same in mutastic-rs, and a move off Gradle changes
  the recipes beneath them, not the words people and agents type.
- **Holding the next release to the last one is a script.** After each release, a dozen lines of
  RELEASING.md were copied by hand into their own pull request, to set `lastStableRelease` and
  keep the release's schemas, rules files, `mutastic.yaml` files and `commands.json` for the
  compatibility checks. `scripts/hold-release.sh X.Y.Z` does it from the tag, refuses until the
  release is on Maven Central, changes nothing when run again, and lists the schema's keys the
  every-key file doesn't use. CI checks it writes 1.3.0's hold as it was made by hand.
- **A release is checked before it's tagged, and its notes come from the changelog.**
  `scripts/release-check.sh X.Y.Z` checks what a release needs at once and lists what's wrong: no
  scoring change in a patch and no release without entries (`scripts/changelog.sh check --for
  X.Y.Z`), ids all kept, the docs' Rust pin on the Rust edition's `X.Y` with the shared pages'
  stamps up to date, and the files on Central. CI runs it on a release pull request.
  `scripts/changelog.sh notes X.Y.Z` prints the release's section for its GitHub release, in place
  of a hand-run `awk`, and `scripts/docs-pin-rust.sh <commit>` moves the Rust pin and stamps the
  shared pages it changes.
- **The contributor docs and AGENTS.md say `just <verb>`.** CONTRIBUTING, AGENTS.md, the README's
  contributing part, docs/README.md and the pull request template name the recipes (`just check`,
  `just fmt`, `just docs-output`, `just merge`, `just setup`) instead of Gradle tasks and scripts,
  so people and agents type the same words in both editions. The docs site's commands, for people
  using mutastic, are unchanged.
- **A release is checked once it's out, and its candidate before it's tagged.**
  `release-verify.yml` resolves the CLI from the GitHub release, the Maven plugin from Central and
  the Gradle plugin through the Plugin Portal, in clean caches on Linux, macOS and Windows, and runs
  each on `samples/pricing`; `candidate-run.yml` runs the CLI built from the tree over a share of
  every sample, and fails on a crash, a run that can't run, or tests that fail without any mutant.
- **A release ships what the merge queue tested, without testing it again.** The release job ran
  the whole build on one runner, from 25 minutes for 1.0.0 to 52 for 1.3.1, against a 60-minute
  limit, though the queue had already run the same tests on the same tree in parallel jobs. It now
  releases only a commit on `main` that CI passed, in the queue or on the push to `main`, and says
  which run is missing or red before anyone is asked to approve; then it builds what ships and
  runs the checks only a release can: the plugin API against the last release, the ids, the files
  on Central and the plugin for the portal, in about five minutes.
- **The editions' contract says how property tests' seeds and inputs are handled.** Decision 25
  pins a run's random inputs where a framework takes a seed from outside the test, so a mutant only
  some inputs catch is caught in every run or in none, and names the frameworks it can't seed. The
  events schema gains `run-started`'s `propertyTests` and `mutant-finished`'s `caughtInput`, and
  the report schema `caughtInput`. Both editions follow it.
- **CI runs the build through `just`.** Each job calls a recipe, `just ci-build`, `just test-cli
  2/4`, `just test-windows 1`, `just coverage-merge`, and the Nightly `just self-shard` and `just
  self-merge`, in place of Gradle commands and shell written into the workflows, so CI and a
  contributor type the same words and a job that fails can be run as CI ran it. Commits checks the
  justfile's format and its list of verbs, so none goes unseen.
- **The editions' contract says how long a mutant's tests may run.** Decision 26 takes a mutant's
  limit from each covering test's own time, shared out between the tests that run side by side and
  never under 10 seconds, under a ceiling that `mutastic.yaml`'s new `timeout-ceiling:` sets. The
  mutastic.yaml schema gains the key, which only the Rust edition reads for now; the Java edition's
  side is pending (N80).
- **Every asset of a release is attested, and checked against its attestation once it's out.** The
  release workflow attests the CLI's zip and tar, `SHA256SUMS` and a CycloneDX SBOM as built by
  `release.yml` at the release's tag, and the SBOM as what the archives are made of. The SBOM is
  attached to the GitHub release, not sent to Central, whose files count against a monthly limit.
  The job that writes to the repository and signs the attestations has no publishing secrets, and
  the job with them can't write. `release-verify.yml` runs `gh attestation verify` on every asset
  it downloads, and RELEASING.md's *Checking a download* says how to check one.
- **Releases leave on a train.** From 1.4.0, a minor release leaves every second Tuesday, with the
  Rust edition's `X.Y.0` beside it, once the corpus, `release-check` and the candidate run pass;
  entries merged by the day before go with it. Patches between trains are for regressions and
  security fixes only, a release candidate is a GitHub pre-release and never reaches Central, and
  Brian decides each patch. RELEASING.md's *The release train* has the rules, as the Rust
  edition's does.
- **A release is a list of `just` recipes.** `just release-prepare X.Y.Z` makes the release commit
  on a branch (the changelog's section, and for `X.Y.0` the docs' Rust pin) and opens its pull
  request, through `scripts/release-prepare.sh`, whose `--dry-run` stops before the push.
  `release-check`, `candidate`, `release-verify` and `release-hold` wrap the scripts and workflows
  that were typed by hand; `release`, `release-portal` and `docs-redeploy` publish, are Brian's,
  and ask first. `docs-pin-rust`, `docs-stamp` and `docs-compare` name the docs' edition scripts.
  RELEASING.md opens with the release as these recipes in order, and AGENTS.md says which an agent
  may run. The `release` environment's approval stays what guards a publish: `just --yes` skips a
  recipe's question.
- **The Maven module is held to the same boundary as the Gradle one.** `ArchitectureTest`'s rule
  that a build tool knows only the api named `io.mutastic.gradle` alone, so `mutastic-maven` could
  have reached into the engine, the report or the CLI unseen. It names `io.mutastic.maven` too.
- **What each test framework needs is decided in one place.** The JUnit Platform, TestNG, JUnit
  4's vintage engine and Quarkus are each a part in `io.mutastic.engine.tests`, behind
  `TestFrameworks`, in place of one class of checks the engine called from three places.
  `ArchitectureTest` holds the engine's parts apart from its core and from each other.
- **mutastic runs on a corpus of real projects every night.** The samples show one feature each,
  and the bugs that mattered turned up in real projects instead: a loop's slots read twice, a test
  helper in another package, a Maven wrapper older than 3.9.6. `corpus/corpus.yaml` pins 28
  projects and modules, each to a commit and a JDK, with what a healthy run does on it: a score,
  the refusal that's right today, or the known bug that stops it, which fails the night once it
  scores so its entry moves to score with the fix. `.github/workflows/corpus.yml` runs a share of
  each one's mutants nightly, and on a release or candidate by hand (`scripts/corpus-run.sh`,
  through `just corpus`), checks the reports and the agent format's head on each score, and
  tables the results on the run's page against the last good night's. CONTRIBUTING.md says how to
  add a project, and that each corpus failure becomes a sample or fixture in the pull request
  that fixes it.
- **The contract says what a likely-flaky test's catches count for: nothing.** Decision 27: in
  the run that names a test likely flaky, for any reason, the mutants it reached run again without
  it; `last-runs/flaky-watch.tsv`, written by full runs and merges but never by a share, remembers
  it, and later runs confirm each of its catches 3 more times until it has held for 3 runs. The
  events gain `run-finished`'s `watched`, `likelyFlaky[].rerun`, the `fails-alone` reason and
  `flakyCatchBy`; mutation.json gains `mutastic.flakyCatchBy`. N81 holds both editions as pending
  (#225).
- **The nightly self-run passes its baseline again.** `ClassFileVersionTest` read its own class
  file and expected its own name, but mutastic runs a test in a production package as a renamed
  copy (`ClassFileVersionTest__m3`), whose name literal is renamed while the file it reads is the
  build's. Every self-run shard stopped on it from 14 Nov. The test now reads a production class,
  `ClassFileVersion`, so it checks the same parse and version refusal under either name.
- **`CardLinesTest` costs a mutant's run far less.** It checked every truth fixture's mutants under
  every operator in one test, so every mutant of the engine that reached it ran all 16,625 of them
  again: about 4 seconds a mutant, and the Nightly's engine shares ran past their 30 minutes. It
  is now a test for each group of operators, with a test that every operator is in one group, so a
  mutant in one operator's code runs only its group. Over 392 of the engine's mutants, every
  status is the same, and they run in 40.5 seconds rather than 1m50s.
- **The output kit has a package of its own.** Colour roles, glyphs and labels, escaping and the
  agent's fence, JSON and the events' envelope moved to `io.mutastic.output`, which
  `ArchitectureTest` holds to the JDK alone, so proptastic can share them without mutastic. What
  mutastic prints is unchanged.
- **`GatherersTruthTest` loads each mutant's class once, not once a pair of inputs.** Its check that
  each skip is what it says loaded the mutated class, and the fixture as written, again for each
  of 49 pairs of inputs, about 3 seconds each time a mutant of the engine reached it. It now
  loads each class once and keeps what it gives, as the other truth tests do, through
  `ClaimFixture.outcomesOf`. Over the 443 mutants of the engine that reach it, every status is
  the same, and the test takes 14 milliseconds a run rather than 3.3 seconds.
- **mutastic's own run of the engine leaves `CardLinesTest` out.** It checks how reports map a
  mutant's lines over every truth fixture, the engine's scanning code reaches it only on the way,
  and it was about 38% of the Nightly engine shares' test time, enough to take each share past its
  30 minutes. `mutastic-engine/mutastic.yaml` leaves it out with that reason, and the build and CI
  still run it. Of the 1,235 mutants it caught, it was the only test to catch one, a `throw` a
  local guards read as an `assert`; `ExceptionTruthTest` now has that shape and catches it too.

## 1.3.1 (24 Nov 2026)

### Security

- **The summary's `Reports` row escapes what can't be seen in a path.** A report's path with an ANSI
  escape or a bidi control in it went to the terminal as it was, free to rewrite the screen; it's
  now shown escaped, as every other value from the project is.
- **The agent format escapes the last values it showed as they were.** A method's name in a
  repeated-ignores note, the last run's operators in `vs last run`, and the catching test's name
  and a skip's reason in a mutant's fate with `--only` went out unescaped, free to carry an ANSI
  escape or a bidi control. Each is now shown escaped, `\x1b`, as every other value of the
  project's is.

### Changes

- **Patches may correct a score upward, and never lower one.** A patch release used to promise
  never to move a score. It now promises never to lower a score, never to add a mutant and never
  to turn a passing run into a failing one: the one score change it may make is a correction that
  drops mutants that could never run, such as code the build never compiles counted by mistake, so
  a score can only rise. Its release notes list each under a new section, *Score corrections*.
  Anything else that moves a score still waits for a minor release's *Scoring changes*. See
  [Compatibility](https://docs.mutastic.io/reference/compatibility/#scores).

### Fixes

- **A loop whose index was stored just before it no longer stops the run.** 1.3.0 checked every
  `while (i < n)` and `for` loop for the shape javac gives a for-each loop over an array, and when
  the store six instructions before the loop was to its index or its bound, the run stopped with
  `IllegalArgumentException: duplicate element`. Such a loop is now left as an ordinary loop, as it
  was before 1.3.0.
- **The agent format names the report files a run wrote.** It never said there were any, so an
  agent took it there was no report and ran again with `--report=html`. A `reports:` line after the
  verdict names them as the summary's Reports row does,
  `reports: build/mutastic/mutation.json · build/mutastic/mutation.html`, and with `--report=none`
  there's no such line.
- **A Spring test configuration in the app's own package no longer fails every test.** A test
  `@Configuration` or `@SpringBootConfiguration` in a package production code also uses, whose
  component scan finds it, gave Spring two configurations: the one the tests named, as mutastic
  ran it, and the class the scan found. Each declared the same beans, so Spring refused them and
  every test failed with `Failed to load ApplicationContext` before any mutant ran. A test class
  that Spring's scan can find is now the class the tests name.
- **A module whose test classes are only helpers gets a report.** Test sources with a fixtures
  class and no test stopped the run with `no-tests`, as if tests had been there and not run. The
  module has no tests, so it's reported as one with no test classes is: every mutant not covered,
  and the summary's Tests row says none were found. Tests that are there and don't run still stop
  it.
- **A run with `--only` says it writes no report when one is asked for.** `--report` with `--only`
  was passed over in silence, so a person or an agent asking for `mutation.json` got none and no
  reason. A note on stderr now says why: a run of some mutants says nothing about the rest. The
  exit code is as it was.
- **Writing the reports takes as long as the tests are many, not their square, and Duration counts
  it.** Each test that covers a mutant is placed in its file for `mutation.json` and the HTML
  report, and its file was read again for each test: with 2,000 tests in a class, the reports took
  3.1s of a 7.5s run, while the Duration row said 4.1s. Each file is now read once, writing them
  took 93ms, and the Duration row has a `reports` phase, in its total.

## 1.3.0 (23 Nov 2026)

### Card changes

- **A removed cleanup call's card says what to look at.** A `close()`, `closeQuietly()`, a pool's
  `shutdown()` or `shutdownNow()`, `addShutdownHook` and a `Cleaner`'s `clean()` had the card any
  call gets, "no test checks the effect of calling `close()`". Each now names its test: a `close()`
  in a `finally` wants a resource you can inspect, closed when the method returns and when it
  throws; one on a single path, such as a `catch`, wants that path taken first; a JDBC
  `Connection`'s wants a `DataSource` you pass in and `close()` verified, a statement's or result
  set's a mock; a pool's wants the pool passed in and `isShutdown()`; a hook's wants
  `removeShutdownHook` to return true; and `clean()` wants its effect checked right away. Each
  named test is run against its mutant. See [Remove void
  call](https://docs.mutastic.io/concepts/operators/calls/#remove-void-call).

### Scoring changes

- **Twins run once, and their place counts once.** Two mutants at one place that always do the
  same now run as one: the other is skipped as `twin: same as <id>`, naming the one that runs, and
  is out of the score. A for-each loop over an array has three such pairs (`<` made `<=` and the
  test always true, `<` made `>=` and `!=`, the test always false and `<` made `>`), and a
  comparison returned as it is, `return a > b;`, two (the test always true and `return true`,
  always false and `return false`). No id changes, and each still works: `verify`, `run --only`
  and `explain` run the one it's the same as, `mutastic ignore` records the decision for that one,
  and an ignore of either holds for both. Runs have fewer mutants to run, and a score moves a
  little where a place was counted twice. Events give a twin's `sameAs` and the skip kind `twin`.
  The Rust edition has twins too. See
  [Twins](https://docs.mutastic.io/concepts/results/#twins).
- **`library/swap-math` swaps a stream's and a collection's `min` and `max` too.** `Stream.min`
  and `max` with a comparator, `IntStream`'s, `LongStream`'s and `DoubleStream`'s, `Collections.min`
  and `max`, and `Collectors.minBy` and `maxBy` swap places, as `Math.min` and `max` already did,
  and as the Rust edition does for an iterator's. It's in the defaults, so runs get more mutants
  and scores move with them; no existing id changes. See [Math method
  swap](https://docs.mutastic.io/concepts/operators/library/#math-method-swap).
- **A for-each loop's test made `!=` is skipped as equivalent (stronger).** javac counts the
  loop's index up from 0 to the array's length and no further, so `mutastic/comparison` changing
  `index < length` to `index != length` changes nothing, and no test could catch it. `stronger`
  runs have one mutant fewer to run for each such loop, and scores go up a little; no id changes.
- **A thread's name, its priority, its stack size and how long a pool's idle threads live are
  skipped as arid.** None of them changes whether, when or how often work runs. A name given to
  `new Thread`, `setName`, `Thread.Builder`'s `name` (and its start index) or Guava's
  `setNameFormat` is `arid: only names a thread`; a priority from 1 to 10, or `setPriority`
  removed, is `arid: only sets a priority hint`, as Linux ignores priorities by default and a
  virtual thread always does; a `ThreadPoolExecutor`'s keep-alive is `arid: only sets how long
  idle threads live`; and a stack size is `arid: only sizes a thread's stack`. A class that reads
  names (`getName()`, other than into a log line) or is a `ThreadFactory` keeps its name mutants,
  and one that reads priorities keeps those. A value that throws, and a keep-alive or a stack size
  of zero, still run, and so do `start`, `interrupt`, `join`, `setDaemon` and pool and queue
  sizes. Runs on code that sets threads up get fewer mutants, and scores can go up; `@DoMutate`
  and a `mutate:` rule bring them back. The Rust edition skips names, stack sizes and tokio's
  keep-alive too.
- **A pool's largest size beside a queue with no limit is skipped as equivalent.** A
  `ThreadPoolExecutor` only grows past its core size when its queue is full, and a
  `LinkedBlockingQueue` made with no bound never is, so changing its largest size to another no
  smaller than the core size changes nothing. A class that changes or reads a pool's sizes keeps
  them.
- **A removed `join` with a time limit runs again.** It was skipped as `arid: only waits`, but
  without it the code reads what the thread does before it's done: the same race a removed
  `join()` with no limit shows, which ran. How long it waits counts too, as a timeout's does: see
  the sleep entry below. Code that joins with a time limit gets mutants more, and its score can
  fall.
- **`@DoMutate` and a `mutate:` rule bring back every arid skip in their code.** They brought
  back only a whole method a filter skips, a trivial accessor or a `toString()`, and still
  skipped a log call, a `Thread.sleep`, a capacity, an exception's message and the other arid
  sites inside it. Now each of those runs too, so code under `@DoMutate` or `mutate:` gets more
  mutants, and its score can fall. What's generated, equivalent or unviable, and a `@DoNotMutate`
  or `skip:` rule's skip, still stand; no id changes. The Rust edition's `mutate:` already worked
  this way.
- **A log call's format string is arid with worked-out values after it (stronger).**
  `log.info("took {} ms", System.currentTimeMillis() - start)` kept a `mutastic/string-constant`
  mutant on `"took {} ms"`: the walk from the string to the logger stopped at the subtraction, a
  call, boxing, a varargs array, a `+` or a `? :` on the way. It now follows the string through
  them to the call that takes it, so the string is skipped as arid, as one with nothing after it
  was; one that may reach anything else on any path still counts. `stronger` runs have fewer
  mutants, and scores move a little. `mutastic/regex-constant` follows an expression the same
  way, so one with a worked-out replacement after it, `a.replaceAll("a+", b + "!")`, is now
  changed. No id changes.
- **A close you write yourself runs, even in a method with a try-with-resources.** The skip for
  the close javac writes for a try-with-resources worked by method: in any method that called
  `addSuppressed`, every `close()` behind a null check, or closed in two places, was skipped as
  `generated: closes a try-with-resources resource`. So an `if (out != null) out.close()` beside a
  try-with-resources, or a close written out by hand with its own `addSuppressed`, was hidden,
  though a test could catch it. Now only the exact code each compiler writes is skipped, found
  from the resource's own handler: javac 11 and later's, javac 7 to 10's (with javac 9 and 10's
  `$closeResource`, which wasn't skipped before) and ECJ's, whose own null and identity checks
  weren't either. Methods like that get more mutants, and their scores can fall; no id changes.
  Kotlin's `use` is skipped the same way, as ``generated: closes a `use` resource``: its
  `closeFinally` call ran before.
- **A mutant that makes the code a test runs exit is caught by that test, or not caught.** A test
  that calls `main` in the tests' own JVM, where a mutant made `main` call `System.exit`, read as a
  timeout. It's now caught by that test, by the exit, when the status fails a build's test run (any
  but 0): same score, but the test is named. Status 0 passes Gradle's test task, so it's no catch,
  and the tests after it decide: such a mutant can now read as missed, and a score can go down.
  See [When the code a test runs
  exits](https://docs.mutastic.io/concepts/results/#when-the-code-a-test-runs-exits).
- **More capacities are arid, and a negative one counts.** The number in the arithmetic, the `2`
  in `new ArrayList<>(n * 2)`, the JDK's `HashMap.newHashMap` and its kin, Guava's sized factories
  (`Lists.newArrayListWithExpectedSize` and the like) and a hash table's load factor while it stays
  above zero (`arid: only sets when a hash table grows`) are skipped as arid. A number changed to a
  negative one there, as `new ArrayList<>(16)` to `-1`, now counts: it always throws. The Rust
  edition makes and skips a number or arithmetic in `with_capacity`, `reserve` and
  `reserve_exact`. See [Capacity](https://docs.mutastic.io/reference/arid/#capacity).
- **The Rust edition makes its arid mutants, and skips them with a reason.** An error's or a
  failed check's text (`mutastic:messages`) and every mutant of a `Debug` or `Hash` impl
  (`mutastic:debug-representations`) are made and skipped, so they're counted as arid, a
  `mutate:` rule brings them back, and `MUTASTIC_ARID=audit` runs them. A `Display` impl's whole
  body now counts. The editions' contract gives each rule both editions.
- **Only a sleep's time is arid, followed all the way to the sleep.** A number, or arithmetic,
  that goes only into how long `Thread.sleep` or `TimeUnit.sleep` waits is skipped as `arid: only
  sets how long to wait` however it gets there: the `1000` in `seconds * 1000L` too, and through
  `Duration.ofSeconds` or `TimeUnit.toMillis`, as `Thread.sleep(Duration.ofSeconds(n * 2))`. A
  `join`'s time limit now counts, as a timeout given to `Future.get` always did: a shorter limit
  gives up on the work sooner, and a test can see that. So does a number made negative for
  `Thread.sleep(long)`, which throws for it. The Rust edition makes and skips the same:
  `thread::sleep` and an awaited `sleep` removed (`mutastic:waits`), and a number that goes into a
  sleep (`mutastic:wait-times`), where it made no mutant before. See [Wait
  times](https://docs.mutastic.io/reference/arid/#wait-times).
- **A value worked out only for a log line is skipped as arid.** In `log.info("took {}",
  System.currentTimeMillis() - start)` the subtraction's mutants only change what the log says, so
  they're now `arid: only feeds a log line`, part of `mutastic:output`. The value is followed in the
  bytecode, however the source is wrapped: through arithmetic, boxing, `"a" + x`, `String.format`,
  a varargs array, a ternary and the methods of `java.time` and `Math`, and through a local, as in
  `long took = now - start; log.info("took {} ms", took)`, when every read of the local on every
  path, a loop's and a `catch`'s included, is a log call's or a print's argument. A value that
  reaches anything else stays counted: logged and returned, compared, stored in a field, recorded
  as a metric, passed to another method, captured by a lambda. Code that logs timings gets fewer
  mutants, and its score can go up; `arid: [mutastic:output]` on a `mutate:` rule, or `@DoMutate`,
  brings them back. The Rust edition skips a `let` read only by output macros.
- **A variable's first value of `0` or `1` runs again (stronger).** `int total = 0;` or
  `for (int i = 0; …)` was skipped as `arid: a variable's first value of 0 or 1`, but where a
  total, a count or an index starts flows into what the code gives, and a test of the result
  catches a wrong start; the skip hid those catches and the misses beside them. Now
  `mutastic/constant-value` changes it like any other number, and one the code replaces before
  anything reads it is skipped as equivalent. `stronger` runs get more mutants, and scores move;
  no id changes. The Rust edition makes them too. See [First
  values](https://docs.mutastic.io/reference/arid/#first-values).
- **The JDK's `@Generated` counts, though javac keeps it for the source alone.**
  `javax.annotation.processing.Generated`, `javax.annotation.Generated` and
  `jakarta.annotation.Generated` never reach the class file, so the code annotation processors
  (Dagger, MapStruct, AutoValue) and generators (OpenAPI Generator, jOOQ) write was mutated and
  scored as yours. mutastic now reads a Java class's source file too: a top-level type with
  `@Generated` on it is skipped as ``generated: @Generated on `Order` in the source``, with every
  type nested in it. Comments and strings that only mention it don't count. The Gradle plugin adds
  where annotation processors write (`build/generated/sources/annotationProcessor`) to the
  module's sources, as Maven already does. Projects with such code have fewer mutants, and their
  score moves. See [Annotations](https://docs.mutastic.io/guides/configuration/#annotations).
- **More loggers' calls are output, and so is a log level's check around nothing else.** The
  `mutastic:output` rule now knows SLF4J's fluent builder (`log.atInfo().log(...)`), Logback's
  `Logger`, Log4j 2's builder, Log4j 1, JBoss Logging, kotlin-logging, Flogger and tinylog, beside
  SLF4J, Log4j 2, `java.util.logging`, `System.Logger` and Commons Logging. And in `if
  (log.isDebugEnabled()) { log.debug(...); }` the check's mutants are skipped as `arid: only
  decides whether output is written`, when every statement it guards writes output and does
  nothing else; a check that also stores a value, calls a method of the code's own, has an `else`
  or returns stays counted. Code that logs through these gets fewer mutants, and its score can go
  up; `arid: [mutastic:output]` on a `mutate:` rule, or `@DoMutate`, brings them back.
- **A print to a stream the code is given is counted.** `out.println(...)` on a `PrintStream`
  passed in or held in a field, as `run(args, out)` takes it, was skipped as `arid: only writes
  output`, though a test can hand the code a stream and read it: mutants such a test catches, and
  the ones it misses, went unseen. Only the console is output now, `System.out` and `System.err`
  read straight from there or from a local that holds nothing else. Code that prints to a stream
  of its own gets more mutants, and its score moves; new ids appear, none moves.
- **How many calls `mapConcurrent` runs at once is arid.** A number given straight to
  `Gatherers.mapConcurrent` and changed to another above zero gives the same results in the same
  order, so it's skipped as `arid: only sets how many run at once`. Changed to `0`, it always
  throws as the gatherer is made, and counts, as a window's size does. The rule is
  `mutastic:gatherer-sizes`, Java only. See [Arid
  rules](https://docs.mutastic.io/reference/arid/#gatherer-sizes).

### Additions

- **Every arid rule has an id.** Each kind of code mutastic skips as arid has a short, stable
  name, shared by both editions where both have the rule (`mutastic:output` and
  `mutastic:null-checks` today): `mutastic:output`, `mutastic:messages`, `mutastic:failed-asserts`,
  `mutastic:capacity`, `mutastic:wait-times`, `mutastic:waits`, `mutastic:null-checks`,
  `mutastic:array-sizes` and `mutastic:split-limits`, beside
  `mutastic:trivial-accessors` and `mutastic:debug-representations`. The editions' contract lists
  each with the reasons it gives, and each has a section on the [Arid
  rules](https://docs.mutastic.io/reference/arid/) page.
- **Bring back one arid rule: `arid:` on a `mutate:` rule.** `arid: [mutastic:waits]` under a
  `mutate:` rule in `mutastic.yaml` brings back only that rule's skips in the code it covers, and
  `@DoMutate(arid = "mutastic:waits")` does the same in the code (`mutastic-annotations` gains
  `arid()`). Without it a `mutate:` rule brings back every arid skip, as before. An id mutastic
  doesn't have is refused, with the one meant when it's close: `mutastic:wait isn't an arid rule.
  There's one called mutastic:waits.` The `mutastic.yaml` schema has the key and its ids. The
  Rust edition shares `mutastic:thread-names`, `mutastic:stack-sizes` and
  `mutastic:keep-alive`.
- **A skip says which arid rule made it, and how to undo it.** `explain` on a mutant an arid rule
  skipped has an `arid` row: the rule's id, what it skips, a link to its docs and the
  `mutastic.yaml` rule to copy that runs it. The HTML report's "Why it was skipped" says the same,
  with a copy button. Events carry the id as `skipRule` (`mutant-finished`) and the row as `arid`
  (`mutant-explained`), mutation.json as `mutastic.skipRule`, and an arid audit gives the rule to
  copy for each method where a test's assertion caught an arid mutant.
- **`mutastic/boolean-constant`, in `stronger`: a flag set the other way.** A `true` or `false` the
  code passes to a method, or stores in a field or a variable, becomes the other, where only a
  returned one did. A condition's own value isn't one, and a variable nothing reads is skipped as
  equivalent. The Rust edition has it too. See [Boolean
  constant](https://docs.mutastic.io/concepts/operators/arguments/#boolean-constant).
- **`library/plain-division`, in `stronger`: division that rounds towards zero.** `Math.floorDiv`
  and `Math.floorMod` become `/` and `%`, so a remainder that's wrong for negative numbers, `-1 %
  3` being `-1` where `floorMod` gives `2`, shows unless a test has one. A JDK length or count
  divided by a constant that isn't negative is skipped as equivalent. The Rust edition has it too,
  for `div_euclid` and `rem_euclid`. See [Plain
  division](https://docs.mutastic.io/concepts/operators/arithmetic/#plain-division).
- **`library/swap-ends`, in `stronger`: one end of a collection for the other.** `getFirst` and
  `getLast`, a `Deque`'s `peekFirst` and `peekLast` and `pollFirst` and `pollLast`, a `SortedSet`'s
  `first` and `last`, and a `SortedMap`'s `firstKey` and `lastKey` and `firstEntry` and `lastEntry`
  swap places. It finds the newest taken where the oldest was meant, which tests with one element
  can't see. The Rust edition has it too, for `first` and `last` and `front` and `back`. See [Swap
  ends](https://docs.mutastic.io/concepts/operators/library/#swap-ends).
- **`library/reverse-ordering`, in `stronger`: an order turned round.** `a.compareTo(b)` becomes
  `b.compareTo(a)`, a comparator's or a list's `reversed()` is left out, `Collections.reverseOrder(c)`
  becomes `c`, and `Comparator.reverseOrder()` becomes `naturalOrder()`. It finds a sort the wrong
  way round that tests with input already in order can't see. A `compareTo` only tested for `0` is
  skipped as equivalent. The Rust edition has had it, for `cmp`. See [Reverse
  ordering](https://docs.mutastic.io/concepts/operators/library/#reverse-ordering).
- **The summary says when the machine slept during the run.** Duration counts the time the
  machine was awake, so a run a Mac slept through for four minutes said 15.4s. When the clock ran
  at least 5 seconds and a tenth of its time more, a line under Duration says `The machine slept
  for 3m49s during the run, which Duration leaves out.`, and `run-finished` has it as `sleptMs`,
  else 0. The Rust edition says it too. See [When the machine
  sleeps](https://docs.mutastic.io/concepts/output/#when-the-machine-sleeps).
- **A plugin's filter can skip one mutant, not only a whole method.** `Filter` gains
  `skipMutant(site, mutant)`, asked about each mutant still to run once mutastic's own checks and
  every filter's `skip` have had their say, with the instruction it changes and the code around
  it. So a rule like "this call only records an audit event" can ship as a plugin. It does nothing
  by default, so existing filters are unchanged. A skip with a blank reason stops the run, naming
  the filter; an `ARID` one is brought back by a `mutate:` rule or `@DoMutate`, as mutastic's own
  are. See [Filters](https://docs.mutastic.io/guides/plugins/#filters).
- **Code only `main` runs says so, and what to do.** A `main` no test calls read as not covered,
  like any other method. Its line in the Not covered list now says it's reached only from `main()`,
  and to move what it does into `run(args, out)`, which returns the exit code, test `run`, and leave
  `main()` a one-line call to it; a `main` whose mutants are all on one line, as one that only calls
  `run`, gets no such advice. The Rust edition says the same. See [Code reached only from
  main](https://docs.mutastic.io/concepts/results/#code-reached-only-from-main).
- **An `output:` rule names your own output calls.** mutastic knows the common loggers, not the
  wrapper your team logs through, an audit log, or a metric no test reads: each of their calls was
  a mutant only a test of the log text would catch. A rule in `mutastic.yaml`, `- output:
  com.acme.AuditLog#*` with the `reason:` it can't do without, has them skipped as a logger's
  calls are, under `mutastic:output`: a removed call as `arid: only calls AuditLog#info (<the
  reason>)`, a string or a value that only goes into one as `arid: only feeds AuditLog#info (…)`,
  and a check around nothing but those calls. A `mutate:` rule brings them back, and
  `MUTASTIC_ARID=audit` runs them. Nothing is output until a rule says so. In the Rust edition the
  rule names a function or a macro by its path. See
  https://docs.mutastic.io/guides/configuration/#your-own-output-calls.
- **A way past a test that fails on its own: `exclude-tests:` in `mutastic.yaml`, each with a
  reason, and `--exclude-tests=Class#method` for one method.** A test that fails with no mutant in
  still stops the run, and its message now ends in the way past it: list it under `exclude-tests:`
  with a `reason:`, or give `--exclude-tests` for one run, which now takes one method of a class,
  `PricingTest#bigOrders`, with every overload and row, as well as a whole class. The summary's
  `Left out` row names each test with its reason, the Score row ends in `· 1 test left out`, and
  `run-finished` lists them as `testsLeftOut`. A left-out test can only make the score fall: what
  only it reaches is not covered, and a run with other tests left out is never compared as the
  same code. The agent format never offers it, and `mutastic gate` holds a task that adds one, as
  a task that took a test away. See
  [Configuration](https://docs.mutastic.io/guides/configuration/#leaving-a-test-out).
- **A parameterized test that catches a mutant names the case that did.** `verify` and `explain`
  say `caught by CalculatorTest#addsMixed(int, int, int) (case [2] 2, 3, 5)`, and the
  `mutant-finished` event has `caughtCase`, with the method, the case's place in this run and its
  display name. A test that fails with no mutant in is named with its first failing case too, and
  once, where a method with two failing cases was named twice. The method is still the test that
  runs, counts and is remembered; the case is evidence of this run, as a row added above it moves
  it ([results](https://docs.mutastic.io/concepts/results/#parameterised-and-data-driven-tests)).
- **`mutants --operators` estimates what a set adds to a run's tests.** Going from the defaults to
  `stronger` can multiply the mutants, and nothing said what that would cost before a run paid for
  it. After a run, `mutastic mutants --operators=stronger` adds a line before the count, such as
  `estimate: 31 more mutants than defaults, up to 7.7s more of tests, from the run of 22 Nov 2026
  14:03 UTC`: the time the covering tests of each extra mutant took in that run's coverage pass,
  added up. It never guesses: with no run recorded, one of other code or other operators, or
  mutants where that run measured nothing, it says why there's no estimate. `mutants --estimate`
  runs every test once, with no mutant in, and estimates `defaults`, `stronger` and `all`. See
  [All operators](https://docs.mutastic.io/concepts/operators/#choosing-operators).
- **`stream/swap-window` and `stream/swap-fold-scan`, in `extended`: Java 24's gatherers.**
  `Gatherers.windowFixed` and `windowSliding` swap places, which finds batches that overlap where
  they shouldn't, unseen by a test with no more elements than one window. `Gatherers.fold` and
  `scan` swap places, which finds a running total where the final one was meant, unseen by a test
  with one element. A window of one is the same either way, and is skipped as equivalent. The Rust
  edition has no gatherers. See [Window
  swap](https://docs.mutastic.io/concepts/operators/streams/#swap-window).

### Changes

- **The agent format no longer offers `--exclude-tests`.** For a test that fails on its own, or one
  that fails from outside the code, it told the agent to run without the test. Leaving a test out
  may hide a broken one, so it's the person's call: the agent is told to find out whether the
  change or the test is wrong, then tell the person, or propose leaving it out under
  `exclude-tests:` with its reason. The hint for tests that fail on a JDK service the project
  provides no longer ends in `--exclude-tests` either: the line after it names the tests to leave
  out, outside the agent format.

### Fixes

- **A file one mutant's tests leave in the temporary directory can't change the next mutant's
  result.** Each worker had a temporary directory of its own, but one worker runs many mutants,
  so a mutant that removes a `Files.delete` left its file there, and a test of another mutant that
  removes the write could read that file and pass: missed in one run, caught in the next. Now what
  each run's tests add to the worker's temporary directory is deleted once they've answered, so
  the next mutant's tests find it as the last ones did. What was there before stays, as a server
  the coverage pass started can hold on to a directory there. The Rust edition gives each test
  process an empty temporary directory of its own. See [How a run
  works](https://docs.mutastic.io/concepts/how-a-run-works/#each-mutant-against-the-tests-that-reach-it).
- **A wrapper in a directory with a space gets commands that run as they're copied.** Since
  mutastic prints the Gradle or Maven it really runs, a wrapper under `/Users/me/My Projects`
  started a command a shell splits at the space. Its path is now quoted, `'/Users/me/My
  Projects/gradlew'`, or for cmd `"C:\My Projects\gradlew.bat"`, and so is the build's directory
  after `-p` or `-f`: in the terminal, the agent's and share-ready text, the events and the
  report's `mutastic.commands`. The HTML report offers these to copy, and a Windows directory after
  the launcher, `-p C:\dir`, which it left out. Its check reads quotes as a shell does: a report
  could get another command past it with a `'` inside double quotes, or `$(…)` in a `<…>`, and
  can't now.
- **A test that runs `main` in a JVM of its own is said to reach no mutant.** A test that starts
  `java` on `java.class.path` to run the project's `main`, as a person would, found none of the
  project there and failed, so mutastic said the tests fail without any mutant, though they pass
  in the build. It now finds the build's classes there and passes. That JVM gets the classes as
  built, though, and coverage can't see it: so a mutant only it could catch was missed, and `main`
  read as reached by no test. The run now says so after its `coverage` line, for each test class
  that starts a process and names a class with a `main`, and says to call what `main` calls from
  a test instead. When that's the only test, the reason the coverage pass recorded nothing says
  so too. The Rust edition has no such gap: a binary a test runs has the mutant in it. See [Which
  tests reach a line](https://docs.mutastic.io/concepts/results/#which-tests-reach-a-line).
- **A thread's card names the test that catches it.** A missed `start()`, `execute()` or
  `submit()` said only that no test checked the effect of calling it. Its card now says no test
  waits for the work and checks what it did, and to join the thread or wait on a latch first. A
  removed `interrupt()` asks for a test that has a waiting thread stop; one that sets the flag
  again after an `InterruptedException` asks for the flag to be checked. A removed `unlock()` asks
  for another thread to take the lock, `setDaemon(true)` for `isDaemon()`, and a handler for
  exceptions for a task that throws, run with `start()` or `execute()`, as one from `submit()`
  never reaches it. A pool's `awaitTermination` that's always true asks for a task still running
  when the wait ends. Each card's test was run against its mutant, in every shape javac compiles
  the call to. The Rust edition's card for a removed `thread::spawn` says the same.
- **A count of one reads as one.** The gate's pass said the tests `catch 1 of the 1 mutants`; it
  now says they `catch the only mutant`, `catch all 6 mutants` when they catch every one, and
  `catch 4 of the 6 mutants` otherwise. `1 of the baseline's mutants is caught now`, from a run
  and from `baseline --prune`, and `removed 1 ignore that no longer holds`, from `ignore
  --prune`, take their verb from the count too, as does the `shares` line's `1 mutant`. The Rust
  edition says the same.
- **A for-each loop over an array is told as the loop.** Its card said what javac compiles it to,
  `local4 < local3` is always true. It now says what the loop does: the for-each loop over `items`
  reads past its last element, an ArrayIndexOutOfBoundsException, or never runs its body.
- **Help fits 100 columns.** The exit codes, `--help`'s list of commands and the long `ignore`
  example ran to 150 columns and more, so a terminal broke them mid-word. They now wrap under
  their first line, and the example breaks before an option with ` \`, as the Rust edition's
  help does. `--progress` also says that the agent and jsonl formats always get a line at least
  every 30s.
- **A module runs with its repository's Gradle wrapper.** A module with a `settings.gradle` of
  its own, the wrapper only at the top of the repository, ran with the `gradle` on the `PATH`
  instead, and an older Gradle failed while it read the build file. mutastic now looks for
  `gradlew` and `mvnw` up to the top of the repository, and runs one that has lost its executable
  bit with `sh`. With no wrapper, it says which Gradle or Maven it runs from the `PATH`, with its
  path and version, and a failed build says that may be why. A Gradle on the `PATH` too old for
  the build's JDK is named as `build-jdk` too. The commands mutastic prints start with the same
  Gradle or Maven. See [Which Gradle and Maven
  run](https://docs.mutastic.io/getting-started/install/#which-gradle-and-maven-run).
- **The HTML report offers those commands to copy.** A mutant's commands that start with the
  wrapper by its path (`sh ./gradlew`, `../gradlew`, `/repo/mvnw`), Gradle or Maven by an absolute
  path, or `.\gradlew.bat` on Windows were left out of the report's page, as it took only
  `./gradlew`, `gradle` and `mvn`. It still offers nothing else: a path is plain names between its
  separators, ending in the wrapper's or the tool's name.
- **An error ends in the one command to run, in the Rust edition's words.** A mistake in the
  command line no longer ends in a `usage:` line. With no close name, it ends in the command that
  lists what there is, `mutastic run --help`, or in yours with a `<…>` to fill in: a missing value
  (`--format=<format>`, with the values it takes), a missing id (`<id>`, where the example was a
  real id that could be run as it was) or reason (`--reason="<why>"`, the directory and options
  kept). An id no mutant has ends in `mutastic mutants`; a directory with no build says where it
  looked and ends in your command on `<project directory>`. `--workers=0` says what it got, and
  an unknown id, a missing reason and a directory with no project read as they do in the Rust
  edition, so a script or an agent reads one message in both.
- **A test whose code exits says so.** A caught mutant's card says `caught by
  CliTest#printsTheDiscount, by the JVM exiting with status 2`, and its event has `caughtWith:
  "exit: 2"` and `failureOrigin: "exit"`. The Rust edition says the same for `process::exit`.
- **`ignore` on a mutant mutastic skips itself says it doesn't run anyway.** A mutant skipped as
  arid, by a `skip:` rule or as unviable got an ignore that decided nothing; now, as for a
  generated or equivalent one, nothing is recorded, as in the Rust edition.
- **`baseline` takes `--operators`.** A baseline is taken under the operators it names, as the
  Rust edition's is, where only `mutastic.yaml`'s `operators:` could choose them.
- **`gate --help` is the gate's help.** Without its action, it shows the help of `gate open`,
  `gate check` and `gate close`, where it showed every command's.
- **Help lists every variable mutastic reads.** `MUTASTIC_PROGRESS`, `MUTASTIC_TERM_PROGRESS`,
  `MUTASTIC_HEARTBEAT`, `TERM=dumb`, `CI` and `CLAUDECODE` were read but not listed. `--workers`
  says it's how many mutants run side by side.
- **An ignore with no reason says so first.** `.mutastic/ignores.yaml line 4: the entry has no
  reason: every entry needs an id and a reason`, as the Rust edition says it, where the rule came
  before the problem.
- **A close name counts letters as the Rust edition does.** A character outside the Basic
  Multilingual Plane, an emoji, is one edit, not two, when mutastic looks for the name you meant.
- **An error with an option before the command, or a directory that isn't there, says what to
  run.** `mutastic --format=agent run` says mutastic takes its command first and gives the line
  with it first, `mutastic run --format=agent`, where it said `--format=agent` wasn't a command.
  `mutastic run pricng` says where it looked, and that there's a directory called `pricing`, with
  the command on it. Both read as the Rust edition's.

## 1.2.0 (15 Nov 2026)

### HTML report

- **`mutation.html` is mutastic's own report page.** It replaces the generic viewer it embedded,
  and shows what the cards say: for each miss the change, why the tests let it through, the
  inputs they used, the test to add and the `mutastic verify` that proves it; tests to write,
  missed and not covered, with `j`/`k` through them; every mutant by status and operator; each
  test with its source and what it let through; code coloured for Java and Kotlin. **Copy** puts
  a list's tests to write on the clipboard, a line each, for an issue or a pull request. It's still
  one file that opens from disk with no network, and the Rust edition's is the same page. The old
  view isn't an option: `mutation.json` hasn't changed shape, so Stryker's report tools, which
  read it, still show it the old way. See [Report files](https://docs.mutastic.io/reference/reports/).

### Security

- **Text from the project reaches an agent fenced off as data.** The agent format, `next`'s agent
  text and the gate's messages put mutastic's instructions (`rules:`, `done when:`, `fix:`) in the
  same text as the project's code and test run: the lines a mutant changes, test names, what a
  failing test said. A string literal or a comment on a mutated line, a test's name or its data
  could write a line an agent takes as an instruction, and agents read this text through the
  plugins' hooks. The project's text now comes after mutastic's instructions, between
  `<<mutastic-data 3f9a0c1e>>` and `<<end mutastic-data 3f9a0c1e>>`, with a token drawn at random
  for each run (and drawn again if the text holds it), so nothing inside can close it early; the
  opening line says everything up to the closing marker is data, not instructions. The lines inside
  keep their shapes. See [Agent output and untrusted
  text](https://docs.mutastic.io/agents/#agent-output-and-untrusted-text).
- **Hidden characters show as escapes.** Every value and line of the project's that mutastic
  prints, to an agent or to a terminal, shows control characters (ANSI escapes among them) as
  `\x1b`, and bidi controls, zero-width characters and every other invisible format character as
  `\u202e`: a Trojan Source line reads as it runs, and an escape can't rewrite the screen. A value
  or line over 200 characters is cut, with `…(n more chars)`. Events keep the text as it is,
  JSON-escaped.
- **Commands come only from mutastic.** Every command offered (`verify`, `run --only`,
  `ignore --propose`, `next`) is made of a mutant's id (`m` and 8 hex digits, or `<id>`), known
  options and placeholders, and the directory, in single quotes when a shell needs them. A word
  with a `<…>` in it was left unquoted as a template: now only mutastic's own templates are.

### Progress

- **A run is never silent.** Every phase is named while it runs and ends with a line: `building`
  (the build tool's task, its latest log line under it), `built`, `coverage` (tests run of those
  planned), `mutants`, `ran`, and `checking` (each catching test run again on the unmutated code,
  the record and the reports), then `checked`. On a terminal a clock moves every 100 ms; anywhere
  else a line is printed at least every 30 seconds (`MUTASTIC_HEARTBEAT` changes that), Gradle's
  plugin and CI logs included. [PROGRESS.md](PROGRESS.md) is the contract, shared with the Rust
  edition.
- **Progress asks whether stderr is a terminal,** not stdin and stdout: `mutastic run > out.txt`
  keeps the live line. The start script says so in `MUTASTIC_STDERR_TTY`; CI, `TERM=dumb` and a
  coding agent get counter lines instead.
- **`--format=agent` and `--format=jsonl` show progress on stderr,** as counter lines, so an agent's
  harness doesn't stop a quiet run; `--progress=none` or `MUTASTIC_PROGRESS=none` silences it.
- **The live block has a bar, and says what's left.** The coverage pass's bar counts its tests; the
  mutants' is weighted, each mutant counting for what its covering tests took in the coverage pass,
  so it moves with the time passed rather than the count. `~21m left` shows once three mutants and
  ten seconds have run. Heartbeat lines carry the percent and what's left too.
- **A line for each worker,** with its own `[HH:MM:SS]` timer and what it runs: the test in the
  coverage pass, or a mutant as `Pricing.java:17 discount() >= becomes >`. `SLOW` marks a mutant at
  three times what its tests took or half its timeout, and a test after a minute. Up to eight show
  (four below 100 columns), then `… and 3 more running`.
- **`t` says what's running,** above the live block: each worker's mutant, its id, its timer against
  what it should take, and the tests that cover it. `kill -USR1`, and Ctrl-T on macOS and the BSDs,
  do the same anywhere, piped or not. Ctrl-C and Ctrl-Z still work, and every way out leaves the
  terminal as it was.
- **Every line of the live block fits the terminal:** the bar shrinks first, then the counts lose
  their words, then a line is cut with `…`, and wrapping is off while it's drawn. The start script
  passes the width in `MUTASTIC_COLUMNS`; without it, `COLUMNS`, or 100.
- **The summary ends on the score, with its verdict beside it:** `Score  90.9%  [PASS] 1 missed,
  above the threshold of 80.` The verdict names the threshold (`[FAIL] Below the threshold of 80: 6
  missed, 0 not covered.`), so the row no longer says `threshold 80` apart. `Next:` moves above the
  rows, under the misses it's about, and the Duration row names the build and the checking after
  the mutants beside setup, coverage and mutants.
- **`--format=jsonl` says how the run is going, as it goes.** Three events join
  `mutastic.events/v1`: `phase-started` and `phase-finished` (with `durationMs`) as each phase starts
  and ends, and `progress` on the heartbeat's cadence, with the phase's clock, its count, and for the
  mutants the weighted fraction, what's left, the fates and the busy workers. They're additive: a
  reader that ignores reasons it doesn't know reads the stream as before.
- **The terminal's tab shows the run** where the terminal draws progress there (Windows Terminal,
  ConEmu, Ghostty, WezTerm; `MUTASTIC_TERM_PROGRESS=true|false` decides elsewhere): busy while
  building and checking, the mutants' weighted percent while they run, red once the score of twenty
  or more falls below the threshold (never with `--fail-on-new`), and cleared on every way out,
  Ctrl-C, kills and Ctrl-Z included.
- **Each frame is painted at once:** on a terminal, the live block's redraw is one write wrapped in
  synchronized output, which terminals that know it paint without flicker.
- **Gradle's progress line follows the run:** `> :mutasticRun > mutants 2871/5525 · 52% · ✗ 41
  missed · ~21m left`, from the run's live events. It's Gradle's internal API, so a Gradle without
  it shows the heartbeat's lines alone.

### Additions

- **The gate takes an operator set.** `gate open` and `gate check` take `--operators`, as `run`
  does, and `mutastic.yaml` takes `gate:` with `operators:` under it, the gate's set in place of
  `operators:`, so a project can hold its agent's tasks to the stronger set without changing its
  everyday runs; the plugins' hooks need nothing new. The set is chosen when the gate opens and
  kept with the task: every check runs it, and a check given another set is refused (exit 2)
  rather than run on fewer operators than the task opened with. The open names the set, and the
  `mutastic run` it gives the agent carries `--operators` when it isn't what a run would choose;
  each verdict on the mutants says `(operators: stronger)`. See [the gate](https://docs.mutastic.io/agents/gate/#which-operators).
- **A run under other operators than the last says it isn't compared.** A score is a share of
  what its operators make, so a run is compared only with the last under the same set; with none,
  the score line said nothing. It now says `not compared with the last run, which used other
  operators (defaults)`, in the summary and the agent format; the `run-finished` event has no
  comparison, as before.
- **A mutant's id opens the HTML report on it.** With links on, each id the terminal shows, on a
  card, in the misses list or in a command, links to a page beside the report,
  `mutation-mutants/<id>.html`, which opens `mutation.html` on that mutant. A link straight to
  `mutation.html#/m/<id>` loses its `#…` on macOS, whose opener drops it from a `file:` URL, and
  on Linux and Windows by reports; the page's own address has nothing to lose. Only a run that
  wrote the HTML report links its ids: not with `--report=none`, nor a share's. The Rust edition
  does the same.
- **Copy as prompt, in the HTML report.** Beside each Copy, on the tests to write, a folder or
  file's side card and each mutant, it puts those tests on the clipboard as a prompt for any coding
  agent, in the agent format's shape: mutastic's rules first, then the mutants fenced off as data on
  a token no one can guess. The page shows hidden characters in the project's text as escapes too,
  as the terminal does.
- **With more than one test to write, the agent format says how to take them.** After `rules:` and
  `decline:`, a `tasks:` line asks the agent to make a task list, one item per mutant grouped by
  file, then write each test, run its `mutastic verify` and mark it done before the next. The Rust
  edition and Copy as prompt say the same.
- **`mutation.json` says what the cards say.** Under one `mutastic` key on each mutant: where it
  is (`method`), and for a miss its evidence, its fix, the inputs the tests passed and the test to
  add; under one at the top, the run's facts: the commands for a mutant, the docs, the score,
  threshold and verdict, the JDK and when it started. Each test in `testFiles` has its `location`.
  The report schema stays as it is: these are additions, described at
  https://docs.mutastic.io/schemas/report/v1.json, and the Rust edition writes the same.
- **`mutastic mutants` lists the mutants, and runs no test.** One line each, as the Rust edition
  prints it: the id, the change's file, line and column, the operator, the change, and the method
  it's in; then how many. With `--operators=stronger` it shows what a set would add before a run
  pays for it. The build still compiles the code, as the mutants are in its classes.
- **The errors page pairs each code with the Rust edition's.** `no-build-tool` is the Rust
  edition's `no-cargo`, `module-without-java` at a build's root its `workspace-root`, and the page
  lists the codes only one edition has, so a script that wraps both reads one kind for each pair.
  The compatibility page says the run record, `next`'s state and `gate.properties` are private to
  each edition: only their names, and `gate close` deleting the gate's file, are promised.
- **A run with no mutant to run runs no test.** `mutastic run --since=HEAD` on a clean tree started
  a worker and ran every test, a minute and more on a big module, to say there was nothing to
  measure. When no mutant is there to run (no changed lines, changed lines with no mutant, `--only`
  with skipped mutants only, a share that holds none, or a module with none), mutastic still builds
  the module and finds its mutants, lists the skipped ones with their reasons, and passes in the
  time the build takes. The summary says `Tests  none ran: no mutant to run`, with no test runs
  row; `run-finished` has `tests` 0 and `workersStarted` 0. Such a run doesn't replace the last
  run's record, or its report files unless a `--report` is asked for, so `explain`, `next` and the
  next run's comparison still read the last run that measured something. The gate still runs the
  tests: see the fixes. `--force-coverage` (`forceCoverage` in the build plugins)
  runs the tests anyway, as before, to check or time the suite. See [When there's nothing to
  run](https://docs.mutastic.io/concepts/how-a-run-works/#when-theres-nothing-to-run).

### Scoring changes

No operator joins or leaves the default set, and no filter skips more or less. Two fixes change
what a run counts:

- **A case an assumption aborts isn't a failure.** `assumeTrue(false)` failed the test as far as
  mutastic was concerned: a red baseline, or a mutant caught. It's skipped now, as JUnit says, so a
  mutant only an aborted case caught is missed. Scores can go down; no id changes.
- **`--since` sees Kotlin.** A Kotlin change had no changed lines, so `--since` ran none of its
  mutants. Now they run, and a `--since` run's score counts them. No id changes. See the gate's
  fix under *Agents*.

### Fixes

- **`baseline --prune` doesn't drop what another set of operators would make.** A mutant only the
  baseline's operators make wasn't found by a run under others, and looked gone, so pruning after
  `operators:` changed dropped it. `.mutastic/baseline.yaml` now keeps the operators it was taken
  under, `operators: defaults`, and `--prune` under others says so and drops nothing; `run` no
  longer counts the baseline's mutants caught under others. A baseline written before keeps
  working as it did.
- **The summary's report files open from where you ran mutastic.** Run from `samples` on
  `testng`, the `Reports` row said `build/mutastic/mutation.html`, which is there only from
  `testng`, and isn't a link: a terminal that guessed one from the text opened
  `/build/mutastic/mutation.html`. Each file is now shown from the directory you ran in
  (`testng/build/mutastic/mutation.html`), whole when it's outside it, and with links on it links
  to the file itself. The logs a failure names (`worker.log`, `gradle.log`) are shown and linked
  the same way. `run-finished`'s `reports` are unchanged: relative to the project. The Rust
  edition does the same.
- **A class file from a newer JDK says so.** mutastic reads class files with the JDK it runs on,
  and JDK 25 reads none newer than its own: code compiled on JDK 26 or 27 stopped the run with
  `internal error: … Unsupported class file version: 70`. Now it names the class file and the JDK
  that wrote it, and says to run mutastic on that JDK or later, with exit status 2. The Gradle
  plugin runs mutastic on the project's JDK when it's newer than 25, so there it just works.
- **`run --only` on a skipped mutant passes in `run-finished` too.** The exit status counted it
  as passing, as there's nothing to catch, but the event said `"passed": false`.
- **The agent format says `of 1 mutant`**, not `of 1 mutants`.
- **A module's own `mutastic.yaml` is read in a temporary directory on macOS.** There `/var` and
  `/tmp` are links into `/private`, so a module the build reported as `/private/var/…` looked
  outside a run typed as `/var/…`, and its rules were dropped. Paths are compared as the file
  system has them now, which also keeps `--tests-from` from taking a module for a library there.
- **`verify` doesn't say it found no test to suggest.** It looks for none, so its `checked` line
  ended in a misleading `no test found to suggest`; that clause is left out now, in `verify` and
  with `--no-suggestions`.
- **`--kill-matrix` lists every catching test in `mutation.json`.** `killedBy` held only the first,
  while the events' `caughtByAll` had them all; now `killedBy` has them all too, the first first.
- **The gate holds a task that changes no line mutastic mutates to its other checks.** Such a task
  skipped the checks for ignores and baseline entries the task made itself, and for tests taken
  away or `@Disabled`, so an agent that only deleted a failing test, or ignored a mutant itself,
  passed once the rest of the tests did. Now they run on every check, whatever lines changed, with
  the same words and the same hand-over; only a task that changed nothing passes at once, and
  an ignore or baseline entry it made itself holds it even where git doesn't see `.mutastic/`.
  An ignore you accept between turns is still the task's to start from.
- **A suggested test compiles as pasted.** In a class of only parameterized tests, which imports
  no `@Test`, a suggestion didn't build: `@Test` and an assertion such as `assertFalse` weren't
  imported. What the class doesn't import is now written in full, `@org.junit.jupiter.api.Test`
  and `org.junit.jupiter.api.Assertions.assertFalse(…)`. A JUnit 4 class gets a `public void`
  test, as JUnit 4 runs no other: a package-private one stopped the whole class running. A
  nested test class is read from its outer class's file.
- **A JUnit 4 class that can't run is named as you write it.** Its red baseline gave the vintage
  engine's unique id, the class's renamed copy (`SubtractJUnit4Test__m1`), a reason cut off at
  its colon, and a `--tests` command that crashed Gradle. Now it's the class, as `--tests` takes
  it (`com.example.calc.SubtractJUnit4Test`), "the class as a whole: JUnit 4 can't run it", and
  the reason in full: `Invalid test class '…': 1. Method notPublic() should be public`. A
  failure mutastic can't name a test or class for gets no command, rather than one that doesn't
  run.
- **"Doesn't build" names what javac can't find:** `line 57: cannot find symbol: class Test`.
- **The events schema says the order events come in, as both editions write them.** It said a run
  writes `run-started` first, but the phase events of reading and building the project come before
  it. Now it says: those phase events may come first; `run-started` comes before the first
  `mutant-finished`; each `mutant-finished` is written as its mutant finishes, before its phase
  ends; and `run-finished` or `run-failed` is last. Only the descriptions changed.
- **The gate runs the tests even with no mutant on the changed lines.** Since a run with no mutant
  to run stopped running the tests, a task that changed only lines with no mutant (a constant, an
  import, a log line) passed the gate with no test run, even when it broke one. The gate's run now
  always runs the tests, as `--force-coverage` does, and a test that fails holds the task as a red
  suite does, with the same words and the same hand-over. A task that changed only files mutastic
  doesn't mutate (a test's data, a build file) runs the tests too; only one that changed nothing
  skips them. A plain `run --since` keeps the fast path.
- **The gate counts only lines in the code it mutates.** A task counted as changing lines when any
  Java file gained one, tests included, so a task that changed only tests ran the mutants on lines
  that hold none. Now, as in the Rust edition, only changed lines in the module's main sources
  count: a task that changed only tests runs its tests, after the checks above, and passes when
  they do.
- **A build of modules names them as commands, for Maven as for Gradle.** At the top of a Maven
  build with no Java code of its own, mutastic said `name a module with some: mutastic run
  :<module>` and named none. Now both tools say `<directory> is a build's root, with no Java code
  of its own.`, name its modules with Java code, and end in `mutastic run :app` for each, up to five.
- **A module the build hasn't got is said to be missing.** `mutastic run :nope` answered with
  `the Maven build failed` and a log, after making `nope/target/mutastic`, or with Gradle's whole
  failure. Now it says `the build has no module :nope.`, names the modules there are, and makes
  nothing. A close name, `:cor`, gets `There's one called :core.` and its command. Gradle, which
  took `:cor` for `:core` and ran it, now says so too.
- **A directory inside a build runs that build.** In a build's `src`, mutastic said it isn't a
  build's top directory and ended in the command to run. Now it runs the build, or the Maven
  module, the directory is in, as the Rust edition runs the package a directory is in. In a build
  of modules but in none of them, it's refused as the build's root is, with a command for each
  module.
- **A close name is said, with the command corrected.** A mistyped command, option, value,
  `mutastic.` property, `mutastic.yaml` section or rule, rules-file key, operator, filter or mutant
  id now gets the one name close to it, as a statement, never run in its place:
  `run has no option --formt. There's one called --format.`, then the command line as typed with
  only that word changed, `mutastic run --format=agent`, its value after an `=`. Close means the
  same but for case, else within a third of the name's length in edits, two letters swapped
  counting as one; an id must be one slip away.
- **A refusal that does nothing goes to stderr, and exits 1.** `ignore --remove` of a mutant that
  isn't ignored (which exited 0), `ignore --accept` of one that isn't proposed, `baseline` with one
  there already and `baseline --prune` with none printed on stdout, after reading the build. Now
  each is refused before the build is read, on stderr, as the Rust edition does, so stdout holds
  only results. `gate check` with no task open says so on stderr too, and still exits 2.
- **An option the command doesn't take is refused.** `mutastic verify m855c8e3c --threshold=70`
  ran as if the option weren't there. Now it says `verify doesn't take --threshold`, with the
  command's usage, and exits 2 with the code `option-not-taken`, as the Rust edition does. A build
  plugin's `mutastic.` properties are still passed to every goal.
- **`baseline` counts one mutant in the singular:** `1 mutant no test catches is in
  .mutastic/baseline.yaml`.
- **A usage error prints one line of usage,** the command's own, `usage: mutastic run [DIR]
  [:MODULE] [OPTIONS]`, not every command's. A mistake in `mutastic.yaml`, a rules file,
  `.mutastic/ignores.yaml`, an environment variable or the git repository prints none: it isn't
  the command line's.
- **Config errors name the line,** for an operator, filter or plugin in `mutastic.yaml` and an entry
  in `.mutastic/ignores.yaml`, and list what's valid when nothing is close. `operators: [stronger]`,
  which mutastic doesn't read, is shown written an item a line, rather than as an unknown section.
- **`--report`'s error lists `sarif`,** which it has taken since 1.0.0.
- **An operator's docs link names its family, in the path both editions use.** Events' `docs`,
  `explain`'s link and the card's linked operator went to the operators page's row,
  `/concepts/operators/#boundary`. Now each goes to the operator's section of its family's page,
  `https://docs.mutastic.io/java/operators/conditions/#boundary`, as the Rust edition's go to
  `/rust/operators/…`, and the site redirects that path to the Java family pages, anchor kept.
  SARIF rules gain the same link as `helpUri`.
- **A build that fails is quoted at your line.** Gradle's failure came whole, its `* Try:` advice
  and all, and Maven's only as a log's path. Now mutastic says `pricing doesn't build, before any
  mutant is in it.`, names the compiler's error at your file and line (the first three, of how
  many), or what the tool says went wrong, and ends in the build's own command, `./gradlew
  testClasses` or `mvn test-compile`: the Rust edition's words.
- **A failing test says what it said, and how to run it alone.** `the tests fail without any
  mutant: <test>; their output is in <log>` is now `<test> fails without any mutant, so mutastic
  can't judge one.`, then `It failed: expected: <24> but was: <25>`, the log, and the build's
  command for that test, `./gradlew test --tests '…'` or `mvn test -Dtest='…'`.
- **A test that ends the JVM, or tests that run past 10 minutes, exit with 3,** as tests failing
  with no mutant in do, naming the test that was running, not with 4 and `internal error:
  java.lang.IllegalStateException`. A file mutastic can't read or write (a read-only build
  directory, a file in the way, a full disk) exits with 2 and the system's reason, and a module
  whose tests none ran on the JUnit Platform says so, with 2.

### Agents

- **A hooked gate check keeps within the hook's time.** The plugins run `gate check` from a Stop
  hook that's stopped after ten minutes, and a hook stopped gates nothing; on a slow project the
  wait for the count of the task's start, up to four minutes, and the check's own run could pass
  that. As a hook, a check now waits for the count only as long as its budget has left once its
  run is done (`MUTASTIC_GATE_BUDGET`, in seconds, 600 unless set), and when the count isn't done
  by then, a pass says the check compared the annotations only, as before. When the last check's
  own run took longer than the whole budget, the next hands over before it runs and says so: run
  `mutastic gate check` yourself. A check run by a person has no budget. Both variables are in
  help now, and the editions' contract holds them (decision 17).
- **The gate keeps the baseline as it was when it opened.** Where git ignores `.mutastic/`, the
  start commit has no baseline, so every entry of a local one counted as the task's own and held
  the gate however the task did. Only an entry added since `gate open` holds it now.
- **`gate open` clears out copies older counts left behind.** The background count works in a
  copy of the tree in the temporary directory; one stopped hard, or its build's daemon writing on,
  could leave it there. Copies over a day old that no running count owns are removed.
- **The gate counts a parameterized test's rows.** It counted test methods, so a task that took a
  row out of a `@CsvSource` or `Arguments.of(…)`, or turned a parameterized test off, passed. Now
  rows a static source holds are counted from its annotations, at `gate open` and at each check:
  `@CsvSource` entries and `textBlock` lines, `@ValueSource` values, `@EnumSource` names,
  `@CsvFileSource` lines, `@NullSource` and `@EmptySource`. `@Disabled` and `@Ignore` turn off all
  of a method's or a class's rows. What only running says (rows a `@MethodSource`,
  `@ArgumentsSource` or `@FieldSource` makes, a test a condition such as `@DisabledOnOs` turns off,
  a case an assumption aborts) a run counts: `gate open` starts one in the background, on a copy of
  the tree, and returns at once; a check waits for it, up to four minutes
  (`MUTASTIC_GATE_COUNT_WAIT`, in seconds), and holds a task whose own run has fewer cases or more
  skipped. If it couldn't count, a pass says so. `gate close` stops it. Comments don't count.
- **The gate and `--since` see Kotlin.** Git's diff and its new-file listing took only `*.java`,
  so a Kotlin task's changed lines were none: `--since` mutated nothing, and the gate passed a
  task that changed `.kt` code with no mutant run. Its test count read only `.java` files too, so
  taking a Kotlin test away didn't hold the task. Both read `.kt` files now, in whichever source
  sets the build compiles; a new sample, `samples/parameterized-kotlin`, pins them.
- **`mutation.original` and `replacement` are source, as in the Rust edition.** In the events and
  `mutation.json`, `original` is the source the mutant replaces and `replacement` the source that
  replaces it, so writing one over the other gives the mutant's line; `mutation.json`'s `location`
  and SARIF's region span that source. A condition made constant had `original` `>=` and no
  replacement; now it's `total >= 100` and `false`. A return's `replacement` was `return 0;`, and
  is `0`. A statement taken out has an empty replacement. Where the source can't show the change,
  `mutation.json` gives no `replacement` rather than the description, which stays in `description`.
- **An ignore you accept between turns doesn't hold the gate.** The gate counted the ignores from
  a session's first prompt, so a proposal you accepted and then prompted again counted as the
  task's own (`the task ignored … itself`). Now, as a hook, a check that lets the agent stop notes
  the ignores, and the next prompt takes in those added since: yours, made between turns. One the
  agent adds in its turn, with `ignore --accept` or by editing `.mutastic/ignores.yaml`, still
  holds the gate after your next prompt.
- **A failure is an event too.** In `--format=agent` and `--format=jsonl`, an error is also the
  last line on stdout, a `run-failed` event in `mutastic.events/v1`, the Rust edition's shape:
  `code` (`unknown-option`, `build-failed`, `red-baseline`, …), `message`, `where` (the directory
  as typed and its whole path), `help` (each command the error ends in, with whether it runs as it
  is, has a `<placeholder>`, or is a close name to check) and `exitCode`, with `rendered`, the
  words stderr has. A `--hook` run writes none. Before, a red baseline in `jsonl` wrote
  `run-started` and stopped.
- **An errors page** in the reference lists every code with what mutastic says on a sample, why and
  what to do, and how the Rust edition's exit statuses differ until 2.0.

## 1.1.0 (12 Nov 2026)

### Card changes

- **A suggested test is named by where its input sits, not its value.** A number in a name goes
  stale when the spec moves, and no guide or big suite names a test that way. A call of one
  argument is named for zero or a negative input, `feeWhenAmountIsZero`, or for the edge of the
  literal its condition compares with, `discountAtTheTotalEdge` and
  `discountJustBelowTheTotalEdge`; a constant the source names is used as before,
  `discountAtFreeFrom`; anything else keeps its values, `isFreeWithTotal0ForFreeFrom50`. The value
  stays in the call.
- **A card names an object made where it's used.** A comparison or sum whose side is a call on
  `new Something(…)` was named without its receiver: the card said `length() != 0` for
  `new Measured(a).length() != 0`, a condition the source doesn't have. The receiver is now read
  back as `new Measured(a)`.
- **Each suggested test says what it's for.** A card with a test for more than one of its mutants
  gave only the first mutant's fix, so the second test came with nothing saying why. Now `help:`
  says `one test for each mutant`, and each test follows its own mutant's fix and id; the agent
  format's `fix:` does the same, with a `fix for <id>:` line before each test.
- **Never change production code to make a mutant go away.** The agent format's `rules:` line now
  says `add or change tests only; never change production code to make a mutant go away: tell the
  person`, and the gate's open and block messages say the same, as in the Rust edition. Production
  code changed to pass a test the spec asks for is the task; code changed so a mutant can't exist
  hides what the mutant found, and was the one cheat mutastic's own evals saw.

### Additions

- **`run --fail-on-new`, for a project whose score can't reach the threshold yet.** The run
  passes while every mutant no test catches is in `.mutastic/baseline.yaml`, and fails, exit 1, on
  one that isn't, whatever the score: the threshold isn't applied. The summary says `No new misses:
  12 in the baseline.` or names the new ones, as does the agent format's first line, whose entries
  put the new misses first, and the GitHub Actions job summary; `run-finished` gains `failOnNew`, `newMisses` and `inBaseline`. Without
  a baseline it's a usage error, exit 2, saying `mutastic baseline` writes one. The build plugins
  take it as `failOnNew`. See [Brownfield: fail only on new misses](https://docs.mutastic.io/guides/ci/#brownfield-fail-only-on-new-misses).
- **Annotations and a job summary on GitHub Actions.** Where `GITHUB_ACTIONS=true`, a full run
  annotates the line of each of its first ten misses, as the agent format ranks them, and adds a
  Markdown summary to the job's page (`$GITHUB_STEP_SUMMARY`): the verdict, the score, the counts
  and the first misses. No token or permission; the annotations go on stderr, so a format's own
  output is untouched. `MUTASTIC_GITHUB=off` turns both off. See
  [Running in CI](https://docs.mutastic.io/guides/ci/#on-github-actions).
- **`explain --format=jsonl`, for agents.** `mutastic explain ID --format=jsonl` writes the
  events a run's JSON Lines has for that one mutant, then a new `mutant-explained` event with each
  row of About this mutant as a field, in the same words: the bytecode change and what each opcode
  does, the operator, how the id is made, the site and the last run. The events schema describes
  it; a v1 reader that doesn't know it skips it. `explain` refuses the formats it has no
  explanation in. See [One mutant, explained](https://docs.mutastic.io/concepts/output/#one-mutant-explained).
- **`extends:` in `mutastic.yaml`.** A module's file adds another's rules, plugins and filters
  when it says `extends: ../mutastic.yaml`; its own `operators:`, if any, replace the other's. See
  [In a build of several modules](https://docs.mutastic.io/guides/configuration/#in-a-build-of-several-modules).
- **`--report=sarif`, for code scanning.** It writes `mutation.sarif`, SARIF 2.1.0: a result for
  each missed mutant (a warning) and each one no test reaches (a note), on its line, with the
  card's headline, keyed by the mutant's id in `partialFingerprints` so an alert follows its
  mutant; never a fix. Paths are from the git repository's root. See
  [Report files](https://docs.mutastic.io/reference/reports/).
- **The Gradle plugin runs a Kotlin Multiplatform module.** It configures on the multiplatform
  plugin as well as `java`, reading the JVM target's compilations, its `Test` task and its runtime
  configuration, as the `mutastic` command's init script already did.
- **Links to each operator's docs.** `explain`'s About this mutant gives the operator's row on the
  [operators page](https://docs.mutastic.io/concepts/operators/), `docs:
  https://docs.mutastic.io/concepts/operators/#boundary`, in the docs of the release running. On a
  terminal with links on (`--hyperlinks`), a card's `^^ changed to` mark links there too, and
  `--format=jsonl`'s mutant events carry it as `docs`. A plugin's operator has no row, so no link.

### Scoring changes

- **An index compared with -1 skips what differs only below -1.** `s.indexOf(c) == -1` made
  `<= -1`, and the like, can't be told apart, since `indexOf` gives -1 or an index: skipped as
  equivalent for `indexOf` and `lastIndexOf` on `String`, `StringBuilder` and `StringBuffer`, and
  `Character.digit`. A `List`'s runs. Scores can go up; no id changes.
- **A module uses its nearest `mutastic.yaml`, however it's run.** `mutastic run :core` from the
  build's top, the Gradle plugin's task and `mvn mutastic:run` used to read only the top's file,
  while a run in `core/` read only `core/mutastic.yaml`, so the same module could get two scores.
  Now each reads `core/mutastic.yaml` for `core` when there is one, and the top's when there
  isn't. A build that keeps rules in a module's file, and runs from the top, now has them applied.
- **A never-negative claim the compiler checked is trusted.** A comparison's change that differs
  only below zero is skipped where the value compared is annotated `@NonNegative`, `@Positive` or
  `@IndexFor` (Checker Framework), or AndroidX `@IntRange` with `from >= 0`, on a parameter, field,
  local or method return; the reason names the annotation. Annotations only checked at run time,
  or by nothing, don't count. Scores can go up on code that has them; no id changes.
- **Only the JDK's own counts are taken as never negative.** A size or length comparison that
  differs only below zero was skipped for any `java.util` `size()` or `CharSequence` `length()`,
  though a project's own class can return -1. Now only an array's length, `length()` on `String`,
  `StringBuilder`, `StringBuffer` and `StringJoiner`, and a few final JDK classes' counts are.
  Those mutants on a project's own collections now run, so scores can go down; no id changes.
- **An edge inside an `a != b` guard is skipped as `equivalent:`.** In `if (a != b) return a < b;`
  the boundary mutant `a <= b` differs only when `a == b`, which the guard rules out, so no test
  could catch it. Proved from the bytecode, for `int` and `long` locals; fields, floats and doubles
  still run. Scores can go up; no id changes.

### Fixes

- **Two runs on one module wait for each other.** Run at once (an agent's gate and a person's
  run), they wrote each other's setup, staged classes and records in the module's work directory
  in the middle of a run. The first now holds the directory until it ends, and a second says it's
  waiting and runs after it. Runs inside one JVM, as a gate's are, don't wait on each other.
- **Kover's agent is left out of the tests too.** A Gradle build that applies Kover adds its agent
  to the tests, and its jar, which Kover writes in a task of its own before them, wasn't there
  when mutastic ran them: the test worker didn't start, and the run stopped with an internal
  error. Kover's agent and IntelliJ's, which it's built on, are left out as JaCoCo's is, and the
  run is the same as without Kover.
- **A Maven build's JaCoCo agent is left out of the tests, as Gradle's is.** mutastic leaves
  JaCoCo out because it changes classes as they load, but it knew the agent only by Gradle's jar
  name, `jacocoagent.jar`. Under Maven's `prepare-agent` (`org.jacoco.agent-…-runtime.jar`) the
  agent stayed in, and on a Quarkus project every mutant was reported as not covered, with tests
  that plainly reached them.
- **Tests that pass but reach nothing stop the run, instead of scoring 0%.** When the tests ran
  and passed but the coverage pass recorded no line of any class with a mutant, mutastic scored
  every mutant as not covered: a confident wrong answer when the cause was an agent or a class
  loader that kept its coverage out. Now the run exits with status 2 and says what happened, the
  `-javaagent:` arguments it saw, and the likely causes. A run of only some mutants (`--only`,
  `--since`, `--shard`), or with `--exclude-tests`, is scored as before.

## 1.0.0 (11 Nov 2026)

mutastic 1.0.0: the Java edition and the Rust edition, released together at the same version.

From 1.0.0, what the [Compatibility](https://docs.mutastic.io/reference/compatibility/) page promises holds until 2.0: mutant ids, the events format (`mutastic.events/v1`), the plugin API, configuration and the command line. This release makes the last breaking changes before that promise starts; they're listed first.

```sh
curl -fsSL https://mutastic.io/install.sh | sh
```

Maven Central: `io.mutastic:*:1.0.0`. Gradle plugin: `id("io.mutastic") version "1.0.0"`. Docs: [docs.mutastic.io](https://docs.mutastic.io).

### Breaking changes

Before 1.0.0 there are no users to keep, so these are made outright, with no deprecation. From 1.0.0 the events format only gains.

- **Events: the old names are gone (both editions).** `run-started`'s `rules` (read `rule`); `mutant-finished`/`mutant-revised`'s `killedBy` and `killedWith` (read `caughtBy` and `caughtWith`); a mutation's `bytecode` (read `applied`, whose `text` is the same, with `level` `bytecode` from Java and `source` from Rust); `run-finished`'s counts keyed by status, `Killed`, `Survived`, `Timeout`, `NoCoverage`, `Ignored` and Rust's `RuntimeError` (read `killed`, `survived`, `timeout`, `noCoverage`, `ignored`, `runtimeError`); a scoped run's `scope.files` and `scope.lines` (read `scope.fileCount` and `scope.lineCount`). A status's value (`"status": "Killed"`) is unchanged. The `mutation.json` report keeps its schema's `killedBy`.
- **Events: every event names its edition, and the schema requires what every run writes.** The Java edition now writes `edition` on every event, first after `schema`, where it wrote it only on `run-started` and `run-finished`; an event without one is no longer taken as Java's. The schema now requires `edition`, `rule`, a mutation's `applied`, a missed mutant's `ignore` and `propose` (of both editions), `run-finished`'s lowerCamel counts, `toolchain`, `workers`, `workersStarted` and `coverageMs`, and `next-finished`'s `waiting`. `caughtBy` stays optional: a timeout names no test, and neither does a crash the Rust edition counts as caught.
- **Compatibility checks start at 1.0.0.** The plugin API check, the events-schema check and the released-rules-file check compare with the last 1.0+ release (`lastStableRelease` in `gradle.properties`), so none ran against 0.5.0; the Rust edition gains the same for its commands, options, variables, exit codes, `mutastic.yaml` and rules files. `Filter` joins `Mutator` and `ClassMutator` under the plugin API promise.
- **The native `mutastic` runs the newest Java edition patch of its own major.minor from 1.0.0** (mutastic-rs), rather than the newest kept or the latest; `MUTASTIC_VERSION` still picks one exactly (see Installing).
- **The agent format's `or propose` line changed (both editions).** It's now `mutastic ignore <id> --propose --as=<equivalent|unreachable|…> --reason="Differs only when <case>. That can't happen because <why>." <project>`, and `ignore --propose --as=equivalent` (or `unreachable`) refuses a reason without a "because", as it does any reason still holding `<case>` or `<why>`. A script or skill that ran the old line as printed needs to fill in the kind and the two sentences. From 1.0.0 the agent format's structure is fixed and its words may change (Output page).
- **Rust: the summary counts an ignore by its kind, as Java's does.** `1 skipped (1 user)` is now `1 skipped (1 ignored as equivalent)` (or `1 ignored` when `--as` gave no kind); a `mutastic.yaml` rule's skip is still `user`. Ignores aren't skips, so the old count is gone with no alias. The events are unchanged and the same as Java's: the mutant's `skipKind` is `user`, and `run-finished`'s `ignored` counts every skip. No id or score changes (mutastic-rs c35c169).
- **Two operator ids are gone (Java).** `mutastic/return-default` is now `mutastic/return-value` (defaults) and `mutastic/negate-conditional` is now `mutastic/other-comparison` (stronger); `operators:` in `mutastic.yaml` or `--operators` naming an old id stops with "no operator or set is called …". Rename it. Their mutants' ids changed too, so an ignore recorded against one no longer matches (see Scoring changes).
- **`stronger` no longer means every operator.** It's `defaults` plus the stronger tier; `all` is every operator, and `extended` adds the extended tier to another set.
- **Plugin API (Java).** `Mutator.Words` has a fourth part, `written`: a plugin that builds `Words` with the canonical constructor must pass it (the three-argument constructor stays). What's marked `@Internal` (the result model, build tools, `Policy`, `BuiltIn` and a few methods of `Mutant` and `Project`) isn't part of the promise: a plugin that named a `BuiltIn` constant should name the operator by its id.
- **A word a command doesn't take is refused with exit status 2 (Java),** where it was dropped, as the Rust edition already did. A script that passed stray words needs them removed.
- **A run fails, with exit status 3, when a test that caught mutants fails on its own (Java),** whatever the score; `verify` and `gate check` don't pass on it either. Fix the test's dependence on another test, or leave it out with `--exclude-tests` (see Scoring changes).

### Operator sets

- A new `extended` tier for operators on modern APIs, and a new `all` set. `--operators` and `operators:` take `defaults`, `stronger` (defaults plus the stronger tier), `extended` (the extended tier alone, added to another set: `--operators=defaults,extended`) and `all` (every operator). `stronger` meant every operator before; with no extended operators yet, it selects the same operators as it did.

### Scoring changes

- **`mutastic/return-default` is replaced by `mutastic/return-value` (defaults).** A return now becomes the value its kind of method most plausibly gets wrong: a `boolean` the other one (a computed one gets both), a number `0` (or `1` where it returns `0`), `Optional`, `String`, collections and `Stream` their empty value, boxed numbers as their primitive, anything else `null`. Every return mutant's id changes, an ignore recorded against a return-default mutant no longer matches any mutant, and scores move: methods returning `boolean` get up to two mutants per return, and `return 0;` / `return false;` are no longer skipped as equivalent but changed to the other value. On the pricing sample, 8 of 9 caught with 2 skipped became 10 of 11 caught.

- **`mutastic/remove-discarded-call` is added to `defaults`.** A call whose result is thrown away (`items.add(item);`, `seen.put(k, v);`, `text.append(x);`) is removed. Runs get more mutants, and scores move with them.

- **`mutastic/negate-conditional` is replaced by `mutastic/other-comparison` (stronger), and `stronger` gains `mutastic/comparison`.** Together with `mutastic/boundary` and `mutastic/remove-conditional`, `stronger` now makes every change a comparison can have (the full relational set): `mutastic/comparison` adds the one-sided change of the sufficient set (`<` to `!=`, `<=` to `==`, `==` to `<=` and `>=`, `!=` to `<` and `>`), and `mutastic/other-comparison` the rest plus the opposite condition that negate-conditional made. Every negated-condition mutant's id changes (the operator is now in its fingerprint), an ignore recorded against one no longer matches, and `stronger` runs get more mutants, so their scores move. `defaults` is unchanged: `mutastic/boundary` keeps its id and its mutants. The minimal set was meant to replace boundary and negate in `defaults`; measured alone on mutastic's own modules its one-sided change left 156 survivors, roughly 85% of them noise, so it went to `stronger` instead.

- **A comparison of a size with zero gets each change once (defaults).** `mutastic/boundary` no longer changes `size() > 0` to `size() >= 0` (or the like on a length, array length or parameter count): for a value that can't be negative that's the condition always true, which `mutastic/remove-conditional` already makes. Runs have slightly fewer boundary mutants, and scores move a little; no other mutant's id changes.

- **`mutastic/logical-connector` is added to `defaults`.** In a condition of two tests, `&&` becomes `||` and `||` becomes `&&`. Runs get more mutants, and scores move with them.

- **`mutastic/remove-assignment` is added to `defaults`.** An assignment to a variable that already has a value is removed. Runs get more mutants, and scores move with them; no existing mutant's id changes.

- **`library/swap-string` and `library/swap-math` are added to `defaults`.** `startsWith` and `endsWith`, `toUpperCase` and `toLowerCase`, `stripLeading` and `stripTrailing`, `Math.min` and `max`, `Math.floor` and `ceil` swap places. Runs get more mutants, and scores move with them; no existing id changes.

- **`mutastic/string-constant` knows an exception by its real supertypes (stronger).** A class named `...Exception` or `...Error` that isn't a `Throwable` now keeps its string mutants, and a project's exception with any other name has its message skipped as arid. If a class's supertypes can't be found, the mutant stays. A failed check's message is skipped only for `Objects.requireNonNull` and Guava's `Preconditions`, no longer for any class called `Preconditions`. `stronger` scores move on code where a name and a type disagree; on mutastic's own engine nothing moved. No id changes.

- **`stream/remove-stage` no longer removes `limit` from a stream only it ends (defaults).** On a stream the method visibly starts from `Stream.iterate(seed, next)` or `generate`, or their `IntStream`, `LongStream` and `DoubleStream` forms, the mutant is now skipped as `unviable:`, because the tests would hang and a hang counted as a catch shows nothing. A timeout used to count as caught, so scores on code like this can go down a little. The same now goes for `ints()`, `longs()` and `doubles()` given no size, with or without a range, on `Random`, `SecureRandom`, `ThreadLocalRandom`, `SplittableRandom` and `RandomGenerator`, and for a limit worked out with arithmetic, as `limit(n + 1)`. The `iterate` with a condition keeps its mutant, and so do `ints(5)`, a stream with `takeWhile`, another `limit`, or a later `findFirst` or `anyMatch`, and a limit with a `?:` in it. No id changes.

- **Kotlin support is experimental.** It runs, and the changes below make its cards truer, but it hasn't yet been proved on real Kotlin projects, Jetpack Compose among them.

- **Kotlin: kotlinc's own code is skipped (Kotlin projects only).** kotlinc's `Intrinsics` checks and a data class's `copy`, `componentN` and `equals` are now skipped as `generated:`, so those projects' scores change. No id moves, and Java projects aren't affected. Kotlin mutants now point at the real `.kt` file (Gradle only).

- **Kotlin: a mutant is on the line its code is on (Kotlin projects only).** kotlinc numbers code it copies in from an inline function past the end of the file, with a map in the class file that mutastic now reads. A copy of the project's own inline function is on that function's line, in that function's file, and runs; a copy from outside the module, like the loop in `filter`, is skipped as `generated:` and leaves the score. An inline function's own body, which the JVM never runs, no longer reads as not covered: it's skipped as `generated:` if copies of it exist, and stays as it was if Java calls it or nothing does. No id moves, Kotlin's or Java's: an id doesn't hold a line, and what's skipped still counts as a site. Java projects aren't affected. Kotlin scores move, since mutants leave.

- **Kotlin: a coroutine's state machine and a `lateinit`'s check are skipped, and `!!` isn't (Kotlin projects only).** What kotlinc writes to make a function suspend (`throwOnFailure`, the comparison with `COROUTINE_SUSPENDED`, saving and restoring locals, the `switch` on `label`) and a `lateinit`'s getter and check are skipped as `generated:`. Kotlin scores move, and often down, as some of these were caught by the coroutine breaking, which said nothing of the tests. `x!!` and `x as String` used to be skipped as kotlinc's own check, and now run, as the person wrote them; `x!!.size` is skipped as `equivalent:`. A mutant before a Kotlin method's first line reported line 1 and not covered however the method was tested: it's on the first line now, so some not-covered mutants become caught or missed. No id moves. Java projects aren't affected.

- **Kotlin: suggested tests are in Kotlin (Kotlin projects only).** A mutated `.kt` file gets `fun`, no `void`, `plusOne(1)` and not `ProbeKt.plusOne(1)`, `Counter(1).next(1)` with no `new`, `1.doubled()` for an extension and `Counter(2).twice` for a property. A call that can't be sure to compile gets no suggestion: a generic function or class, `@JvmName`, an `object` or companion's member, a file-private class, or a test class in Java. Cards name `name.isEmpty()` for `length() == 0`, "a lambda in `labels()`" for `labels$lambda$0` and a suspending lambda's `invokeSuspend`, and drop `local3` and `x$iv`. Scores don't change. No id moves.

- **Code a test class runs outside its tests counts for the tests that depend on it (all frameworks).** What a `@BeforeAll`/`@AfterAll`, JUnit 4 `@BeforeClass`/`@ClassRule`, TestNG `@BeforeClass`/`@BeforeMethod`/suite methods, a test class's constructor, field and static initialisers, or a `@MethodSource` runs was put down to whichever test happened to run before it, often in another class: its mutants were missed, or "not covered" on TestNG, and cards said "covered by" a test that never ran the code. Now it counts for every test of its class (a `@MethodSource` for its test; TestNG's suite methods and class construction for every test). Scores go up where setup does real work (on the lifecycle samples 50 of 100 such mutants were caught before, all 100 after; on mutastic's own engine, whose truth tests now hold their fixtures per test, it hardly moves). A test that passes among the others but fails on its own is now found the first time it catches, named as flaky, and its catches don't count, so a score can also go down where one was catching by accident. No id changes.

- **A test that caught mutants and fails on its own fails the run (any project).** Once the mutants have run, each test that caught one runs again, on its own with no mutant in, in a new worker. One that fails there (it needs another test's set-up, or trips on something an earlier test or the run left behind) is named as flaky, as a test that "passes among the others but fails on its own"; its catches don't count, and every mutant it reached runs again without it, so scores can go down. Unlike other flaky tests it fails the run whatever the score, with exit status 3, and `verify` and `gate check` don't pass on it either; `--exclude-tests` leaves such a test out. Projects whose suites are order-dependent, or whose tests share files or a database without cleaning up, are the ones that could see it; a healthy suite's results don't change, at the cost of one run of each catching test (about 9 s on mutastic's own engine). In `--format=jsonl`, a mutant run again comes as a `mutant-revised` event, naming the test as `falseCatchBy`. No id changes.

- **Kotlin: what the Compose compiler writes is skipped, and so are kotlinc's default stand-ins and a lambda's `Unit` (Kotlin projects only).** In a `@Composable` (one taking a `Composer` and its masks), the runtime's bookkeeping (groups, `remember`'s cache, `changed`, skipping, trace and source information, the restart scope), the `$changed` and `$default` masks and what works on them, and the zero or `null` a call passes for an argument left to its default are skipped as `generated:`. So are the mask and stand-ins of any call to a Kotlin `f$default` or `DefaultConstructorMarker` constructor, and the `Unit` a lambda returns where the source returns nothing. On mutastic's Compose sample under `defaults`, 249 mutants that ran are skipped now (218 missed, 31 caught only by the compiler's code breaking) and the score went from 25.5% to 55.2%. Cards call Compose's `Text` `Text` (not `Text--4IGK_g`), place a `ComposableSingletons` lambda in its `.kt` file as "a composable lambda", and don't list a `$changed` mask among the inputs seen. No id moves. Java projects aren't affected.

- **Lombok: a `@Cleanup`'s close is skipped, and a `@NonNull` check in a setter Lombok writes runs (Lombok projects only).** The close a `@Cleanup` writes into a method, `if (Collections.singletonList(r).get(0) != null) r.close()`, is now skipped as `generated:`, as a try-with-resources's close is. Its cards asked for a test where the resource was null. The null check a `@NonNull` asks for in a setter Lombok writes now runs, as the check in the person's own methods already did; the rest of the setter stays skipped. Members Lombok marks `@lombok.Generated` (by default from Lombok 1.18.34) were already skipped and still are; with an older Lombok, set `lombok.addLombokGeneratedAnnotation = true` (docs: Results, Lombok). Scores move a little on Lombok projects that use `@Cleanup` or `@NonNull` on fields with setters. No id changes, and projects without Lombok aren't affected.

- **A test class whose setup fails now and then is left out as flaky, and the run goes on (projects with such a class, any framework).** A `@BeforeAll`, `@AfterAll`, JUnit 4's or TestNG's `@BeforeClass`, a class rule or a static initialiser that failed once before any mutant used to stop the run with exit status 3, naming the class by the platform's id (`[engine:junit-jupiter]/[class:…]`). The class now runs again as a class; if it passes, it's left out with every test in it and named (`flaky: SetupTest as a whole (its setup or teardown, outside any test) failed, then passed when run again; left out of this run with every test in it…`), and the run carries on. What only its tests reach is counted as not covered, so those projects get a score where they got none, and its tests catch nothing, as its setup could fail against any mutant. A class that fails every time still stops the run, and the message names it and says its setup or teardown failed outside any test. No id changes; a project whose tests pass before any mutant sees nothing new.

- **Rust edition: `mutastic/unwrap-try` is in the defaults.** `f()?` becoming `f().unwrap()` was in `stronger`; every Rust run now has it. A missed one is an error path no test runs, which line coverage can't show. A `?` on a formatter's write stays skipped as equivalent. Rust crates that use `?` get more mutants and their scores usually fall a little: on semver, humantime, clap_lex and httparse the defaults score moved by −1.7 to +0.4 points. No id changes; `stronger` and `extended` are unchanged. Java runs are unaffected. Already in the Rust edition's 0.2.0, so new only to readers coming from Java 0.5.0.

### Cards

Both editions, so a card stands alone without the source, for a person labelling misses and for an agent that reads the card alone. No id or score changes.

- **The `+` line is always the mutant's code.** Library and stream swaps, an `Optional`'s or a `Predicate`'s rule, a removed stream stage, a call left out, an array one value short, swapped arguments, a removed `throw`, `case` or `catch` type and a string or regex changed used to put words in the `+` slot, `+ (changed to endsWith)`, which read as code and hid which call changed. The change is now made where the source has it, the call on the mutant's own line when the statement has two of one name: `+ && ((value.endsWith("\"") && value.endsWith("\""))`. Where the source can't show it (a constant the source names, a parameter set to `null`, a method's whole body, a call whose arguments still run), the change goes on a line of its own that can't be taken for code: `= change  startsWith changed to endsWith (not shown in the source)`, `change: …` in the agent format. A statement the mutant takes out has a `-` and no `+`. The label under the caret names both sides, `startsWith changed to endsWith`, `>= changed to >`. A plugin's `Mutator.Words` has a fourth part, `written`, the changed call as a template on the call's parts (`{receiver}.allMatch({args})`), for its cards to show the code; a rules file's rewrites fill it in. The built-in rules' `changed:` now reads `{name} changed to {to}`. **Breaking** for a Java plugin that builds `Words` by its canonical constructor (the three-argument one stays).
- **A forced condition reads as its value.** `!true` is `false` and `!false` is `true`, the rest of the line as written: `+ return (false && next.getFirst().opcode() == Opcode.ATHROW)`. A condition with a constant javac wrote in (`count >= 50` for `count >= BULK_FROM`) is found by the name in the number's place.
- **The whole statement shows when it spans lines.** The `-` and `+` lines run from the statement's first line to its last (Java: the lines before javac's that don't end a statement, and on to the one that does; Rust: the syntax tree), cut to six lines around the change with `…`, in the full card, `explain`, the agent format and `also` lines.
- **`explain` on a skipped mutant says "skipped" once:** `SKIPPED  user: …`, not `SKIPPED  skipped: user: …` (Java; the Rust edition's `skipped: unviable: …` too).
- **Suggested tests use the source's names.** A parameter is named as the class file names it (MethodParameters, else the LocalVariableTable, which `-g` writes and Gradle and Maven compile with by default), so a boxed `Integer chosen` no longer gives `sizeWithArg01…`; a constructor's arguments are named by its parameters (`isFreeWithTotal0ForFreeFrom50`, was `…ForDelivery50`). An input at a value the source names says it the source's way and names the test: a constant the test can use goes in the call with its value in the comment (`discountAtFreeFrom`, `Discounts.discount(Discounts.FREE_FROM)) // FREE_FROM = 100 · …`); one it can't (private) stays a number and the comment says whose (`// 50 is Discounts's BULK_FROM · …`); a field the constructor sets from an argument, passed the same value as the parameter it's compared with, is one local passed to both (`int freeFrom = 50; … new Delivery(freeFrom).isFree(freeFrom)`). Rust: a `const` in the function's file, and a field of the receiver of the parameter's type; its value is now tried among the inputs too. Kotlin's suggestions are unchanged. The events' `suggestion` gains `named` and each receiver's `parameters`.
- **A card's headline is plain words with its code bold (Java),** as the Rust edition's is; the words were bold up to the first code term and plain after it.
- **Rust: covering tests in the Java edition's order,** the function's own test module first, then by name.
- **A removed part that still runs is shown as what's left (Java).** Removing a call or an assignment leaves the receiver and arguments Java works out first, so the `+` line now shows them as statements, `- out.append(System.lineSeparator());` / `+ System.lineSeparator();`, `+ count++;`, `+ next();` for `total = (next());`; the `= change … (not shown in the source)` line is kept only when what's left can't be written as a statement (`prefix + next()`). Rust's cards already show the source the mutant compiles.
- **Card rendering fixes (Java).** A conditional's arm on its own line (`low :`, `1 :`) is part of the statement, not a label; a line that starts with a closed comment (`/* x */ code`) has its code, and a line that ends a comment (`… */`) doesn't; a receiver kept alone (`raw\n    .strip()`) takes its line break, not a lone `;` line; an empty `--only` id is refused, saying what's wrong (both editions; Rust's ran every mutant).
- **A name a card uses says what it is and what it was.** A suggestion first tries the receiver as a covering test makes it, read from the test's source (`new Delivery(50)`; Rust: `Delivery::new(50)` in the test module beside the function), and when that call tells the mutant apart the test makes it the same way: `var delivery = new Delivery(50); // as DeliveryTest#smallOrdersPayForDelivery builds it`, `assertTrue(delivery.isFree(50)); // total == freeFrom · today true · with this mutant false`. The evidence says what the name is and its value: `inputs seen: total = 20, 80, with freeFrom = 50 (Delivery's field, from new Delivery(50))` and `none has total == freeFrom`; otherwise `the edge is FREE_FROM (Discounts.FREE_FROM = 100)` or `the edge is freeFrom (Delivery's field, set by its constructor)`. Events gain `suggestion.builtBy` and `suggestion.named.meaning` (Java).
- **A `char` reads as a character (Java).** Where javac writes `'/'` as `47`, a card now writes `'/'` again, by the type: an argument a `char` parameter takes, or the character `indexOf`, `lastIndexOf` and `Character`'s methods take as an `int` (`internal.lastIndexOf('/') + 1`, was `lastIndexOf(47)`); a number compared with, or added to, a `char` (`no test checks kind() at c == 'a'`); a `char` parameter's inputs seen (`'A', 'z' (none is 'a')`); and what a `char` method returns (`returns '\0' instead`). An `int` stays a number. Suggested tests already asserted a `char` as one, and don't take `char` arguments. The Rust edition's cards read their values from the source already. No id or score changes.

### Fixes

*From the real-project runs:*

- **Kotlin Multiplatform modules run, through their JVM target (Gradle).** A module with `kotlin("multiplatform")` and a `jvm()` or `jvm("desktop")` target was refused as having "no Java code", as mutastic read only modules with the `java` plugin. It now reads the target's compilations (common code included) and runs its tests (`desktopTest`, `jvmTest`); with one JVM target that's the default suite, with more `--suite` names one. A file named `Board.common.kt` is shown as itself, not as kotlinc's class `Board_commonKt.java` with no source. The Gradle plugin still needs the `java` plugin.

- **JUnit 4 tests run without the JUnit Platform, and a module with no JUnit at all runs.** A build that runs JUnit 4 with its own runner (Gradle's `useJUnit()`, which `kotlin("test")` picks) had no platform on its test classpath, and the worker didn't start ("internal error: the test worker didn't start"). mutastic now brings the platform, and JUnit 4's (vintage) engine for it, as it does TestNG's. A module with no tests and no JUnit, which crashed the same way after every mutant was reported not covered, now finishes.

- **A library finds the module's resources, as in the build (Gradle and Maven).** A library on the test classpath that looks a resource up with its own class loader (`ResourceBundle.getBundle(name, locale)`, say) couldn't see the module's own resources, so tests that pass in the build failed under mutastic ("the tests fail without any mutant"). The module's resources (not its classes, nor `META-INF`) are now on the classpath beside its libraries, where the build has them.

- **A class whose static initialiser failed no longer stops the worker.** A test that expects a class to fail to initialise (or a red baseline with one) ended the worker with `class redefinition failed: invalid class`; such a class can't run again, so it's left as it is.

- **Kotlin: two more of the compilers' values skipped as generated (`all` only).** A `$default` call with more than 32 arguments left out has a mask for every 32; only the last was read, so the stand-ins and masks before it were mutated. And the `$changed` `0` passed to a composable lambda's `invoke` is the Compose compiler's. Fewer mutants on such code, all of them noise; no id changes for the rest.

- **A ghosts run that finds none says so** (`--experimental=ghosts`): the summary's Ghosts row reads `none found`, and `run-finished` has `"ghosts": []`.

- **A module's directory runs its build's wrapper and its own tasks (Gradle and Maven).** Pointed at a module of a multi-project build (`mutastic run app/core`), mutastic looked for `gradlew` only in that directory, so it fell back to `gradle` on the `PATH`, or failed without one, and ran the root project's `:mutasticSetup`. The wrapper is now the nearest one up to the top of the build (its settings file; `.mvn` for Maven), and the task is the module's.

- **Each command's `--help` and reference page say how it exits,** beside the statuses every command shares.

- **The agent format's `rules:` line quotes the verify command alone:** "a fix counts when `mutastic verify <id>` passes", where "passes" was inside the command an agent would copy.

- **`run --only=a,b,c` says every mutant it was asked for (Java).** It printed only the first one's fate, and for an agent only its card; the rest were run and never shown. Each one's fate now ends the run, with the card of each one missed. The events' `only` still holds the first id; `passed` was already whether every one is caught. The Rust edition shows every one already. No id or score changes.

- **An `Integer` edge clamp is skipped as equivalent, as the `int` one is (Java).** `chosen > 3 ? chosen : 3` with `chosen` an `Integer` (or `Long`) unboxed on each read gives the same value either side of the edge, and is now skipped as `equivalent: both sides give the same value at the edge`. Scores on such code go up slightly; no id changes.

- **Windows: Maven builds run, and output reads as it does elsewhere.** On Windows mutastic couldn't start Maven: it ran `mvnw` or `mvn`, the scripts for other systems, and now runs `mvnw.cmd`, or `mvn.cmd` from the PATH. A Gradle build without a wrapper ran only where `gradle` was an `.exe`; `gradle.bat` runs too. Cards, report paths and the commands they offer wrote `\` (`src\main\java\...\Pricing.java:17`) and quoted a Windows path (`'C:\code\app'`); paths below the project are now written with `/` on every platform and a Windows path isn't quoted. Lines end with a plain newline everywhere, where Windows mixed in CRLF, and output to a pipe or file is UTF-8, where Windows wrote its legacy code page and lost `✓` and `✗`. No id or score changes. The CLI's end-to-end tests on the cards, the pricing sample and the Maven plugin now run on Windows on every change.

- **A module whose code another module of the build finds by name runs (Gradle and Maven).** When one module looked up another's class by name (`Class.forName("...Impl")`, the usual way to pick an optional implementation), the lookup failed under mutastic though it passed in the build, and the run stopped with "the tests fail without any mutant". The build's other modules are now loaded with the module's own code, as the build's one classpath has them. A library from outside the build is still loaded as a library. Scores don't change where runs already worked; no id changes.

- **`explain`, `verify` and `ignore` say when the word in the id's place isn't a mutant id.** A directory there was taken as the id, and the answer was that the current directory isn't a Gradle or Maven build. Now it says a mutant id comes first, with the command.

- **`next` counts as a run for `explain`.** After `mutastic next`, `explain`'s last-run row said "none yet". next's pass over every mutant is now kept as the last run, as `run`'s is; its later passes still rerun only what was left.

- **Cards name a class literal, and a string constant, as the source writes them.** A card on `if (!KyberParameterSpec.class.isAssignableFrom(spec))` said `ClassOrInterfaceDesc[KyberParameterSpec].isAssignableFrom(spec)`, and one on `msg.equals(Protocol.EXIT_CODE)` said `msg.equals("{}")`, the value javac writes in. Cards now say `KyberParameterSpec.class`, `int.class` (not `Integer.TYPE`) and `msg.equals(Protocol.EXIT_CODE)`; a string stays its value where the statement doesn't show which name it is. A number named by a constant still shows its value, as the input to test with. Scores and ids don't change.

- **`next` leaves a proposed mutant to a person.** A mutant proposed for ignoring (`ignore --propose`) was handed back by `next` as if no one had looked at it, and `next` never exited 0 while one waited. It's now left out of the queue and counted ("2 mutants proposed for ignoring, waiting on a person to accept them"), `next-finished` has a `waiting` count, and when only proposals are left `next` exits 0. For a line with several mutants, the agent's `decline:` line names each of them, not only the first.

- **A word a command doesn't take is refused (exit 2).** `mutastic run samples/pricing explain m855c8e3c` used to drop the extra words and run the module. Now it says "run doesn't take explain m855c8e3c: mutastic run [DIR] [:MODULE] [OPTIONS]", as the Rust edition does. A script that passed stray words now stops with exit 2.

- **`mutastic next`: the missed mutants one at a time.** It shows the missed line most worth a test first, in the order a run ranks them, with why it's first; `--top=N` shows a few, spread over the code; for an agent, one task and to run `next` again. While the code under test is unchanged, it reruns only what the last `next` left uncaught. Exits 1 while something is queued. JSON Lines gains `next-item` and `next-finished` events.

- **`mutastic baseline`: new misses told from old.** It records every mutant no test catches in `.mutastic/baseline.yaml`, once; `--prune` drops those caught now. With a baseline, the gate holds only misses that aren't in it (and holds a task that adds to it), `next` offers new misses first, and `run` says how many of the baseline's are caught now. Scores don't change.

- **The gate holds a task that takes a failing test away.** A test that failed at a gate check and is gone at a later one holds the gate, by name, for the rest of the task: deleting the test that said a task was wrong used to pass it. A test moved to another class (same name) or renamed (same body) still counts. The gate's message for a failing test the task added also tells the agent to leave it in place.

- **Finding the mutants in a big class is faster.** To check that a mutant will load, mutastic verified the whole mutated class, every method of it, once per mutant. It now verifies the mutated method alone when the class as it is verifies, and the whole class only when it doesn't. The verdict is the same: mutastic's own classes gave the same verdict and message for all 43,427 such mutants, in 6.2 s instead of 15.7 s. No result or id changes.

- **A run leaves nothing behind.** A worker killed mid-test, by a mutant that never finishes, left that test's temporary files in the system's temporary directory for good, and a process a test started and left running outlived its worker however the worker ended. Each worker now has a temporary directory of its own, deleted when it goes, and what its tests started ends with it. A project that names `-Djava.io.tmpdir` in its test JVM arguments keeps its own directory. A test that counts on finding something already in the temporary directory (a download cached between runs, a file shared with another process) needs to name one that way. A process that has detached itself, such as a Gradle daemon or a Docker container, is left alone.

- **Each mutant now costs one class redefinition fewer.** A mutant stays in place until the next one, which goes straight in if it's of the same class, so nothing is redefined back only to be replaced. A redefinition takes tens of milliseconds, more than most tests that catch a mutant: on mutastic's own engine the median mutant went from 212 ms to 145 ms, and no result changed.

- **A worker that has slowed is replaced.** A class redefinition walks every class a worker has loaded, so on a project whose tests sit in its production packages, a worker grew slower with every test it ran: on mutastic's own engine a redefinition went from about 25 ms on a new worker to between half a second and three seconds on an old one. A worker now measures what its redefinitions lose, and past a budget the next mutant goes to a new worker, which first initialises the classes the coverage pass loaded, in the same order, so a mutant in a static initialiser can't break a class for the mutants after it. On mutastic's own engine the run took about half the time, and no caught mutant became missed.

- **`ignore --prune` keeps a reviewed ignore on a mutant the run's operators leave out.** An ignore made under `stronger` counted as stale in a run under `defaults`, which reported it and let `--prune` delete it. An ignore is now stale only when its mutant no longer exists under any operator, or its line has changed.

- **A score is compared only with a run under the same operators.** A whole run under another `--operators` used to report a previous score and changed results from a different set. `last-run.tsv` now records the operators, so such a run has no comparison. A record from an earlier version still loads, and its next run has no comparison either, as its set can't be known.

- **The gate leaves room for a wrong spec.** When a test the task added fails, the gate now says to make it pass unless the spec or plan is what's wrong, in which case to say so and stop.

- **A hooked gate outside a project mutastic reads says nothing.** With `--hook`, `gate open` and `gate check` in a directory that isn't a build mutastic reads now exit 0 with no output, as a hook with nothing to gate should, so agent plugins no longer need to know which builds mutastic reads. Run by a person, the command still says the directory isn't a build it reads.

- **A hooked gate doesn't ask the agent to run `gate check`.** With `--hook`, `gate open` used to end with "`mutastic gate check` says when it's done", so an agent ran the check itself before stopping and the Stop hook ran the same mutants again. It now says the gate checks the lines when the agent finishes. Without `--hook` it's unchanged.

- **In Codex's sandbox, a build it refused says so.** Codex runs an agent's commands in a sandbox where a Gradle or Maven build can't write its caches in the home directory or use the network, and the build failed with a stack trace that never said why. When `CODEX_SANDBOX` is set and the build's failure is the sandbox's refusal ("Operation not permitted"), mutastic now adds a line saying so, and that a rule (`prefix_rule(pattern = ["mutastic"], decision = "allow")` in `~/.codex/rules/default.rules`) lets Codex run it outside the sandbox. Nothing changes outside Codex's sandbox. Docs: a Codex page under Coding agents; the mutastic plugin now works in Codex too (tasticlabs marketplace).

- **One proposed rewrite no longer stops a run.** With `--operators=proposed`, a class with a method where `?:` joins two of the project's own types (`given != null ? given : new Flat()`) ended the run with `internal error: Could not resolve class …` for every proposal of that class. Proposals are now compared without needing the project's types, and a proposal that still can't be judged is skipped as `unviable: it couldn't be judged: …` while the rest of the run goes on. A change to a nested class filed under its outer class now says which folder it goes in (`.mutastic/proposed/<Outer>$<Nested>/`).

- **A plugin's skip reason without a kind no longer breaks `--format=jsonl`.** `skipKind` was the reason's text before its first colon, which failed for a reason with no colon and could be a kind the events schema doesn't list. It's now left out unless the reason starts with `generated`, `equivalent`, `unviable`, `arid` or `user`; `statusReason` still has the reason.

- **A fresh multi-module Gradle checkout runs (Gradle only).** On a checkout never built, or after `./gradlew clean`, a module whose tests use another module's jar (any build using `java-library`) stopped with "the tests fail without any mutant", because mutastic built only that module's classes and the other module's jar didn't exist yet. mutastic now builds everything the test task's classpath names, as the test task would. The Gradle plugin's `mutasticWriteSetup` also ran the module's whole test task before writing its setup; it no longer does, so a plugin run starts sooner. Maven builds weren't affected. Scores don't change.

- **A suggested test no longer says a mutant "doesn't return" when it does.** A suggestion's call had 200 ms before mutastic took it as one that never returns, so on a busy machine a card could say `// today 1 · with this mutant doesn't return` for a mutant that returns at once, and the same run could give a different card on another machine. A call now has 2 s; one that really loops costs that once.

- **A card lists its covering tests in the same order every run.** "Covered by" listed the tests in the order they ran, fastest first, and timings move with the machine's load, so the same card could list them differently from one run to the next. Now the mutant's own test class's tests (`PricingTest`'s for `Pricing`) come first, then the rest by name, in the cards, `coveredBy` in the events and report files, and `succeedingTests`. A suggested test goes into the first listed test's class, which was the fastest test's: it's now the mutant's own test class when one of its tests reaches the mutant. The tests still run fastest first. Card text only: no score or id changes.

### New operators

- `mutastic/bitwise` (stronger): `&`, `|` and `^` each become the other two, `<<` and `>>` swap, and so do `>>` and `>>>`, on `int`, `long` and `boolean`, as the Rust edition's operator of the same id does. `~x` (javac's `x ^ -1`) isn't changed, and `&=`/`|=` never become `^=`. `defaults` runs are unchanged; `stronger` runs on code that uses bitwise operators get more mutants, and their scores move. No existing id changes.

- `mutastic/return-value` (defaults): replaces `mutastic/return-default`; see Scoring changes.
- `mutastic/remove-discarded-call` (defaults): a call whose result is thrown away, removed; `Objects.requireNonNull(x);` is skipped as arid.
- `mutastic/comparison` (stronger): a comparison becomes the one that differs from it on one side of its edge (`<` to `!=`, `==` to `<=` and `>=`); only on numbers, `NaN`-safe for `float` and `double`, and a size or length changed only below zero is skipped as equivalent.
- `mutastic/other-comparison` (stronger): every other change of a comparison, and any condition's opposite; replaces `mutastic/negate-conditional`.
- `mutastic/logical-connector` (defaults): `&&` to `||` and back, in a condition of two tests; conditions of three or more, nested `if`s and a test that reads what a pattern binds are left alone.
- `mutastic/remove-assignment` (defaults): an assignment to a variable that already has a value, removed; a first assignment isn't changed, code without its table of local variables gets none, and one nothing reads is skipped as equivalent.
- `mutastic/remove-field-write` (stronger): a write to a field, removed; constructors and static initialisers are left alone, and a plain setter is skipped as arid.
- `library/swap-string` (defaults): `startsWith`/`endsWith`, `toUpperCase`/`toLowerCase`, `stripLeading`/`stripTrailing`.
- `library/swap-index-of` (stronger): `indexOf`/`lastIndexOf`; a search only tested for being there is skipped as equivalent, and one with a starting point is left alone.
- `library/swap-math` (defaults): `Math.min`/`max`, `Math.floor`/`ceil`; rounding a value just converted from a whole number is skipped as equivalent.
- `mutastic/omit-call` (stronger): a call that only wraps a value, left out, `text.trim()` to `text`; `String`'s and the string builders' methods, `Math.abs`, and the project's own non-generic methods.
- `mutastic/swap-arguments` (stronger): a call's last two arguments of one type, swapped; not `Object`, and a commutative call or one value twice is skipped as equivalent.
- `mutastic/null-parameter` (stronger): a parameter holding an object, `null` from the start of the method; one nothing reads is skipped as equivalent, and code without its table of variables has none.
- `mutastic/drop-vararg` (stronger): an array built for a call on the spot, without its last element.
- `library/omit-argument` (stronger): curated JDK overloads without their last argument, `indexOf(x, from)` to `indexOf(x)`.
- `mutastic/flip-increment` (stronger): a local variable's step the other way, `i++` to `i--`, `i += 2` to `i -= 2`; a step nothing reads is skipped as equivalent, and an enhanced `for`'s own index is left alone.
- `mutastic/remove-negation` (stronger): a minus sign removed, `-x` to `x`, on all four number types.
- `mutastic/other-arithmetic` (stronger): every other change among `+`, `-`, `*`, `/` and `%`, on `int`, `long`, `float` and `double`, beyond what `mutastic/math` and `mutastic/arithmetic-replacement` make.
- `mutastic/keep-operand` (stronger): `a + b` to `a` and to `b`, both still worked out; a constant beside a variable isn't what's kept.
- `mutastic/constant-value` (stronger): a number, a `static final`'s included, to one next to it and to `0`, `1` and `-1`; booleans and javac's own numbers are left alone, and array sizes, capacities, waits, a `split`'s limit and a variable's first `0` or `1` are skipped as arid.
- `library/unchecked-arithmetic` (stronger): `Math.addExact`, `subtractExact`, `multiplyExact`, `incrementExact`, `decrementExact`, `negateExact` and `toIntExact`, and `StrictMath`'s, as the plain operation, which overflows instead of throwing.
- `stream/remove-other-stage` (extended): `peek`, and `map` on a primitive stream, removed; `Stream.map` is left alone, as it can change what the stream holds.
- `predicate/swap-connector` (extended): `Predicate.and` and `or`, on `BiPredicate` and the primitive predicates too.
- `predicate/remove-negate` (extended): a predicate's `negate()`, removed.
- `predicate/remove-not` (extended): `Predicate.not(p)` to `p`.
- `optional/swap-present` (extended): `isPresent` and `isEmpty`; skipped as unviable in a class file older than Java 11.
- `optional/empty` (extended): `Optional.of(x)` and `ofNullable(x)` to `Optional.empty()`, and the primitive forms.
- `optional/remove-filter` (extended): `Optional.filter`, removed.
- `optional/always-default` (extended): `opt.orElse(x)` to `x`.
- `optional/no-default` (extended): `opt.orElse(x)` and `orElseGet(s)` to `opt.get()`.
- Rules files can now use the `keep argument` rewrite and a `since:` field naming the Java release a rewrite needs.
- `mutastic/remove-switch-arm` (extended): one `case` of a `switch` sent to the default, per label; where the only default is javac's own, a value that reached the arm throws, and the card says so.
- `mutastic/replace-body` (extended): a method's whole body, to returning one value or nothing; a `boolean` gets both values. Meant as a first pass run alone, to find methods no test notices.
- `mutastic/drop-catch-type` (extended, experimental): one type of a multi-catch, no longer caught.
- `mutastic/remove-throw` (extended, experimental): a `throw` removed, and the code carries on; with nothing after it, skipped as unviable; javac's own throws are left alone, and a failed `assert`'s is skipped as arid.
- `mutastic/string-constant` (stronger): a string in the code to `""`, and an empty one to a word; what goes into a log call, an exception or a failed check is skipped as arid. Expect misses on text a person reads.
- `mutastic/regex-constant` (extended): a regular expression going straight into `Pattern.compile`, `matches`, `split`, `replaceAll` or `replaceFirst`, with an anchor gone, a class or `\d` the other way round, or a quantifier gone; it also runs in constructors and static initialisers.
- Plugins shipped in the distribution's `plugins` directory, off until listed in `mutastic.yaml` and chosen, all in `extended`:
- `annotations/remove-validation`, `annotations/remove-security` (`mutastic-plugins.jar`): one annotation removed. Each mutant loads every class anew, and a survivor costs a run of every test.
- `kotlin/empty-return` (`mutastic-plugins.jar`): an empty range or sequence, in what kotlinc compiled.
- `proposed/rewrite` (`mutastic-plugins.jar`): rewrites kept as Java files in `.mutastic/proposed`, compiled and checked; mutastic calls no model.
- `bigdecimal/swap-arithmetic`, `bigdecimal/swap-scaling`, `bigdecimal/remove-step` (`bigdecimal.yaml`).
- `reactive/remove-stage`, `reactive/remove-recovery`, `reactive/swap-match`, `reactive/swap-order` (`reactive.yaml`).
- New in the plugin API: `ClassMutator`, for a change to a class as a whole.

### Compatibility and distribution

- **A Compatibility page** in the reference says what stays the same between releases: mutant ids (and the one way an id can come to mean another mutant, when its method's code changes), scores (a patch release never moves one; a minor release that does says how here), and the plugin API.
- **`@Internal`** marks what's public in `mutastic-api` only for mutastic's own modules: the result model, build tools, `Policy`, `BuiltIn` and a few methods of `Mutant` and `Project`. A plugin written against `Mutator`, `ClassMutator` and `Filter` is unaffected; one that named a `BuiltIn` constant should name the operator by its id. `BuiltIn.RETURN_DEFAULT` and `NEGATE_CONDITIONAL` are gone since 0.5.0 (see Scoring changes).
- **`io.mutastic:mutastic-plugins`** is on Maven Central, beside the copy in the distribution's `plugins` directory.
- **The Gradle plugin works with the configuration cache and Isolated Projects,** and says so on the Plugin Portal.
- **JSON Schemas** for the `--format=jsonl` events, `mutastic.yaml` and rules files, at https://docs.mutastic.io/schemas/events/v1.json, `/schemas/mutastic-yaml/v1.json` and `/schemas/rules/v1.json`. The build checks every event against the events schema and holds it to the last release's, and the reference has a Schemas and stability page saying what may change in v1.

- **Events say which edition wrote them (`mutastic.events/v1`).** Every event may carry `edition`, `java` or `rust`, and one without is the Java edition's. The Java edition writes `edition` on `run-started` and `run-finished`, and `toolchain` (`{"name": "jdk", "version": "17"}`) beside `jdk`. `jdk`, a mutation's `bytecode`, and a missed mutant's `ignore` and `propose` are now required only of the Java edition's events, which every event without an `edition` is. The Java edition still writes them all, so a reader of Java output finds nothing missing. The schema adds `RuntimeError` as a status and documents the Rust edition's own fields: `nearUnsafe`, `notMutated.unsafe`, `runtimeError`, `profile`, `unsafe`, `location.column` and `build`. A reader that treats an unknown status as neither caught nor missed, as the schemas page asks, needs no change. Superseded in part by Breaking changes: `edition` is on every event, and `bytecode` is gone.

### Running

- **`--shard=N/M` splits one run across CI jobs, and `--from-shards=DIR` puts it back together**. `mutastic run --shard=2/4` runs only the second of four shares of the module's mutants, dealt by each mutant's id, so every mutant is in exactly one share and the shares come out about the same size. Each share keeps what putting it back together needs in one folder, `shares/N-of-M/` in the module's work directory: its events (as `--format=jsonl` writes them, whatever the format shown) and its own run record, so a share compares only with the same share's last run. Run shares with `--threshold=0`; then `mutastic run --from-shards=DIR --threshold=70`, with every share's folder somewhere under `DIR`, runs no mutants: it finds them in the build as a whole run would, takes each result from its share, and is the whole run, with the same summary and cards in every format, the same report files, the threshold checked on the whole score, and the whole run's record for `explain`, `next` and the next run to compare with. It refuses (exit status 2, saying what's wrong) a share missing or there twice, one that didn't finish, shares split differently, a mutant in two shares, and shares run by another mutastic or on other code than each other or the build. The events gain `share` on a share's `run-started`, a `suggestion` on a mutant that has one, and `workers`, `workersStarted` and `coverageMs` on `run-finished`. The docs guide "Changed lines, other tests and suites" has a GitHub Actions example. No scoring change: a run without `--shard` is as before.

### Agent output

Both editions. No id or score changes.

- **An agent's proposal carries its kind and a reduction.** The agent format's `or propose` line is now `mutastic ignore <id> --propose --as=<equivalent|unreachable|…> --reason="Differs only when <case>. That can't happen because <why>." <project>`, and the `decline:` line asks for the kind and the two sentences. `ignore --propose --as=equivalent` (or `unreachable`) refuses a reason without a "because", saying what's wanted; any proposal that still has the template's `<case>` or `<why>` is refused; other kinds, and a person's own `ignore`, keep a free reason. **Breaking** for a script that ran the old `or propose` command as it was printed.
- **mutastic's own equivalent skips say why in the same shape** where there's a case to name: a size or length compared with zero, a test of an `||` the next one covers, a whole number rounded, an anchor on a whole-text match, `@NotNull` on a primitive (Java); a `?` on a formatter's error (Rust). Others (nothing reads the value, both sides agree at the edge) keep their words.
- **Mutants no test reaches list their ids in the agent format,** by line, each with its `or propose` command (several on a line share one, `for each of …`).
- **The gate names every mutant that holds it,** by id, those no test reaches too (`no test reaches: m04b90863, m304d2733`), says a proposed mutant is "proposed, waiting on a person" rather than missed, and leaves proposed ones out of its cards. It used to say "2 mutants … are missed", showing the two already proposed, while two not-covered mutants without ids were what held it.
- **The gate hands over at once when an agent sent back changes nothing.** A hooked check keeps the working tree's hash when it sends the agent back; if the next check finds it unchanged, the agent may stop and the person is told what's left, where the agent was sent back for every try. A change, even one that doesn't close the gap, is still a try.
- **The gate doesn't tell an agent to make a test that was there before the task pass.** When tests fail before any mutant, it names those that were in their class's source when the task started, and tells the agent to find out whether the change or the test is wrong, and to ask.
- **A pass names an existing test the task weakened.** When the gate passes or hands over, it names the test files that were there when the task started and lost an assertion or expectation, for the person to check: a test made to fit a wrong change catches every mutant, so the score can't show it.
- **The Equivalent mutants page has "How to argue a mutant can't be caught"**, equivalent and unreachable examples each with what pins its "because", and Rust tabs throughout; the mutastic plugin's skill teaches the two-line reason.

### Installing

- **One line installs `mutastic` for Java, Kotlin and Rust projects.** `curl -fsSL https://mutastic.io/install.sh | sh` installs the native `mutastic` (mutastic-rs), which runs Rust crates itself and, the first time it runs in a Maven or Gradle project, fetches the Java edition, checks it against its release's checksums and keeps it in `~/.mutastic`. The Java edition needs JDK 25 only for Java projects. `install.sh` in the Java repository now runs that installer. `MUTASTIC_VERSION` picks the Java edition's release when `mutastic` runs, rather than at install. The Gradle and Maven plugins are unchanged.
- **The native `mutastic` runs the newest Java edition patch of its own minor version.** The editions release each minor version together and either may ship a patch alone, so `mutastic 1.0.0` runs the newest Java 1.0.x, fetching it if it isn't kept. It looks the releases up at most once a day, runs the newest matching release it has kept when they can't be reached, and when a newer patch can't be fetched yet (its GitHub release is published before its CLI is attached) runs the kept one of the same minor, saying why. `MUTASTIC_VERSION` still picks one exactly.
- **Windows (Rust edition's builds):** x64 and Arm64 zips with each release; `irm https://mutastic.io/install.ps1 | iex` in PowerShell installs one and puts it on the user `Path`; `install.sh` in Git Bash, MSYS2 or Cygwin installs the same build; each release has a Scoop manifest, and `cargo binstall --git https://github.com/mutastic/mutastic-rs mutastic` works. In a Maven or Gradle project on Windows, `mutastic` fetches and runs the Java edition.

- **docs.mutastic.io shows both editions,** with a Java | Rust switch at the top of the sidebar, the concepts both share written once, a page for each operator family (each operator with the bug it stands for, a real card and the test that catches it), a Coding agents section (the Claude Code and Codex plugins, how the gate decides, opencode and other agents), a Running in CI guide for GitHub Actions and GitLab CI, and a Compatibility page.

### Experimental

- **`--kill-matrix` (for measuring, slower).** A run with it runs every test that reaches a caught mutant, not only until the first fails, and JSON Lines names each catcher in `caughtByAll`. It's what the replay of `next`'s order against random order reads (`tools/replay.py`). Scores don't change.

- **Ghosts (`--experimental=ghosts`, or `MUTASTIC_EXPERIMENTAL=ghosts`).** Where most writes to a bean's fields fire a `PropertyChangeSupport` property change and one doesn't, mutastic inserts the call the others make after that write and runs the tests that reach it. A ghost that no test notices is listed apart, as a question with both answers; one a test notices names that test. Ghosts are never in the score, the counts or the gate, and `--format=jsonl` lists them under `ghosts` in `run-finished`, each with `"experimental": true`.

## 0.5.0 (5 Nov 2026)

### The gate: a coding agent's task held to its mutants

```sh
mutastic gate open     # where the task starts
mutastic gate check    # is it done?
mutastic gate close
```

`gate check` passes when every mutant on the lines changed since `gate open` is caught, or proposed for a person to ignore. An ignore the task made itself holds it, and so does a test deleted or disabled. Until then it answers with the cards, in the agent format, so the agent can carry on. With `--hook=claude` it reads and answers as a Claude Code hook. After `--tries`, it lets the agent stop and tells the person what's left, rather than sending the agent round for ever.

The [tasticlabs plugin](https://github.com/tasticlabs/plugins) wires it into Claude Code for you:

```
/plugin marketplace add tasticlabs/plugins
/plugin install mutastic@tasticlabs
```

### An agent proposes an ignore, and a person accepts it

Whether a mutant's case can happen in practice is a person's call. `mutastic ignore ID --propose --reason="…"` records the proposal in `.mutastic/proposals.yaml`, where the mutant still counts as missed. `ignore --accept ID` makes it an ignore, with its reason and kind. `--remove` withdraws it. Cards offer agents `or propose` where people get `or ignore`, and the event stream has both.

### Advice an agent can act on

Each card's claim is now checked against Java itself: it's written into the source, compiled, and run against the mutant on a grid of inputs. That check found, and this release fixes:

- **A removed condition on a boolean** read backwards for the first test of an `||`. It's now read from the jump itself.
- **A condition split over lines** had the wrong line rewritten. `wide < 1L` was rewritten as if it were `wide < 1`. A line is now rewritten where the mutated comparison is, by whole words.
- **Cards quote the source more exactly:** a class's own statics bare, and comparisons by their names.

Also:

- **`verify` on a skipped mutant** says it's skipped, and why, and passes. It no longer says no test reaches it.
- **A flaky test's advice goes by why it's flaky.** The test makes its own flakiness (an unseeded `Random`, the clock): fix it. It comes from outside the code: leave it, and tell the person. It's in the code under test: fix it through its seam. Unknown: say so. In evals, telling an agent to "fix it first" for a slow shared service led to retries in every run, hiding the timeout. JSON Lines has the evidence as `flakyEvidence`.
- **When a JDK service the project provides** (a `System.LoggerFinder` in `META-INF/services`) is why the tests fail under mutastic, the failure says so.

### Fewer false misses

- **JDK services are found as in the build.** The worker's system class loader now finds the project's classes. So a test that installs a `LoggerFinder` or `FileSystemProvider` passes under mutastic as it does in Gradle. This works with `-javaagent` jars such as JaCoCo's and Mockito's, but not in framework mode.
- **New equivalent skips:**
  - a clamp to a constant at its edge (`fee < 10 ? 10 : fee`, `if (x < 2) x = 2;`), for `int` and `long`;
  - the first test of an `||` whose case the next test already covers (`inCredit(balance) || balance > -1000`).

  Both are checked on every input by the truth check.
- **`--tests-from` through another module.** Say `app`'s tests run over `core`'s mutants, and `app` also uses `web`, which uses `core`. `web` is now loaded beside the mutated classes, not as a library, so it uses them instead of failing to find them.
- **The summary** counts the workers that ran, so a small run no longer says "-1 replaced".

- **[Flaky tests](https://docs.mutastic.io/concepts/flaky-tests/):** what mutastic says, and why.

## 0.4.0 (4 Nov 2026)

### Install in one line

```sh
curl -fsSL https://mutastic.io/install.sh | sh
```

It installs into `~/.mutastic`, links `mutastic` into `~/.local/bin`, and updates when run again. This release is the first with `SHA256SUMS`, which the script checks the download against. The Gradle plugin now resolves from the Gradle Plugin Portal with no `pluginManagement` setup.

### Scores change in this release

Expect your score to move, for these reasons, not because your tests changed:

- **`negate-conditional` left the defaults** and is now only in `stronger`. A test can catch a negated condition while leaving both "always true" and "always false" uncaught. The reverse never happens: a test that catches either of those catches the negation too. In the defaults, negate's catches only added to the score. PIT made the same change in 1.7.2. Scores usually fall: mutastic's own engine module went from 57.4% to 53.8%. `--operators=stronger` brings negate back.
- **Code that runs only while a class loads is now really tested.** A mutant in a method only a static initialiser calls used to be reported as missed, because the class was already loaded. It now runs in a fresh class loader, so those false misses become catches.
- **New default skips,** each recognised from the exact instructions involved:
  - `equivalent:` a boundary where both sides give the same value at the edge (`if (x > max) max = x;`, `a < b ? a : b`).
  - `arid:` arithmetic that only sets a collection's starting size (`new ArrayList<>(n * 2)`) or how long to wait (`Thread.sleep(s * 1000)`), and removing a `sleep`.

### Less to read, and more to act on

- **One card per line.** The missed mutants on one line share a card. It shows each distinct suggested test once, and its `done when` checks them all: `mutastic verify a,b`. Use `--each-mutant` (`eachMutant` in the build plugins) for a card per mutant.
- **`verify` takes several ids,** as do `--only=a,b` and `-Dmutastic.mutant=a,b`. It passes only when every one is caught.
- **Code no test reaches is listed once per method,** and the result adds a score for the code tests do reach (`coveredScore` in JSON Lines). The threshold still applies to the whole score.
- **Ranking and caps.** The agent format's ten entries come most valuable first: conditions and removals before arithmetic. People see at most seven cards a file, with the rest counted.
- **When not to write a test.** The agent format and JSON Lines now tell agents to say why, and ignore the mutant with that reason, when a mutant's case can't happen in practice or its change is one no caller can see.
- **`mutastic ignore --as=KIND`** records what sort of decision an ignore is: `equivalent`, `unreachable`, `telemetry`, `deprecated` or `accepted-risk`. The summary counts ignores by kind, and three or more ignores in one method suggest one `skip:` rule.
