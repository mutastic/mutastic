{/* Every version on this page is `release`, the newest release tag's: none is typed in. */}

For a Java or Kotlin project, mutastic runs on JDK 25. The project it tests can be on JDK 17 or
later, with JUnit or TestNG tests.[^tests]

<Tabs syncKey="runner">
<TabItem label="Command line">

```sh
curl -fsSL https://mutastic.io/install.sh | sh
```

That one line installs the `mutastic` command for Java, Kotlin and Rust projects alike. It
downloads the native `mutastic` for your machine into `~/.mutastic`, checks it against the
release's checksums, and links it into `~/.local/bin`, which must be on your `PATH`; if it isn't,
the installer prints the line to add. The script is
[`install.sh`](https://github.com/mutastic/mutastic-rs/blob/main/scripts/install.sh) in mutastic-rs's
repository, to read before you run it.

The first time `mutastic` runs in a Gradle or Maven project, it fetches the Java edition, checks
it against its release's checksums, and keeps it in `~/.mutastic`; after that it runs straight
away. The Java edition runs on the `java` in `JAVA_HOME`, or on the `PATH`, which must be JDK 25 or
later, and `mutastic` checks for one before it downloads anything. A Rust project needs no JDK.

Running the installer again updates the native `mutastic`. From 1.0.0 the Rust and Java editions
are released together, at the same version, and `mutastic` uses the Java edition with its own
version; before 1.0.0 it uses the newest it has kept, or the latest release when it has none.
`MUTASTIC_VERSION=0.3.0` uses that release instead, fetching it if it isn't kept, and `MUTASTIC_HOME` and `MUTASTIC_BIN_DIR` choose the
directories. `mutastic --version` shows the version of each.

Then, in a Gradle or Maven project's directory:

```sh
mutastic run
```

mutastic builds the project the way you do: with its wrapper, `gradlew` or `mvnw`, whenever the
build has one, and with the `gradle` or `mvn` on your `PATH` when it doesn't.

Or the Java edition by hand: download <code>mutastic-{release}.zip</code> from the{' '}
<a href={`https://github.com/mutastic/mutastic/releases/tag/v${release}`}>{release} release</a>,
unzip it, and put its `bin` directory on your `PATH`.

<Code
  lang="sh"
  code={`unzip mutastic-${release}.zip
export PATH="$PWD/mutastic-${release}/bin:$PATH"
mutastic --version`}
/>

</TabItem>
<TabItem label="Gradle">

Apply the plugin, from the Gradle Plugin Portal, in `build.gradle.kts`. The project's repositories
need Maven Central, for the `mutastic` command the tasks run:

<Code
  lang="kotlin"
  code={`plugins {
    id("io.mutastic") version "${release}"
}

repositories {
    mavenCentral()
}`}
/>

```sh
./gradlew mutasticRun
```

mutastic runs on a JDK 25 Gradle toolchain, which Gradle finds or downloads.

</TabItem>
<TabItem label="Maven">

Declare the plugin in your POM's build plugins, so its goals take the short `mutastic:` prefix:

<Code
  lang="xml"
  code={`<plugin>
  <groupId>io.mutastic</groupId>
  <artifactId>mutastic-maven-plugin</artifactId>
  <version>${release}</version>
</plugin>`}
/>

```sh
mvn mutastic:run
```

Maven can run on JDK 17. mutastic finds a JDK 25 for itself: a JDK 25 toolchain in
`~/.m2/toolchains.xml`, else the JDK Maven runs on if it's new enough, else the one
`-Dmutastic.jdk=<directory>` names.

</TabItem>
</Tabs>

[^tests]: Its tests run on the JDK its build gives them, as they always do. They can be JUnit 5 or 6
    (Jupiter), anything else on the JUnit Platform, or TestNG, which mutastic runs with TestNG's own
    engine for the platform, so a project needs nothing extra. TestNG's groups count as the
    platform's tags: a build that leaves out a group leaves it out of mutastic's runs too.
    `@QuarkusTest` tests work as they are: Quarkus loads the app in its own class loader, and
    mutastic swaps each mutant into Quarkus's copy of the class, so the app starts once per worker,
    not once per mutant.
