## Only what changed

`--since=main` mutates only the lines changed since the branch left `main` (its merge-base), uncommitted edits and new files included: a pull request's or an agent's change, which is where a missed mutant is worth acting on. A bare `--since` means the repository's default branch. The summary says what the run covered (`Changed  12 lines in 3 files since main`); a scoped run writes its reports but doesn't replace the last full run's record. A change with no mutant on its lines has nothing to measure, so no test runs and the run passes in seconds (`Tests  none ran: no mutant to run`), leaving the last run's record and reports as they were; `--force-coverage` runs the tests anyway, to check or time them. In CI, a pull request's run needs the base branch's history: see [Running in CI](/guides/ci/#only-what-a-pull-request-changed).

## A coding agent's task

The [gate](/agents/gate/) scopes itself. `gate check` runs mutastic on the lines changed since the task started, as `--since=<that commit>` would, so there's nothing to pass it.

## Other modules' tests

A module's own tests are often not all that test it: another module that uses it may test it more. `--tests-from=:app` (as often as needed) runs `:app`'s tests over the mutants the module's own tests leave uncaught, as `:app`'s build runs them, with this module's mutated classes in place of its jar; a mutant caught by either is caught. `mutastic run :core --tests-from=:app`, or `--tests-from=dependents` for every module that depends on this one, directly or through others, as the build's own graph has it.

## Another test suite

A module's tests aren't always in one suite: integration tests often live apart, in a suite of their own that checks what the unit tests leave out. `--suite` picks which suite's tests run, `test` unless set:

| Build | `--suite` | Runs |
|---|---|---|
| Gradle | `test`, or any `Test` task's name, `integrationTest` say | That task's tests, from its own source set, with its JDK, JVM arguments, classpath and environment |
| Maven | `test` | Surefire's tests, as `mvn test` runs them |
| Maven | `integration-test` (or `integrationTest`) | Failsafe's tests, `*IT` by default, as its `integration-test` goal runs them |

```sh
mutastic run --suite=integrationTest
```

From a build plugin, `-Pmutastic.suite=integrationTest` or `-Dmutastic.suite=integration-test` for one run, or for every run `suite = "integrationTest"` in `mutastic { }`, or `<suite>integration-test</suite>` in the Maven plugin's configuration. A suite the build doesn't have is an error that lists those it does.

A suite but `test` keeps its own run record and reports, under `suites/<name>/` in the module's work directory (`build/mutastic/suites/integrationTest/`), so its runs compare only with its own. The commands a run offers keep the suite: `mutastic verify m2f3930a4 --suite=integrationTest` checks a mutant against the tests that found it.

## One run across CI jobs

`--shard` splits a module's run across CI jobs, and `--from-shards` puts the shares back together: see [Running in CI](/guides/ci/#one-run-across-ci-jobs).

## One line

When you're fixing a line, or an agent is working on one function, you have a file and a line in
hand, not mutant ids. `--at` takes them: `--at=<file>:<line>`, or `<file>:<from>-<to>` for the
lines between, counted from 1 as an editor counts them. `mutants --at` lists what's there, and `run
--at` runs it:

```sh
mutastic mutants --at=src/main/java/com/example/pricing/Pricing.java:17-20
mutastic run --at=src/main/java/com/example/pricing/Pricing.java:17-20
```

<Code code={atMutants} lang="ansi" />

A mutant is on a line when its card points at the line: from the line its statement starts on to
the one its change is on, so each line of a statement written over several has its mutants. The
operators are the run's own, as a full run would have them on those lines; with `--since`, only
those on the change. Several files or spans go in one option, split by commas
(`--at=Pricing.java:17,Tier.java:3-5`), or in several.

The run is about those mutants, as [one mutant's](#one-mutant) is: it says each one's fate, after
a line that counts them, and passes when every one is caught or skipped. It has no score, writes no
report and isn't kept as the last run.

<Code code={atRun} lang="ansi" />

The path is absolute, or from where you run mutastic, or from the project, as a card prints it. The
file must be one of the module's sources; in a build of several modules it picks its module, so
`mutastic run --at=app/src/main/java/com/example/app/Checkout.java:9` from the build's top runs
`:app`. Lines with no mutant on them are an error, never a run of none: it names the nearest lines
that have one, and the `mutants --at` command that lists them. The lines are read from the file on
disk, so an editor's unsaved changes aren't in them.

From a build plugin it's `-Pmutastic.at` or `-Dmutastic.at`:

```sh
./gradlew mutasticRun -Pmutastic.at=src/main/java/com/example/pricing/Pricing.java:17
mvn mutastic:run -Dmutastic.at=src/main/java/com/example/pricing/Pricing.java:17
```

## One mutant

With `--only=<id>` the run is about one mutant, so it passes when that mutant is caught (or skipped, with nothing to catch), as `verify` does, and says the mutant's fate rather than a score. Given several ids (`--only=<id>,<id>`), it says each one's fate, with the card of each one missed, and passes when every one does.
