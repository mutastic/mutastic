Some mutants are never worth a test: code a generator wrote, a call that only logs. Left in, they
count against the score, and the gaps worth closing hide among them. mutastic skips some on its
own, and a project can say which others to skip, or bring back, always with a reason, so the score
is about the code you mean to test and anyone reviewing a skip can see why it's there.

## A rule, and what it changes

The `configured` sample in mutastic's repository has a class its tests check, and one a code
generator wrote, tested where it's generated:

{/* from: samples/configured/src/main/java/com/example/configured/generated/Checksums.java */}
```java
public final class Checksums {
  private Checksums() {}

  public static int of(byte[] bytes) {
    int sum = 1;
    for (byte b : bytes) {
      sum += b;
    }
    return sum;
  }
}
```

With no `mutastic.yaml`, the generated code's mutants count as not covered, and the score says
more about the generator than about the tests:

One rule in `mutastic.yaml`, beside the build, says to skip that package, and why:

{/* from: samples/configured/mutastic.yaml */}

    reason: written by a code generator

## What mutastic skips

mutastic skips these on its own, and gives the reason with each. Skipped mutants don't count
towards the score.

- **Equivalent changes,** which can't be told apart from the original: `return 0` becoming "return
  the default".
- **Code the compiler wrote:** a `switch` on a `String`, a record's `equals()`.
- **Calls that only write output:** logging, `System.out`.
- **Trivial accessors:** a getter that only returns one of its class's fields, or a setter that
  only stores its argument in one, named for that field. An accessor with any logic (a copy, a
  check, lazy set-up, a notification) is mutated like any code.
- **`toString()` and `hashCode()`,** with the lambdas they define and the helpers only they call.
  `toString()` is a debug representation, and `hashCode()` may return any value consistent with
  `equals()`.

`@DoMutate` on a method or class brings back what mutastic would skip there as trivial: its
accessors, or a `toString()` or `hashCode()` that's a contract.

### Annotations

- `@DoNotMutate` or `@CoverageIgnore` skips a method or class, with its `value()` or `reason()` as
  the reason.
- `@DoMutate` brings back trivial code, as above.
- `@Generated` marks code a tool wrote.

Annotations are matched by simple name, so your own work. Or depend on
`io.mutastic:mutastic-annotations`, a small jar with `@DoNotMutate` and `@DoMutate` and nothing
else. mutastic reads them from the class files, so the jar is never needed at run time.

## mutastic.yaml

A project's own say goes in `mutastic.yaml`, in its directory:

```yaml
rules:
  - skip: com.acme.generated.**      # ** any depth, * one name, Class#method one method
    reason: protobuf output
  - mutate: com.acme.Money#toString  # brings back what mutastic would skip as arid
    reason: shown to customers
plugins:
  - build/libs/acme-filters.jar      # a jar: filters and operators of your own
  - mutiny.yaml                      # a rules file: call operators, as data
filters:
  - acme:no-metrics                  # a plugin's filter runs only when named here
operators:
  - defaults                         # which operators run, as --operators chooses
  - -stream/swap-match
```

`plugins:` lists jars and rules files, relative to the project: see [Plugins](/guides/plugins/).
`operators:` chooses which operators run, the same way as [`--operators`](/reference/run/#operators),
which replaces it for one run. The sets are `defaults` (what runs unless told otherwise), `stronger`
(the defaults and the operators that find more but need more care to read), `extended` (the
operators on modern APIs and language features, such as `Optional`, more of streams, `switch` arms, regular expressions, exceptions and whole method bodies,
added to another set:
`defaults,extended`) and `all` (every operator); see [Choosing
operators](/concepts/operators/#choosing-operators).

mutastic reads the file strictly, and a line it doesn't understand is an error that names it. [Its
JSON Schema](https://docs.mutastic.io/schemas/mutastic-yaml/v1.json) says the same, so an editor
that knows JSON Schema flags a mistake as you type. With the YAML language server, name it on the
file's first line:

```yaml
# yaml-language-server: $schema=https://docs.mutastic.io/schemas/mutastic-yaml/v1.json
```

See [Schemas and stability](/reference/schemas/).

An annotation on the code comes first, then a rule, then mutastic's own filters. A `mutate:` rule, like `@DoMutate`, brings back only what mutastic would call arid, never generated or equivalent code. Every rule needs a reason, which is shown with each mutant it skips.

## Ignoring one mutant

For one mutant no test should catch, `mutastic ignore ID [dir] [:module] --reason="…"` records the decision in `.mutastic/ignores.yaml`, with where the mutant is, what it changes, the line it's on and the reason. Commit it: each entry is a decision someone reviews. An ignore holds until its line changes; then the mutant runs again, and the run says the ignore no longer holds (`mutastic ignore --prune` removes those). An ignore on a mutant of an operator the run doesn't use still holds, as long as its line hasn't changed. Each says where it wrote and how to undo it: `mutastic ignore --remove ID` takes one back. Every missed mutant's card offers the command (`or ignore`), and an ignore never hides code the compiler wrote or a change that can't be told apart from the original.

A coding agent proposes an ignore instead of making one: `mutastic ignore ID --propose --as=unreachable --reason="…"` records it in `.mutastic/proposals.yaml`, and until a person accepts it the mutant still counts as missed. `mutastic ignore --accept ID` makes it an ignore, with its reason and sort as proposed, and `--remove` withdraws it. Commit the proposals too: reviewing a pull request is where a person decides them. The agent format offers `or propose` where a person's card offers `or ignore`, since whether a case can happen is a person's decision.

`--as` says what sort of decision it is: `equivalent` (no test could tell the change apart), `unreachable` (its case can't happen in practice), `telemetry` (it only feeds logs or metrics), `deprecated` (the code is on its way out) or `accepted-risk`. The summary counts ignores by sort (`3 ignored as unreachable`), so what they hide can be reviewed by sort. Three or more ignores in one method are one decision said again and again: the run suggests the `skip:` rule that says it once.

To see what the arid skips hide, `MUTASTIC_ARID=audit` runs them anyway and adds an `Arid audit` row: how many ran, how many were caught and how many of those by a test's own assertion (a check on what the code returns, which may make it a contract worth `@DoMutate`), and where.
