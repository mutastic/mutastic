Some mutants are never worth a test: code a generator wrote, a call that only logs. Left in, they
count against the score, and the gaps worth closing hide among them. mutastic skips some on its
own, and a project can say which others to skip, or bring back, always with a reason, so the score
is about the code you mean to test and anyone reviewing a skip can see why it's there.

## A rule, and what it changes

The `configured` sample in mutastic's repository has a class its tests check, and one a code
generator wrote, tested where it's generated:

{/* from: samples/configured/src/main/java/com/example/configured/generated/Checksums.java */}
```java
public final class Checksums {
  private Checksums() {}

  public static int of(byte[] bytes) {
    int sum = 1;
    for (byte b : bytes) {
      sum += b;
    }
    return sum;
  }
}
```

With no `mutastic.yaml`, the generated code's mutants count as not covered, and the score says
more about the generator than about the tests:

One rule in `mutastic.yaml`, beside the build, says to skip that package, and why:

{/* from: samples/configured/mutastic.yaml */}
```yaml

  - skip: com.example.configured.generated.**
    reason: written by a code generator
```

The run after it skips them as `user`, out of the score. `Customer.toString()` was skipped both
times, as `arid`, by mutastic on its own:

and so do the [events](/reference/schemas/#events) and the [report files](/reference/reports/):

## What mutastic skips

mutastic skips these on its own, and gives the reason with each. Skipped mutants don't count
towards the score.

- **Equivalent changes,** which can't be told apart from the original: `return 0` becoming "return
  the default".
- **Code the compiler wrote:** a `switch` on a `String`, a record's `equals()`.
- **Arid code,** which a test could check but none should have to: a call that only writes
  output, a trivial getter or setter, `toString()` and `hashCode()`, a list's starting size, a
  removed `Thread.sleep`. [Arid rules](/reference/arid/) has each rule: what it skips, why, what it
  can hide and how to bring it back.

Sometimes what mutastic skips is part of what the code promises: a `toString()` customers see, a
getter that's an API, a log line an alert watches. `@DoMutate` on a method or class brings back
every mutant mutastic would skip there as [arid](/concepts/arid/): a whole
accessor or `toString()`, and each call that only writes output, each wait, capacity or message in
the code. Code the compiler wrote and equivalent changes stay skipped, and so does a method's own
`@DoNotMutate`.

### Annotations

- `@DoNotMutate` or `@CoverageIgnore` skips a method or class, with its `value()` or `reason()` as
  the reason.
- `@DoMutate` brings back what mutastic would skip as arid, as above.
- `@Generated` marks code a tool wrote.

Annotations are matched by simple name, so your own work. Or depend on
`io.mutastic:mutastic-annotations`, a small jar with `@DoNotMutate` and `@DoMutate` and nothing
else. mutastic reads them from the class files, so the jar is never needed at run time.

The JDK's own `@Generated` (`javax.annotation.processing.Generated`, and the older
`javax.annotation.Generated` and `jakarta.annotation.Generated`) never reaches the class file: it's
kept for the source alone. Annotation processors such as Dagger, MapStruct and AutoValue put it on
the classes they write, and so do generators such as OpenAPI Generator and jOOQ. So for a Java
class, mutastic also reads the source file: when the file's top-level type has `@Generated` on it,
that type's mutants, and those of every type nested in it, are skipped as `generated:`. Comments
and strings that mention `@Generated` don't count, and neither does `@Generated` on one member. The
source has to be in one of the module's source directories: Maven includes where annotation
processors write, and mutastic adds it for Gradle.

## mutastic.yaml

A project's own say goes in `mutastic.yaml`, in its directory:

```yaml
rules:
  - skip: com.acme.generated.**      # ** any depth, * one name, Class#method one method
    reason: protobuf output
  - mutate: com.acme.Money#toString  # brings back what mutastic would skip as arid
    reason: shown to customers
  - mutate: com.acme.Worker#run      # only what one arid rule skips: its waits
    arid: [mutastic:waits]
    reason: callers rely on run() returning once the work is done
  - output: com.acme.AuditLog#*      # your own output calls, skipped as log calls are
    reason: the audit trail, which ops read and tests don't
plugins:
  - build/libs/acme-filters.jar      # a jar: filters and operators of your own
  - mutiny.yaml                      # a rules file: call operators, as data
filters:
  - acme:no-metrics                  # a plugin's filter runs only when named here
operators:
  - defaults                         # which operators run, as --operators chooses
  - -stream/swap-match
gate:
  operators:
    - stronger                       # what the gate holds an agent's task to
```

`plugins:` lists jars and rules files, relative to the project: see [Plugins](/guides/plugins/).
`operators:` chooses which operators run, the same way as [`--operators`](/reference/run/#operators),
which replaces it for one run. The sets are `defaults` (what runs unless told otherwise), `stronger`
(the defaults and the operators that find more but need more care to read), `extended` (the
operators on modern APIs and language features, such as `Optional`, more of streams, `switch` arms, regular expressions, exceptions and whole method bodies,
added to another set:
`defaults,extended`) and `all` (every operator); see [Choosing
operators](/concepts/operators/#choosing-operators). `gate:`'s `operators:` chooses for
[the gate](/agents/gate/#which-operators) alone, in its place, so an agent's tasks can be held to
more than everyday runs: [`gate open --operators`](/reference/gate-open/#operators) replaces it.

mutastic reads the file strictly, and a line it doesn't understand is an error that names it. [Its
JSON Schema](https://docs.mutastic.io/schemas/mutastic-yaml/v1.json) says the same, so an editor
that knows JSON Schema flags a mistake as you type. With the YAML language server, name it on the
file's first line:

```yaml
# yaml-language-server: $schema=https://docs.mutastic.io/schemas/mutastic-yaml/v1.json
```

See [Schemas and stability](/reference/schemas/).

### In a build of several modules

Each module uses the nearest `mutastic.yaml` at or above its own directory, however it's run:
`mutastic run :core` from the build's top, `mutastic run` in `core/`, the Gradle plugin's task, and
`mvn mutastic:run` all read `core/mutastic.yaml` for `core` when there is one, and the top's when
there isn't. The search stops at the top of the git repository, or outside one at the directory the
run is on, so a stray file above the build is never read.

One file applies, never a cascade: a module's file replaces the top's for that module. To add to
the top's instead, say so with `extends:`, a path from the file's own directory:

```yaml title="core/mutastic.yaml"
extends: ../mutastic.yaml
rules:
  - skip: com.acme.core.legacy.**
    reason: on its way out, replaced in 2.0
```

The module's rules come first, then the top's; the plugins and filters of both apply, each plugin
found from the file that names it; and the module's `operators:`, if it has any, replace the top's.
A file names one other, which may extend another in turn.

Ignores are the run's: `.mutastic/` beside the directory the run is on, the top's for `mutastic run
:core` there and `core/.mutastic/` for a run in `core/`.

An annotation on the code comes first, then a rule, then mutastic's own filters, then a plugin's: its verdict on a whole method, and last its verdict on one mutant. A `mutate:` rule, like `@DoMutate`, brings back every mutant mutastic would call arid in the code it covers, a whole method or one call in it, and never generated or equivalent code. Every rule needs a reason, which is shown with each mutant it skips.

Every arid skip is one rule's, by an id that never changes: `mutastic:output`, `mutastic:waits`, `mutastic:capacity` and the rest. An `arid:` list on a `mutate:` rule brings back only those rules' skips, so a team whose tests measure its pauses can count its sleeps and still leave its log lines out. `@DoMutate(arid = "mutastic:waits")` does the same in the code. `mutastic explain` on a skipped mutant names its rule, links to its docs and prints the rule to copy.

### Your own output calls

mutastic knows the common loggers, but not the wrapper your team logs through, an audit log, or a
metric nobody's tests read. Without a rule, each of their calls is a mutant that only a test of the
log text would catch. An `output:` rule names them, with a reason, and mutastic skips them as it
skips a logger's calls, under `mutastic:output`:

```yaml title="mutastic.yaml"
rules:
  - output: com.acme.AuditLog#*
    reason: the audit trail, which ops read and tests don't
```

A removed call says `arid: only calls AuditLog#info (the audit trail, which ops read and tests
don't)`. So does a string or a value that only goes into one, as `arid: only feeds AuditLog#info
(…)`, and a check like `if (audit.enabled())` around nothing but those calls. The pattern names the
methods called, as `skip:` names the code: `Class#method`, `*` for one name, `**` for any depth.
The skips are arid like the rest: a `mutate:` rule brings them back, and `MUTASTIC_ARID=audit` runs
them. None are output until a rule says so, since some teams test their metrics.

<EditionOnly edition="rust">
**In the Rust edition:** an `output:` rule names a function or a macro by its path,
`crate::audit::record` or `metrics::counter`, and a statement that calls it is skipped as
`arid: only calls audit::record (…)`. The path in the code may be shorter, `audit::record` or
`record` after a `use`: its segments are matched against the end of the rule's.
</EditionOnly>

## Ignoring one mutant

For one mutant no test should catch, `mutastic ignore ID [dir] [:module] --reason="…"` records the decision in `.mutastic/ignores.yaml`, with where the mutant is, what it changes, the line it's on and the reason. Commit it: each entry is a decision someone reviews. An ignore holds until its line changes; then the mutant runs again, and the run says the ignore no longer holds (`mutastic ignore --prune` removes those). An ignore on a mutant of an operator the run doesn't use still holds, as long as its line hasn't changed. Each says where it wrote and how to undo it: `mutastic ignore --remove ID` takes one back. Every missed mutant's card offers the command (`or ignore`), and an ignore never hides code the compiler wrote or a change that can't be told apart from the original.

A coding agent proposes an ignore instead of making one: `mutastic ignore ID --propose --as=unreachable --reason="Differs only when … That can't happen because …"` records it in `.mutastic/proposals.yaml` (an equivalent or unreachable mutant's reason [says why](/concepts/equivalence/#how-to-argue-a-mutant-cant-be-caught), with a "because"), and until a person accepts it the mutant still counts as missed. `mutastic ignore --accept ID` makes it an ignore, with its reason and sort as proposed, and `--remove` withdraws it. Commit the proposals too: reviewing a pull request is where a person decides them. The agent format offers `or propose` where a person's card offers `or ignore`, since whether a case can happen is a person's decision.

`--as` says what sort of decision it is: `equivalent` (no test could tell the change apart), `unreachable` (its case can't happen in practice), `telemetry` (it only feeds logs or metrics), `deprecated` (the code is on its way out) or `accepted-risk`. The summary counts ignores by sort (`3 ignored as unreachable`), so what they hide can be reviewed by sort. Three or more ignores in one method are one decision said again and again: the run suggests the `skip:` rule that says it once.

To see what the [arid](/concepts/arid/) skips hide, `MUTASTIC_ARID=audit` runs them anyway and adds an `Arid audit` row: how many ran, how many were caught and how many of those by a test's own assertion (a check on what the code returns, which may make it a contract worth `@DoMutate`), and where.
