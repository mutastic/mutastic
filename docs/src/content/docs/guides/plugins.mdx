mutastic's [operators](/concepts/operators/) cover the language and the JDK's streams. A plugin adds
more, for the libraries and patterns your code uses. mutastic [ships some](/guides/operator-plugins/),
and you can write your own. There are two kinds:

| Kind | File | Adds | Needs |
|---|---|---|---|
| [A rules file](#rules-files) | `.yaml` | Operators on calls: remove one, rename it, or call another method instead | Nothing but the file |
| [A jar](#java-plugins) | `.jar` | Operators on any instruction or [a class as a whole](#changing-a-class-as-a-whole), and [filters](#filters) | Java, built against `io.mutastic:mutastic-api` |

List each under `plugins:` in `mutastic.yaml`, relative to the project's directory:

```yaml
plugins:
  - mutastic/mutiny.yaml
  - build/libs/acme-mutastic.jar
```

A plugin's operators then run like mutastic's own: each in the `defaults` set unless it says it's
`stronger` or `extended`, chosen by its id or namespace with [`--operators`](/concepts/operators/#choosing-operators)
(`--operators=defaults,-mutiny`), and reported, explained and ignored the same way. A plugin's code
runs in mutastic's own process, so only list plugins you trust.

## Rules files

A rules file describes call operators as data: which calls to match, by the type that declares the
method and the method's name, and how to rewrite them. mutastic's own [stream
operators](/concepts/operators/streams/#stream-stage-removal) are a rules file of exactly this shape. This
one adds two operators for [Mutiny](https://smallrye.io/smallrye-mutiny/), and mutastic's own
tests run it on a Quarkus app:

Each rule is a list item with these fields:

| Field | | |
|---|---|---|
| `id` | required | `namespace/name`, lower case: how reports, `--operators` and ignores name it |
| `explanation` | required | What it changes, and when a test misses that: shown by `mutastic explain` |
| `owners` | required | The types whose calls it matches, in full: `java.lang.String` |
| `methods` | required | The method names it matches |
| `descriptors` | | The overloads it matches, as the JVM writes them: `(Ljava/lang/String;)Z`. Every overload if it's left out. List them when a rename's target doesn't have them all: the rewrite calls the same overload of the other method, and a method that doesn't exist can't be told from a catch |
| `since` | | The Java release the rewrite needs: `11`. In a class file for an older one its mutants are skipped as `unviable:`, as the method may not be there, and calling one that isn't can't be told from a catch |
| `rewrite` | required | What the call becomes: [see below](#rewrites) |
| `headline` | required | A missed mutant's headline, the gap in the tests |
| `help` | required | The test to write |
| `changed` | | The change in words, under the code it marks: `stage removed`, `{name} changed to {to}` |
| `source` | | How a `call` rewrite reads in the source, for its label: `first(Long.MAX_VALUE)` |
| `tier` | | `defaults` (unless it says), `stronger` or `extended` |

`headline` and `help` can have a version per method, `headline.sorted`, used for that method
instead. In all three wordings, `{name}` is the method called, `{to}` what a rename calls instead,
and `{method}` the method the call is in.

[A JSON Schema](https://docs.mutastic.io/schemas/rules/v1.json) describes these fields, for an
editor to check a rules file as you write it: see [Schemas and stability](/reference/schemas/).

### Rewrites

| Rewrite | Does | For example |
|---|---|---|
| `remove` | Drops the call and its arguments, and keeps the object it was called on as the result. Only for a method that returns its own type: a stream stage, a builder step, `String.strip()` | `stream.filter(p).count()` becomes `stream.count()` |
| `rename a->b, c->d` | Calls another method of the same type with the same arguments; each `a->b` is one mutant | `anyMatch->allMatch, anyMatch->noneMatch` |
| `omit last argument` | Calls the same method without its last argument. List the overloads in `descriptors`, each of which must have the shorter one | `parseInt(text, 16)` becomes `parseInt(text)` |
| `unchecked arithmetic` | Makes `addExact`, `subtractExact`, `multiplyExact`, `incrementExact`, `decrementExact`, `negateExact` or `toIntExact` the plain operation, which overflows instead of throwing. A method of another name is skipped as unviable | `Math.addExact(a, b)` becomes `a + b` |
| `keep argument` | What the call was given goes on in its place, and what it was called on is dropped. Only for a call of one argument of the type it returns; any other is skipped as unviable | `opt.orElse(x)` becomes `x` |
| `call name(ARGS) with A, B` | Drops the arguments and calls another method on the same object, which must return the same type. `ARGS` are the method's parameter types as the JVM writes them (`J` for `long`, `Ljava/util/function/Function;`) | `call first(J) with Long.MAX_VALUE` |

A `call` rewrite's arguments are `0`, `0L`, `true`, `false`, `null`, `Integer.MAX_VALUE`,
`Long.MAX_VALUE`, or a static method with no arguments, written in full:
`java.util.function.Function.identity()`.

A rewrite that doesn't fit a call it meets, because the types don't line up, isn't run: the mutant
is skipped as `unviable:`, with the reason, and stays out of the score. A label, the replacement a
mutant shows, is part of its id, so once a rule is in use, change its `rewrite` and `source` only
knowing that its mutants get new ids.

## Java plugins

For an operator a rules file can't describe, write it in Java: implement
[`io.mutastic.api.Mutator`](/reference/api/mutator/),
with the JDK's `java.lang.classfile` API, which mutastic is built on. This one makes every
whole-number constant one more:

```java
package acme;

import io.mutastic.api.Mutant;
import io.mutastic.api.Mutator;
import java.lang.classfile.CodeBuilder;
import java.lang.classfile.Instruction;
import java.lang.classfile.instruction.ConstantInstruction;
import java.util.List;

public class ConstantPlusOne implements Mutator {
  public String id() {
    return "acme/constant-plus-one";
  }

  public String explanation() {
    return "A whole-number constant goes up by one.";
  }

  public boolean onCalls() {
    return false; // every instruction is a site, not only calls
  }

  public List<Change> changes(Site site) {
    return site.instruction() instanceof ConstantInstruction constant
            && constant.constantValue() instanceof Integer
        ? List.of(Change.of("plus one"))
        : List.of();
  }

  public void write(CodeBuilder builder, Instruction instruction, String label) {
    var value = (Integer) ((ConstantInstruction) instruction).constantValue();
    builder.loadConstant(value + 1);
  }

  public Words words(Mutant mutant) {
    return new Words(
        "constant plus one",
        "no test tells the constant in " + mutant.methodName() + "() from one more",
        "test at the constant itself, and assert the result");
  }
}
```

- **`changes`** is asked about each instruction, with the method and its code around it
  (`site.code()`, `site.index()`), and gives a label for each change it makes there, if any, and
  why one shouldn't run (`equivalent: …`), if it shouldn't.
- **`write`** puts the changed instruction in its place. Afterwards the stack must hold what the
  original left; a change that doesn't verify is skipped as `unviable:`, never run.
- **`words`** is what a missed mutant's card says: the change, the headline and the test to write.
  For a change to a call, give it the call as the source would be written with the change made,
  on the call's parts, and the card shows the line as the mutant has it: `{receiver}.allMatch({args})`,
  `{receiver}` for a call left out, `{arg1} + {arg2}`. Without one, the card says the change in
  words beside the line. A rules file's rewrites do this for you.
- **`onCalls`** says which sites the operator counts: calls, as mutastic's call operators count
  them, or every instruction in the method. **`tier`** defaults to `defaults`; return
  `Tier.STRONGER` or `Tier.EXTENDED` to leave an operator out unless asked for.

Build it against `io.mutastic:mutastic-api` (`compileOnly`, or Maven's `provided`: mutastic brings
it), on JDK 25, and name the class in the jar's
`META-INF/services/io.mutastic.api.Mutator`:

```text
acme.ConstantPlusOne
```

Labels are part of mutant ids, as a rules file's are: keep them once the operator is in use.

## Changing a class as a whole

A `Mutator` changes one instruction. For a change no instruction holds, as an annotation is, or a
method written anew, implement [`io.mutastic.api.ClassMutator`](/reference/api/classmutator/), named in
`META-INF/services/io.mutastic.api.ClassMutator`. This one takes `@Deprecated` off a class:

```java
package acme;

import io.mutastic.api.ClassMutator;
import io.mutastic.api.Mutant;
import io.mutastic.api.Mutator;
import java.lang.classfile.Attributes;
import java.lang.classfile.ClassFile;
import java.lang.classfile.ClassModel;
import java.lang.classfile.ClassTransform;
import java.lang.classfile.attribute.RuntimeVisibleAnnotationsAttribute;
import java.util.List;

public class Undeprecate implements ClassMutator {
  public String id() {
    return "acme/undeprecate";
  }

  public String explanation() {
    return "A class is no longer marked deprecated.";
  }

  public List<Change> changes(ClassModel owner) {
    var deprecated =
        owner.findAttribute(Attributes.runtimeVisibleAnnotations()).stream()
            .flatMap(attribute -> attribute.annotations().stream())
            .anyMatch(annotation -> annotation.className().equalsString("Ljava/lang/Deprecated;"));
    return deprecated
        ? List.of(Change.of(Member.ofClass(), "not deprecated", "@Deprecated", "@Deprecated"))
        : List.of();
  }

  public byte[] write(ClassModel owner, Member member, String label) {
    return ClassFile.of()
        .transformClass(
            owner,
            ClassTransform.dropping(RuntimeVisibleAnnotationsAttribute.class::isInstance));
  }

  public Mutator.Words words(Mutant mutant) {
    return new Mutator.Words(
        "@Deprecated removed",
        "no test needs " + mutant.className() + " to be deprecated",
        "assert what's deprecated, and that callers are told");
  }
}
```

- **`changes`** is asked about each class, and gives each change's **member** (the class, a field or a
  method: what its id stands on), its label, what's there now, and the text that marks its line in the
  source, which is how a card finds a line class files don't have.
- **`write`** gives the whole class back, changed. As with a `Mutator`, one that doesn't verify is
  skipped as `unviable:`.
- **`reach`** says which tests a mutant runs against. By default, `EVERY_TEST`: those that reach the
  class first, until one fails, for what's read by reflection, where the test that matters may run none
  of its lines. `METHOD` runs the tests that reach a line of the mutant's method.
- **`prepare`** hears of the project before its classes, for what a class file doesn't hold: its
  classpath, or its sources.
- **`tier`** defaults to `extended`, not `defaults`, as these cost more.

Each mutant runs with every class loaded anew, since what reads an annotation may have kept what it
read, and a class written anew may have methods the build's doesn't. Where a framework loads the app
itself (`@QuarkusTest`) that can't be done, and they're skipped as `unviable:`.

## Filters

A jar can also hold filters, which decide that a method's mutants shouldn't run:
[`io.mutastic.api.Filter`](/reference/api/filter/),
named in `META-INF/services/io.mutastic.api.Filter`. Unlike operators, a plugin's filters run only
when `filters:` in `mutastic.yaml` names them: see [Configuration and
skipping](/guides/configuration/).
