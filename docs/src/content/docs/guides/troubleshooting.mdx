---
title: Troubleshooting
description: What mutastic's exit status means, and what to do about each.
---

mutastic says what went wrong, then exits with a status that says what kind of thing it was. The
build plugins fail the build on any status but 0.

## 1: the score is below the threshold

For `run`, the score didn't reach the threshold. Each missed mutant in the output says what to test
and how to prove it; start with the ones on lines you changed. If the threshold is wrong for this
module, set it, for example `--threshold=70`.

For `verify`, the mutant is still missed: no test fails with it in. The card for that mutant shows
the inputs your tests used and a test that would catch it.

## 2: a usage error, or a build mutastic couldn't read

The message says which. For an option, check `mutastic --help`: a value follows `=` or a space,
except `--since`, which needs `=` (`--since=main`). For a build, mutastic must be run in, or
pointed at, a Gradle or Maven build's directory, and a module named as the build names it: `:app`
for Gradle, a directory as `-pl` takes it for Maven. A mutant's id belongs to the project its run
was on, so run the command the run printed.

## 3: the tests fail without any mutant

mutastic runs your tests once before it changes anything. They have to pass first, as a mutant is
only caught when a test that passed fails. Run the build's own tests and fix what fails. A test
that passes when run again is reported as flaky, and doesn't stop a run.

Tests run with a temporary directory of their own, deleted when their worker ends. A test that
counts on finding something already in `java.io.tmpdir`, such as a file it shares with another
process or a download cached between runs, won't find it there: name a directory in the test
task's JVM arguments (`-Djava.io.tmpdir=...`), and mutastic uses that instead.

A process a test starts and leaves running ends with its worker too. One that has detached itself,
as a Gradle daemon or a container under Docker's own daemon has, is left alone.

### A test that caught mutants fails on the unmutated code

Once the mutants have run, each test that caught one runs again on the code as it is, on its own,
in a new worker. One that fails there is named as flaky, as a test that `passes among the others
but fails on its own`: its catches don't count, the mutants it reached ran again without it, and
the run exits with 3, whatever the score. See [When a catch isn't the mutant's](/concepts/results/#when-a-catch-isnt-the-mutants).

The test passed when the whole suite ran, so it most likely depends on something it doesn't set up
itself:

- **Another test's set-up.** It reads a static, a system property or a singleton another test
  fills in, and only passes when that test runs first. Run it on its own in your IDE: it fails
  there too. Make it set up what it needs.
- **Something left behind.** It expects a file, a directory or a database to be empty, and an
  earlier test, or an earlier run of itself, left something there. Clean up after the test that
  writes it, or give each test a place of its own (JUnit's `@TempDir`).

Fix the test rather than what it checks: loosening the assertion makes its catches count again
without making them true. If a test class can't be made to run on its own yet, leave it out with
[`--exclude-tests`](/reference/run/#exclude-tests): the run then passes or fails on the other
tests, and the lines only it reached count as not covered. There's no switch to count its catches
anyway: they're known to be false.

## 4: mutastic itself went wrong

That's a bug in mutastic. Please [open an issue](https://github.com/mutastic/mutastic/issues) with
the command, the message, and the worker log from the module's work directory
(`build/mutastic/worker.log` or `target/mutastic/worker.log`).
