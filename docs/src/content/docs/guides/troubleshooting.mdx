When a run doesn't pass, what to do depends on why: a gap in the tests is closed with a test, a
command typed wrong is typed again, and a failing test is fixed before mutastic can say anything.
So mutastic says what went wrong, then exits with a status that says what kind of thing it was, and
a script or a CI step can tell them apart. The build plugins fail the build on any status but 0.
Each section below starts from what you see, on mutastic's samples, then says what to do.

## 1: the score is below the threshold

On the pricing sample, with the threshold set above its score:

```sh
mutastic run samples/pricing --format=concise --threshold=95
```

<Code code={below} lang="ansi" />

For `run`, the score didn't reach the threshold. Each missed mutant in the output says what to test
and how to prove it; start with the ones on lines you changed. If the threshold is wrong for this
module, set it, for example `--threshold=70`.

For `verify`, the mutant is still missed: no test fails with it in. The card for that mutant shows
the inputs your tests used and a test that would catch it.

## 2: a usage error, or a build mutastic couldn't read

The message says which. Here, a mutant's id from the `configured` sample, given to the pricing
sample:

```sh
mutastic verify m6393711d samples/pricing
```

<Code code={elsewhere} lang="ansi" />

A mutant's id belongs to the project its run was on, so run the command the run printed. For an
option, check `mutastic <command> --help`: a value follows `=` or a space, except `--since`, which
needs `=` (`--since=main`). When what you typed is close to a name mutastic has, it says so and gives
your command with that one word changed, to run if it's what you meant:

```
mutastic: run has no option --formt. There's one called --format.
  mutastic run --format=agent
```

mutastic never runs the close name in place of yours. A mistake in `mutastic.yaml`, a rules file or
`.mutastic/ignores.yaml` names the file and the line.

When the project doesn't build, mutastic quotes the compiler's first errors at your files' lines, or
what the build tool says went wrong, and ends in the build's command that builds it as mutastic did:
run it to see the whole output. A file mutastic can't read or write, such as a build directory
that's read-only, a file where it keeps a directory, or a full disk, is named with the system's
reason.

For a build, mutastic must be run in, or pointed at, a Gradle or Maven build's directory, and a
module named as the build names it: `:app` for Gradle, a directory as `-pl` takes it for Maven.

### A build of modules

mutastic tests one module at a time. Run at the top of a build whose Java code is all in its
modules, it names the modules that have some, as the commands that test them. On the Maven sample
of two modules:

```sh
mutastic run samples/maven-modules
```

<Code code={moduleRoot} lang="ansi" />

A module the build hasn't got gets the same list, and leaves nothing behind for it:

```sh
mutastic run samples/maven-modules :nope
```

<Code code={moduleMissing} lang="ansi" />

When the name is close to a module's, `:cor` for `:core`, mutastic says `There's one called :core.`
and gives that module's command. It never runs it in place of the one you named. Gradle builds say
the same.

Run in a directory inside a build, such as its `src`, mutastic runs the build it's in. In a Maven
module it runs the module from the top of its build, which builds the modules it uses, as
`mutastic run ../.. :app` would. In a build of modules but in none of them, it names the modules,
as at the build's root.

### The tests pass, but coverage recorded nothing

On the pricing sample, with its tests replaced by one that never calls the code:

<Code code={nothingCovered} lang="ansi" />

mutastic runs your tests once with every class that has a mutant instrumented, to find which tests
reach which lines. When tests ran and passed but not one line of those classes was recorded, that
pass measured nothing, and a score would read every mutant as one no test reaches: a 0% that says
your tests miss the code when it's mutastic that didn't see them. So the run stops instead. The
usual causes:

- **Another agent in the tests' JVM arguments.** A coverage tool's agent rewrites classes as they
  load. mutastic leaves out JaCoCo's agent itself; the message names any `-javaagent:` it left in.
  Take it out of the test task's JVM arguments for mutastic's run.
- **A framework that loads the code in a class loader of its own,** such as Quarkus's for
  `@QuarkusTest`. mutastic reaches Quarkus's copies of the classes through its own agent, but not
  when another agent has rewritten them first: with JaCoCo's in the JVM, a Quarkus project's run
  once found no test reached anything.
- **Tests that reach none of the code.** The build's test filters left in only tests that never
  call it.

A run of only some mutants (`--only`, `--since`, `--shard`), or one that leaves tests out with
`--exclude-tests`, isn't stopped: there the tests that run may well reach none of the classes, and
those mutants are reported as not covered. With no tests at all, a
module's mutants are not covered too.

## 3: the tests fail without any mutant

On the pricing sample, with one of its tests changed to expect 24 where the code gives 25:

<Code code={testsFail} lang="ansi" />

mutastic runs your tests once before it changes anything. They have to pass first, as a mutant is
only caught when a test that passed fails. The message names the test and what it said, and ends in
the build's own command that runs it alone (`./gradlew test --tests '…'`, or `mvn test -Dtest='…'`):
run it, and fix what fails. A test that passes when run again is reported as flaky, and doesn't stop
a run.

A test that ends the tests' JVM, with `System.exit` or a crash, stops the run the same way, and the
message names the test that was running. So does a coverage pass that runs past its 10 minutes:
a test is waiting for something that never comes.

When the message names a class "as a whole", its tests never got to fail: what the class runs
around them did, in a `@BeforeAll`, `@AfterAll`, `@BeforeClass`, a class rule or a static
initialiser. The exception it failed with, and its output, are in the log the message names. A
class whose setup passes when run again is left out as flaky instead, with all its tests.

Tests run with a temporary directory of their own, deleted when their worker ends. A test that
counts on finding something already in `java.io.tmpdir`, such as a file it shares with another
process or a download cached between runs, won't find it there: name a directory in the test
task's JVM arguments (`-Djava.io.tmpdir=...`), and mutastic uses that instead.

A process a test starts and leaves running ends with its worker too. One that has detached itself,
as a Gradle daemon or a container under Docker's own daemon has, is left alone.

### A test that caught mutants fails on the unmutated code

Once the mutants have run, each test that caught one runs again on the code as it is, on its own,
in a new worker. One that fails there is named as flaky, as a test that `passes among the others
but fails on its own`: its catches don't count, the mutants it reached ran again without it, and
the run exits with 3, whatever the score. See [When a catch isn't the mutant's](/concepts/results/#when-a-catch-isnt-the-mutants).

The test passed when the whole suite ran, so it most likely depends on something it doesn't set up
itself:

- **Another test's set-up.** It reads a static, a system property or a singleton another test
  fills in, and only passes when that test runs first. Run it on its own in your IDE: it fails
  there too. Make it set up what it needs.
- **Something left behind.** It expects a file, a directory or a database to be empty, and an
  earlier test, or an earlier run of itself, left something there. Clean up after the test that
  writes it, or give each test a place of its own (JUnit's `@TempDir`).

Fix the test rather than what it checks: loosening the assertion makes its catches count again
without making them true. If a test class can't be made to run on its own yet, leave it out with
[`--exclude-tests`](/reference/run/#exclude-tests): the run then passes or fails on the other
tests, and the lines only it reached count as not covered. There's no switch to count its catches
anyway: they're known to be false.

## 4: mutastic itself went wrong

That's a bug in mutastic: what your tests, your build or the disk do exits with 2 or 3. Please [open
an issue](https://github.com/mutastic/mutastic/issues) with the command, the message, and the worker
log from the module's work directory (`build/mutastic/worker.log` or `target/mutastic/worker.log`).

## `+` and `x` where `✓` and `✗` should be

A Windows console on its legacy code page has no `✓`, `✗`, `○` or `…`, so mutastic writes `+`,
`x`, `o` and `...` in their place, rather than the `?` Java would. Windows Terminal and the console
show the real ones once the console is in UTF-8: run `chcp 65001` first, or turn on Windows'
*Beta: Use Unicode UTF-8 for worldwide language support*. Output to a pipe or a file is UTF-8
whatever the console's code page.
