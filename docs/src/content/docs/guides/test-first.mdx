One cycle, on the pricing sample, with every command and what it prints: a test from the spec,
the least code that passes it, mutastic on the cycle's lines, the tests its cards ask for, and a
commit. [Working test-first](/concepts/test-first/) says why mutastic comes where it does, and
[why tests written first still need checking](/concepts/test-first/#why-tests-written-first-still-need-checking).

<RustAwaiting>
This guide's Rust cycle comes with mutastic for Rust's next release. Until then, these are the Java
edition's steps: on a crate they're the same, with `mutastic run` and `mutastic verify` as
[the quickstart](/rust/getting-started/) runs them.
</RustAwaiting>

The spec for this cycle: loyal customers get 5 off orders of 30 or more.

## Before you start

Start from a clean tree, and commit at the end of each cycle, not before: `--since=HEAD` runs the
mutants on the lines changed since the last commit, so the commit marks where the cycle started.

## Make it pass with the least code

<EditionTabs>
<div slot="java">

{/* changed in: samples/pricing/src/main/java/com/example/pricing/Pricing.java */}
```java
/// 5 off orders of 30 or more, for loyal customers.
public int loyaltyCredit(int total) {
  if (total >= 30) {
    return 5;
  }
  return 0;
}
```

</div>
<div slot="rust">

```rust
/// 5 off orders of 30 or more, for loyal customers.
pub fn loyalty_credit(&self, total: u32) -> u32 {

        return 5;
```

</div>
</EditionTabs>

The one test is at 50, so nothing checks the edge at 30, nothing checks an order below it, and no
test reaches the code for an order below 30 at all: the code ran ahead of its tests. The card
suggests a test for each.

## Write the card's tests

Check each value against the spec before you keep it: an order of exactly 30 gets 5 off, and one of
29 gets nothing. Here both are what the spec asks for. Had one not been, the test would keep the
spec's value and fail on today's code: that's a bug found, and the cycle goes back to green.

<EditionTabs>
<div slot="java">

{/* added to: samples/pricing/src/test/java/com/example/pricing/PricingTest.java */}
```java
@Test
void loyaltyCreditAtTheTotalEdge() {
  assertEquals(5, new Pricing().loyaltyCredit(30));
}

@Test
void loyaltyCreditJustBelowTheTotalEdge() {
  assertEquals(0, new Pricing().loyaltyCredit(29));
}
```

</div>
<div slot="rust">

```rust
#[test]
fn loyalty_credit_at_the_total_edge() {
    assert_eq!(Pricing::new().loyalty_credit(30), 5);
}

#[test]
fn loyalty_credit_just_below_the_total_edge() {
    assert_eq!(Pricing::new().loyalty_credit(29), 0);
}
```

</div>
</EditionTabs>

## A mutant you can't catch

A mutant no test could catch, because its case can't happen or no caller can see the change, is
proposed for a person to ignore, with its reason (see [Equivalent mutants](/concepts/equivalence/)).
Don't change the code so the mutant can't exist: that hides what it found.

## Refactor, run again, commit

Change the structure if it needs it, with the suite green, and run the cycle again. This cycle's
code is one `if`, with nothing to refactor, so here the run only confirms the cycle:
[Test-first with a refactor](/guides/test-first-refactor/) carries on to a refactor the code does
need.

## One card at a time

<EditionOnly edition="java">

`mutastic next --since=HEAD` gives the cycle's missed mutants one at a time, the one most worth a
test first, in place of the whole run: see [Working through misses](/concepts/next/). It leaves out
the lines no test reaches, which `run` lists under `Not covered`.

## Agents

A coding agent runs the same cycle through the [agent format](/concepts/output/#formats) and
[the gate](/agents/gate/), whose one rule for it is the agent format's `rules:` line: add or change
tests only, and never change production code to make a mutant go away.
