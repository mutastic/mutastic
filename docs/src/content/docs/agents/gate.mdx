`mutastic gate` holds an agent's "done" to what mutastic says of the lines it changed. A plugin runs
it from the agent's hooks ([Claude Code](/agents/claude-code/), [Codex](/agents/codex/)); anything else can run the same
three commands.

```sh
mutastic gate open     # the task starts here
mutastic gate check    # is it done?
mutastic gate close    # forget the task
```

## Where a task starts

`gate open` keeps where the task starts: the commit, the ignores there are, and how many tests there
are and how many are turned off. An agent that can't make a test pass can delete it, or turn it
off, and the tests would then pass. Comparing the counts at the end catches that. `gate open` also
tells the agent how to check its own work as it goes:
`mutastic run --since=<that commit> --format=agent`. Uncommitted changes count as the task's, so
start from a clean tree to gate only what the agent does.

### Tests over a table of cases

Many tests run the same check over a table of cases, a row each. Taking a row away loses a case as
surely as deleting a test does, so the gate counts each row as a test.

In JUnit, such a test is a parameterized test, `@ParameterizedTest`, with a source of rows. Rows a
static source holds are counted from its annotations: a `@CsvSource`'s entries and `textBlock`
lines, a `@ValueSource`'s values, an `@EnumSource`'s names, a `@CsvFileSource`'s lines. What only
running says (rows a `@MethodSource`, `@ArgumentsSource` or `@FieldSource` makes, a test a
condition such as `@DisabledOnOs` turns off, a case an assumption aborts) is counted by a run of the
tests that `gate open` starts in the background, on a copy of the tree as it is then, so the agent
needn't wait.

Each rstest `#[case]`, test-case row and `#[values]` cell is a test of its own, as the test
binaries list them with `--list`, and a test turned off is one marked `#[ignore]`. `gate open`
lists them in the background, on a copy of the tree as it is then, so the agent needn't wait, and a
check waits for the list. Where the list failed, as for a package that doesn't build when the task
starts, or isn't done in four minutes, the gate counts the test functions in `src` and `tests`
instead, and a pass says so. A loop over rows inside one `#[test]` is one test, however many rows
it has.

## When it's done

`gate check` runs the tests, and mutastic on the lines changed since the task started, committed
or not. It runs the tests even when no mutant is on those lines: a constant, an import or a log
line can break a test too. Since only the mutants on those lines run, a stronger operator set in
`mutastic.yaml` stays cheap in an agent's loop: see
[Choosing operators](/concepts/operators/#choosing-operators). The task is done when:

- **each mutant on those lines is caught, or proposed** for a person to ignore. A proposed mutant
  still counts as missed in the score, but it doesn't hold the gate: deciding it is yours. With a
  [baseline](/concepts/next/#a-baseline-for-older-misses), a mutant missed before the task is the
  project's backlog, not the task's, and doesn't hold it either, though the task can't add to the
  baseline itself;
- **the task added no ignore of its own.** Ignoring a mutant is a person's call: the agent
  proposes, with `mutastic ignore ID --propose`, and you accept between turns. As a hook, a check
  that lets the agent stop notes the ignores, and your next prompt takes in those added since, so
  an ignore you accept after the agent stops doesn't hold the task. One added while the agent has
  the turn, with `ignore --accept` or by editing `.mutastic/ignores.yaml`, does, after your next
  prompt too;
- **no test was taken away**: there are no fewer tests than when the task started, and no more
  turned off, each row of a table of cases counted as a test. The check counts them again and
  compares them with the count `gate open` started: fewer cases run, or more skipped, holds the
  task. If that count couldn't finish (the tests failed at the start, or it was stopped), the check
  says so when it passes, and counts from the source instead. A test the task left out under
  [`exclude-tests:`](/guides/configuration/#leaving-a-test-out) in `mutastic.yaml` is a test taken
  away too: leaving one out is your call, so the agent finds out whether the change or the test is
  wrong, then tells you, or proposes leaving it out with its reason;
- **the tests pass.** When a test that was there when the task started fails, the gate says so,
  and tells the agent to find out whether the change or the test is wrong, and to ask you if it
  isn't sure, rather than rewrite what the test expects. Every mutant is caught by a test made to
  fit a wrong change, so the score can't tell you. For the same reason, when the gate passes or
  hands over, it names the test files there when the task started that the task took an assertion
  out of, for you to check. When a test the task added fails, the gate tells the agent to make it
  pass, unless the spec or plan is what's wrong, in which case it's to say so and stop, and either
  way to leave the failing test in place;
- **no test that failed at an earlier check is gone.** The gate remembers each test that failed
  at a check, for the rest of the task. Deleting the test would otherwise pass a task the test
  said was wrong. A test that moved to another class keeps its name, and one that was renamed
  keeps its body, so either still counts; a test changed in both at once can't be told from one
  taken away, so the gate names it and holds the task.

These hold whatever lines the task changed. A task that changes no lines mutastic mutates (docs,
build files, tests only) is still held when it took a test away, or ignored a mutant or added one
to the baseline itself: an agent that only deletes the failing test isn't done. Otherwise it passes
once the tests do, and one that changed nothing passes at once.
Mutants on lines the task didn't touch aren't its business: they were missed before it started.

When it isn't done, `gate check` says why, as [the agent format](/concepts/output/#formats)
does: a card for each missed mutant, with the test to write and its `done when` command. As a hook,
that's the agent's next instruction. Exit codes follow `run`'s: 0 when it passes, 1 when it
doesn't.

## Which operators

The gate runs the operators a run would: `operators:` in `mutastic.yaml`, or the defaults. To hold
an agent's tasks to more than your everyday runs, gate them on the stronger set. Give the gate its
own set in `mutastic.yaml`, and the plugins' hooks pick it up with nothing else to change:

```yaml
gate:
  operators:
    - stronger
```

`gate open --operators=stronger` does the same for one task, in place of both. The set is chosen
when the gate opens and kept with the task: every check runs it, a check given another set is
refused rather than run on fewer operators than the task opened with, and a change to
`mutastic.yaml` waits for the next task (`gate close`, then `gate open`; with a hook, the next
session). The open names the set, and the `mutastic run` it gives the agent carries `--operators`
when the set isn't what a run would choose; each verdict on the mutants names it too:
`(operators: stronger)`.

A task can pass on the defaults and be held on stronger: in `samples/checkout`, a test that buys
one item catches `quantity * price` becoming `quantity / price`, but not becoming `price`.

## When it hands over

An agent can't always get there, and sometimes shouldn't: you asked for the change without tests,
or a test needs something only you know. So a hook's `gate check` lets the agent stop, and tells
you what's still missed:

- **when the agent changed nothing** since the gate last sent it back: it has declined, and
  sending it back again only spends its turns;
- **after a few tries** in a row (`--tries`) that didn't get there.

The count starts again when a check passes. "Nothing changed" is the working tree as git sees it,
so a project whose build output git doesn't ignore always looks changed, and gets only the tries.

## Within the hook's time

The plugins run `gate check` from a Stop hook that's stopped after ten minutes, and a check that's
stopped gates nothing. So as a hook, a check keeps within a budget, `MUTASTIC_GATE_BUDGET` seconds
(600 unless set, what the hook allows):

- **it waits for the count `gate open` started** only as long as the budget has left once its own
  run is done, and never longer than `MUTASTIC_GATE_COUNT_WAIT` seconds (240 unless set). A count
  that isn't done by then is left, and a pass says the check compared the annotations only;
- **it hands over before it runs** when the last check's own run took longer than the whole
  budget: "this project's gate check takes longer than the hook allows", so run
  `mutastic gate check` yourself. Your own check has no budget, and once it's quicker than the
  budget, the hook checks again.

An agent whose hook allows more or less time (opencode sets none) can set `MUTASTIC_GATE_BUDGET`
to match.

## As a hook

With `--hook=claude`, `open` and `check` read the hook's input on stdin and answer as Claude Code's
hooks do: `open` once per session (a later prompt only takes in the ignores made between turns), and `check` with a block, whose reason is the cards, or a
message for you. Codex's hooks take the same input and answers, so its plugin runs the same
commands. A hook runs in whatever project the agent is in, so where mutastic reads no build,
`open` and `check` with `--hook` say nothing and let the agent go on. Other agents' hooks can call
the commands without `--hook` and act on the exit code and the text: see
[other agents](/agents/other-agents/).

For an agent working test-first, what it sees at each step and what the gate can't check, such as
whether a test came first, are in [Working test-first: with an agent](/guides/test-first-agent/).

The flags each command takes are in the reference: [`gate open`](/reference/gate-open/),
[`gate check`](/reference/gate-check/) and [`gate close`](/reference/gate-close/).
