An operator is a kind of change. Each mutant is one operator applied at one place in your code.
Reports and rules name an operator by its id, `mutastic/boundary` say.

Each operator has its place on a family's page: what it changes, the bug it stands for, a real
example with the card mutastic prints for it, and the test that catches it.

- [Conditions](/concepts/operators/conditions/): comparisons, conditions, and how two combine.
- [Arithmetic](/concepts/operators/arithmetic/): operators, numbers and bits.
- [Returns and errors](/concepts/operators/returns/): what a method returns, and what it throws.
- [Calls and writes](/concepts/operators/calls/): calls, assignments and field writes left out.
- [Arguments](/concepts/operators/arguments/): what a call is given, and what a method gets.
- [Library methods](/concepts/operators/library/): a JDK method for its counterpart, and the text in
  your code.
- [Streams](/concepts/operators/streams/): stream stages and matches.
- [Optional](/concepts/operators/optional/): how an `Optional` is made, checked and unwrapped.
- [Control flow](/concepts/operators/control/): `switch` arms and caught exceptions.

## The Rust edition

The Rust edition uses these ids wherever the meaning is the same, so a rule, a script or an agent
that names `mutastic/boundary` means one thing in both. Six have no Rust equivalent, for want of the
language feature they change: `mutastic/flip-increment` (Rust has no `++`, and `+=` and `-=` are
math's), `library/omit-argument` (no overloading), the three `predicate/*` ids (std has no `Predicate`
combinators) and `mutastic/drop-catch-type` (no multi-catch). The Rust edition adds a few of its own,
each in the family it fits: `mutastic/unwrap-try` in returns and errors,
`mutastic/remove-struct-field` in calls and writes, `mutastic/default-parameter` in arguments,
`library/reverse-ordering` and `bigdecimal/remove-step` in library methods, and `mutastic/swap-break`
in control flow.

Some ids sit in another set there: the four `optional/*` ids above and `remove-switch-arm` are in
`stronger`, since `Option`, `Result` and `match` are everyday Rust rather than modern APIs; and
`drop-vararg` is in `extended`, as an array's length is part of its type there.

## Choosing operators

A run uses the `defaults` set: every operator above but those in `stronger` and `extended`. To
choose, give a list of sets, operator ids and namespaces, any with a `-` in front to leave it out:

| Choice | Runs |
|---|---|
| `defaults` | What runs unless told otherwise |
| `stronger` | The defaults and the operators in `stronger` |
| `extended` | The operators on modern APIs alone: add it to another set |
| `defaults,extended` | The defaults and the operators in `extended` |
| `all` | Every operator, in every set |
| `mutastic/arithmetic-replacement` | That one operator |
| `stream` | Every operator in that namespace: `stream/remove-stage`, `stream/swap-match` |
| `-stream` | The defaults without the stream operators |
| `defaults,mutastic/arithmetic-replacement` | The defaults and that one |

On the command line, or from a build plugin, as [`--operators`](/reference/run/#operators):

```sh
mutastic run --operators=stronger
mutastic run --operators=defaults,-stream/swap-match
```

Or for every run, in `mutastic.yaml`, which a command-line choice replaces:

```yaml
operators:
  - stronger
  - -stream/swap-match
```

A run of one mutant, by id (`verify`, `explain`, `run --only`), looks among every operator, so a
mutant any run found can always be checked again.

To see what a choice adds before a run pays for it, [`mutastic mutants`](/reference/mutants/) lists
the mutants it makes, a line each, and runs no test:

```sh
mutastic mutants --operators=stronger
```

A mutant's id doesn't depend on which operators run: choosing more adds mutants, and never changes
the ids of the others.

A score does: it's a share of the mutants a set makes, so scores compare only within a set. A run
is compared with the last one that used the same operators.

## When a miss is fine

Not every missed mutant is a gap worth closing. mutastic already skips the changes that would tell
you nothing, such as calls that only log and trivial getters: see
[Skipped mutants](/concepts/results/#skipped-mutants). What's left can still include changes no one
could see:

- **A boundary nobody can reach.** If `count` can never be exactly `limit`, `<` and `<=` behave the
  same.
- **A call whose effect is checked elsewhere, or not at all on purpose,** such as warming a cache
  that only makes things faster.
- **A result the code always overwrites,** or a check made twice where the second never decides
  anything.

For those, record the decision rather than writing a test that pins nothing. It goes in
`.mutastic/ignores.yaml`, to commit and review, and lapses when the line changes:

```sh
mutastic ignore m855c8e3c --reason="count never reaches limit"
```

For a whole class or method that isn't worth testing, generated code say, a rule in `mutastic.yaml`
skips it: see [Configuration and skipping](/guides/configuration/).
