[Operators](/concepts/operators/) says what each operator changes. This page says why a test that
catches it is worth having. Each mutant stands for a bug someone could really write, and a
missed mutant means that bug would get through: the tests pass whichever way the line is written.

For each operator below: the bug it stands for, where missing it costs, the test that catches
it, and when a miss is fine to [ignore](#when-a-miss-is-fine).

## Boundary

**The bug it stands for:** the off-by-one. `>=` and `>` read almost the same, and code reviews
rarely stop on them, so the wrong one gets written and the wrong one gets through.

**Where it costs:** every rule with a limit. Free shipping from 100, a discount from 10 items, a
login locked after 3 failures, a plan's 5-seat limit, a page of 20 results, the last day a refund
is allowed. Customers are at the edge all the time: someone who spends exactly 100 because the site
said "free shipping from 100" is the case the rule exists for.

```java
if (total >= 100)   // becomes: if (total > 100)
  shipping = 0;
```

**The test that catches it:** one at the edge. Tests with totals of 50 and 250 pass either way;
only 100 tells `>=` from `>`. mutastic's [inputs seen](/concepts/suggested-tests/) shows which values
the tests tried, so the missing edge is easy to spot.

```java
@Test
void shippingIsFreeFromExactly100() {
  assertEquals(0, new Checkout().shipping(100));   // free from 100, so nothing to pay
}
```

A boundary miss is a question for whoever owns the rule as much as for the tests: should 100 get
free shipping? The test records the answer.

## Comparison

**The bug it stands for:** a comparison that's right at the edge and wrong past it: `==` where
`>=` was meant, so the rule holds for exactly 100 and stops at 101.

**Where it costs:** the same rules as a boundary, on the side tests skip. Tests often try a value
below the limit and one exactly at it, and never one well past it.

```java
if (total >= 100)   // becomes: if (total == 100)
  shipping = 0;
```

**The test that catches it:** one on the side where the two disagree, which the card names: here
a total above 100.

```java
@Test
void shippingStaysFreeAbove100() {
  assertEquals(0, new Checkout().shipping(250));
}
```

## Other comparison

**The bug it stands for:** a condition the wrong way round: a missing `!`, `==` for `!=`, a null
check that guards the wrong case.

**Where it costs:** where code decides which way to go: whether an order is paid before it ships,
whether a user may see a page, whether to retry, whether a value is missing. Getting it backwards
usually means doing the wrong thing in exactly the case that matters: shipping unpaid orders, or
refusing paid ones.

```java
if (order.isPaid())   // becomes: if (!order.isPaid())
  warehouse.ship(order);
```

**The test that catches it:** one for each side of the `if`. A miss here usually means the tests
only ever took one path, the happy one, and nothing checks what happens on the other.

```java
@Test
void unpaidOrdersDontShip() {
  var warehouse = new Warehouse();
  var checkout = new Checkout(warehouse);
  var order = Order.unpaid();
  checkout.complete(order);
  assertThat(warehouse.shipped()).doesNotContain(order);
}
```

Security checks deserve this most. A permission check whose negation no test notices is one
nobody has proved refuses anyone.

## Remove conditional

**The bug it stands for:** a check that doesn't matter as much as its author thought, or that's
the wrong check entirely. Forcing a condition always true or always false asks whether any test
depends on it deciding.

**Where it costs:** guards. A permission check, a validation, a "only if it's changed" before a
write, a retry that should stop. If the code behaves the same with the guard always passing, no
test has ever been refused by it; if it behaves the same with the guard never passing, no test has
ever needed it to let something through.

```java
if (user.canEdit(document))   // becomes: if (true)
  document.save(changes);
```

**The test that catches it:** one for each answer the condition can give. Other comparison asks
the same question from a different angle; remove conditional is clearer about which answer no test
has tried, and catches the case where the condition is checked twice and one check never decides.

```java
@Test
void aReaderCantSave() {
  var document = new Document();
  var reader = User.withRole(Role.READER);
  assertThrows(AccessDenied.class, () -> editor(reader).save(document, "changes"));
}
```

## Logical connector

**The bug it stands for:** `&&` where `||` was meant, or the other way round: a rule that needs
both conditions written as either, a discount for members *or* big orders written as *and*.

**Where it costs:** eligibility and permission rules, validation that should reject on any of
several problems, retries that stop on either of two signals. Tests that set both conditions
true, or both false, pass either way.

```java
if (member || total >= 100)   // becomes: if (member && total >= 100)
  discount = 10;
```

**The test that catches it:** one where the two conditions disagree: a member with a small
order, or a big order from someone who isn't one.

```java
@Test
void membersGetTheDiscountOnSmallOrders() {
  assertEquals(10, new Pricing().discount(true, 20));
}
```

## Math

**The bug it stands for:** the wrong operator in a calculation: `-` for `+`, `/` for `*`.

**Where it costs:** money, quantities and time: prices, tax, totals, stock levels, durations. A
wrong calculation is often silent: nothing crashes, the number is just wrong, and it's found later
on an invoice or in a report, by a customer.

```java
return price * quantity;   // becomes: return price / quantity;
```

**The test that catches it:** one whose values tell the operators apart. Tests often use values
where they don't: a quantity of `1` gives the same answer for `*` and `/`, and adding `0` the same
for `+` and `-`. Those are exactly the values a quick test tends to pick.

```java
@Test
void totalIsPriceTimesQuantity() {
  assertEquals(1500, new LineItem(500, 3).total());   // 500 × 3; with / it would be 166
}
```

## Arithmetic replacement

**The bug it stands for:** an operation mixed up with another one entirely: adding where it should
multiply, a total that should be a product. It's in the `stronger` set because the values that
let it through are rarer than math's, so it finds less, but what it finds is a test that checks
almost nothing.

**Where it costs:** the same places as math: prices, quantities, scores. Its real value is as a
check on the tests' values: `2 + 2 == 2 * 2`, `0 + 0 == 0 * 0` and `1 + 0` against `1 * 0` are the
numbers quick tests pick.

```java
return price + shipping;   // becomes: return price * shipping;
```

**The test that catches it:** one with ordinary values, where the sum and the product are far
apart.

```java
@Test
void totalAddsShipping() {
  assertEquals(1250, new Order(1200, 50).total());   // 1200 + 50; with * it would be 60000
}
```

Run it with `--operators=stronger`.

## Return value

**The bug it stands for:** a method that doesn't return what it worked out. This is less a typo
than a sign: tests that call the method but never look at its answer.

**Where it costs:** everywhere a result is used. If returning the other `boolean`, `0`, an empty
list or `null` instead passes every test, the tests run the method without checking it. Its line
counts as covered, and the coverage report says it's tested when it isn't. The value is the one a
method of that kind most plausibly gets wrong: a check that answers the wrong way, a count of
nothing, a search that finds nothing. That's why a list becomes an empty list rather than `null`:
code that forgot to add the results returns one, and a `null` would fail on its first use, which
any test notices.

```java
boolean isEligible() {
  return orders >= 10;   // becomes: return false; and: return true;
}
```

**The test that catches it:** one that asserts on the result. A computed `boolean` gets both
mutants, so it needs a test where the answer is `true` and one where it's `false`. A number
becomes `0`, caught by a test whose answer isn't `0`; a list becomes empty, caught by a test whose
answer has something in it.

```java
@Test
void loyalCustomersAreEligible() {
  assertTrue(Customer.withOrders(12).isEligible());   // eligible from 10 orders
}
```

A test that calls a method and asserts nothing about what comes back is the commonest gap this
operator finds, and often the easiest to fix.

## Remove void call

**The bug it stands for:** a step left out: a call removed in a refactor, never added, or
skipped on one path.

**Where it costs:** side effects, which are often the point of the code: saving a record,
reserving stock, sending an email, writing an audit entry, releasing a lock, invalidating a cache.
If removing the call passes every test, nothing checks the step happens. That's how an order can
be confirmed without its stock being reserved, or a change made without the audit entry that
compliance relies on.

```java
inventory.reserve(item);   // becomes: nothing, the line is gone
```

**The test that catches it:** one that checks the effect, the stock afterwards or the record
written, rather than only that the method returned.

```java
@Test
void confirmingReservesStock() {
  inventory.restock(item, 5);
  orders.confirm(orderFor(item));   // one of the item
  assertEquals(4, inventory.available(item));   // 5 in stock, 1 reserved
}
```

## Remove discarded call

**The bug it stands for:** the same as a removed void call: a step left out. Many calls that do
something also return something nobody needs: `add` and `remove` on a collection say whether it
changed, `put` returns what was there, a builder's `append` returns the builder.

**Where it costs:** the same side effects, and the ones that hide best, since a call written for
its effect reads like a query. A set that never gets its `add`, a map whose `put` is gone, a
counter that's never incremented.

```java
seen.add(order.id());   // becomes: nothing, the line is gone
```

**The test that catches it:** one that checks the effect: that an order already seen isn't handled
again, not only that the method ran.

```java
@Test
void anOrderIsHandledOnce() {
  var order = Order.numbered(7);
  orders.handle(order);
  orders.handle(order);   // the same order again
  assertEquals(1, orders.handledCount());
}
```

## Stream stage removal

**The bug it stands for:** a stage that's wrong, or in the wrong place, and no test would know: a
filter with the wrong condition, a `distinct()` someone forgot, a `limit` that's off by one, a sort
by the wrong key.

**Where it costs:** streams are where business rules hide in one line: only the paid orders, the
first ten results, each customer once. If removing the stage changes nothing a test checks, the
rule isn't tested at all, however many tests run the line.

```java
return orders.stream().filter(Order::isPaid).toList();   // becomes: orders.stream().toList()
```

**The test that catches it:** one whose input the stage has to change: an unpaid order the filter
must drop, a duplicate for `distinct()`, more elements than the `limit`, input out of order for
`sorted()`.

```java
@Test
void onlyPaidOrdersAreListed() {
  var paid = Order.paid();
  var unpaid = Order.unpaid();
  assertEquals(List.of(paid), orders.paid(List.of(paid, unpaid)));   // the unpaid one is dropped
}
```

A test with only paid orders passes with the filter or without it: that's the gap this operator
finds.

## Stream match swap

**The bug it stands for:** "any" where "all" was meant, or the other way round. They read alike,
and with the inputs tests usually pick, all of them matching or none, they give the same answer.

**Where it costs:** checks over collections: whether any item is out of stock, whether all
approvers have signed, whether none of the lines is negative. Getting it wrong lets an order
through with one bad line, or blocks one with a single good one.

```java
return lines.stream().anyMatch(Line::isBackordered);   // becomes: .allMatch(…), and: .noneMatch(…)
```

**The test that catches it:** one with a mix: some elements that match and some that don't. That's
the only input where `anyMatch` and `allMatch` disagree.

```java
@Test
void oneBackorderedLineDelaysTheOrder() {
  var order = new Order(List.of(Line.inStock(), Line.backordered()));   // one of each
  assertTrue(order.isDelayed());
}
```

## When a miss is fine

Not every missed mutant is a gap worth closing. mutastic already skips the changes that would
tell you nothing, such as calls that only log and trivial getters: see
[Skipped mutants](/concepts/results/#skipped-mutants). What's left can still include changes no
one could see:

- **A boundary nobody can reach.** If `count` can never be exactly `limit`, `<` and `<=` behave the
  same.
- **A call whose effect is checked elsewhere, or not at all on purpose,** such as warming a cache
  that only makes things faster.
- **A result the code always overwrites,** or a check made twice where the second never decides
  anything.

For those, record the decision rather than writing a test that pins nothing. It goes in
`.mutastic/ignores.yaml`, to commit and review, and lapses when the line changes:

```sh
mutastic ignore m855c8e3c --reason="count never reaches limit"
```

For a whole class or method that isn't worth testing, generated code say, a rule in
`mutastic.yaml` skips it: see [Configuration and skipping](/guides/configuration/).
