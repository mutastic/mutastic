A CI step that fails the build, a dashboard, a coding agent's plugin: each reads what mutastic
found, and each breaks if what it reads moves under it. So what mutastic writes for another tool
comes with a JSON Schema and a promise. Within a version, a field keeps its name and its type, and
anything new is optional, so a reader that takes what it knows and lets the rest pass keeps
working, release after release.

## Events

`--format=jsonl` writes one JSON object per line, as the run goes, so a reader can act on each
mutant as it finishes. This is the [Quickstart](/getting-started/quickstart/)'s run of the pricing
sample, as `mutastic run samples/pricing --format=jsonl` writes it:

<Code code={jsonl} lang="ansi" />

Each line says which format it is, and its major version, in `schema`: `mutastic.events/v1`. Its
`reason` says which event it is:

| `reason` | When |
|---|---|
| `run-started` | First, once the build has been read |
| `mutant-finished` | For each mutant, as it finishes |
| `mutant-revised` | Once every mutant has its result, for each mutant a test reached that then failed on its own with no mutant in: its result again, without that test, which replaces the first |
| `run-finished` | Last: the totals, the score and the verdict |
| `phase-started` | As each phase of `run` starts, among the others (`phase`: `reading`, `building`, `coverage`, `mutants`, `checking`); the phases before `run-started` come before it |
| `phase-finished` | As each phase ends, with `durationMs` |
| `progress` | Every 30 seconds (`MUTASTIC_HEARTBEAT`) while a phase runs, whatever stderr shows: `elapsedMs`, `done` and `total` where there's a count, and for the mutants `weighted`, `leftMs`, the four fates and the busy workers (`running`) |
| `run-failed` | When mutastic can't run, last, in place of `run-finished`, in the agent format too: the error's `code`, its words, the commands it ends in and the exit status ([Errors](/reference/errors/#the-run-failed-event)) |
| `mutant-explained` | Only from `mutastic explain ID --format=jsonl`, after the other three for its one mutant: what the text's About this mutant says, a field for each row ([One mutant, explained](/concepts/output/#one-mutant-explained)) |

### A missed mutant

The one mutant the tests missed, laid out:

<Code code={missed} lang="json" />

- **`status`** is what became of it, named as the mutation-testing report schema names it:
  `Survived` is missed, `Killed` caught.
- **`id`** names it to `verify`, `explain` and `ignore`, and stays the same while code around it
  moves. **`location`** is where it is: the file and line, the class, and the method with its JVM
  descriptor.
- **`operator`** is the kind of change, and **`docs`** where the docs describe it; a plugin's
  operator has no `docs`.
- **`mutation`** is the change: in words in `description`, and in `applied` as the engine made it,
  here to the compiled instruction.
- **`coveredBy`** and **`inputs`** are the evidence: the tests that reach the line, which all still
  pass with the change in, and the values they passed.
- **`suggestedTest`** is the test that would catch it, with what the call gives today and with the
  mutant in.
- **`doneWhen`** is the command that proves a fix, and **`rendered`** the whole miss in the agent
  format's words, for a coding agent to read as it is.

[The schema](https://docs.mutastic.io/schemas/events/v1.json) gives every field, its type, whether
every event has it, and the values it can take.

## Editions

The same events come from each edition of mutastic, Java's and Rust's. Every event's `edition`
says which wrote it, `java` or `rust`. One field is required only of the Java edition, because only
it has it: `run-finished`'s `jdk`. What every edition shares says the same in its own words: `toolchain` is `{"name": "jdk", "version": "17"}` from Java and
`{"name": "rustc", "version": "1.91.0"}` from Rust, and a mutation's `applied` is the change as
each engine makes it: `{"level": "bytecode", "text": "IF_ICMPLT -> IF_ICMPLE"}` from Java, to the
compiled instruction, and `{"level": "source", "text": "x < 0 -> true"}` from Rust, to the source.

The Rust edition writes some fields of its own, each marked as such in the schema:

| Field | In | What it is |
|---|---|---|
| `profile` | `run-started` | The build settings that decide what a mutant means: the profile's name, `optLevel`, `overflowChecks` and `debugAssertions` |
| `unsafe` | `run-started` | Which code near `unsafe` was mutated: `skip`, `enclosing` or `all` |
| `location.column` | `mutant-finished` | The column, from 1 |
| `nearUnsafe` | `mutant-finished` | Why the mutant is near unsafe code, when it is: it runs on its own, and a crash isn't a catch |
| `RuntimeError` | a mutant's `status` | The tests crashed the process where the crash may be undefined behaviour: nothing caught it, and it's out of the score |
| `runtimeError` | `run-finished` | How many mutants were `RuntimeError` |
| `notMutated.unsafe` | `run-finished` | How many mutants weren't made because the `unsafe` setting leaves their code out |
| `build` | `run-finished` | How many times the crate was compiled with mutants in, how many mutants didn't compile, and how long reading and building the package took (`setupMs`) |

In the Rust edition, `location.class` is the path of what holds the function and `location.method`
is the function's name, where the Java edition has a class's binary name and a method's name and
JVM descriptor.

## The schemas

mutastic publishes a JSON Schema (2020-12) for each format another tool reads or writes:

| Schema | Describes |
|---|---|
| [`/schemas/events/v1.json`](https://docs.mutastic.io/schemas/events/v1.json) | The events `--format=jsonl` writes, one per line |
| [`/schemas/mutastic-yaml/v1.json`](https://docs.mutastic.io/schemas/mutastic-yaml/v1.json) | A project's [`mutastic.yaml`](/guides/configuration/#mutasticyaml) |
| [`/schemas/rules/v1.json`](https://docs.mutastic.io/schemas/rules/v1.json) | A [rules file](/guides/plugins/#rules-files) of call operators |

Each schema's `$id` is the address it's served at. mutastic's own tests check every event their runs
write against the events schema, field for field, and every `mutastic.yaml` and rules file they read
against theirs, so a schema can't drift from what mutastic does.

The report files follow formats of their own: `mutation.json` is the [mutation-testing report
schema](https://github.com/stryker-mutator/mutation-testing-elements/tree/master/packages/report-schema)'s,
version 2, and mutastic's tests check it against that schema too. See [Report files](/reference/reports/).

## What v1 promises

This is the events format's part of what stays the same between releases; [Compatibility](/reference/compatibility/)
has the rest: mutant ids, scores and the plugin API.

From 1.0.0, while events say `mutastic.events/v1`:

- **A field keeps its name and its type.** A field every event has stays in every event, and a field
  only some events have stays optional, so a reader that handles it missing keeps working.
- **A value a field can take stays one it can take:** each status, skip kind and failure origin.
- **Each event keeps its `reason`.**

Any release may add:

- **A field,** always optional.
- **An event,** with a `reason` of its own.
- **A value** a field can take, such as a status, a skip kind or a mutation's `applied.level`: an
  engine that changes code at another level, such as `llvm-ir`, says so with a level of its own, and
  its `text` is opaque.

So read what you know and let the rest pass: ignore a field you don't know, ignore an event whose
`reason` you don't know, and treat a value you don't know as neither caught nor missed rather than
failing. Validate against the schema as it's published, which allows fields it doesn't name; don't
close its objects.

Some fields hold words for people and agents to read: `rendered`, `rule`, `decline`, a mutation's
`description` and the commands offered with a missed mutant. The field stays, but its words can
change from one release to the next. The order of the fields in an event isn't part of the promise.

Before 1.0.0, a release that has to break one of these says so in its release notes.

## What counts as breaking

Before 1.0.0 the schema may change; from 1.0.0 it only gains. The build compares the events schema
with the last 1.0+ release's, and fails when a change:

- removes a field, or renames one, which is the same thing to a reader;
- makes an optional field required, or a required one optional, including for one edition's
  events only;
- changes a field's type, whether narrowing it (a number that's no longer ever null) or widening it
  (a whole number that can now have a fraction);
- removes a value from those a field can take;
- adds, changes or removes a constraint, such as the pattern an id follows;
- removes an event.

A new optional field, a new value, a new event and new descriptions pass.

## How a version moves to v2

A change that would break a v1 reader comes only with a major release of mutastic, as
`mutastic.events/v2`, with a schema of its own at `/schemas/events/v2.json`. Every event says which
version it is in its `schema` field, so a reader can tell before it reads anything else. v1's schema
stays published at its address.

## mutastic.yaml and rules files

mutastic reads both strictly: a key it doesn't know is an error, so the schemas refuse one too. An
editor that knows JSON Schema can then flag a mistake before a run does. With the YAML language
server (VS Code's YAML extension, for one), name the schema in the file's first line:

```yaml
# yaml-language-server: $schema=https://docs.mutastic.io/schemas/mutastic-yaml/v1.json
rules:
  - skip: com.acme.generated.**
    reason: protobuf output
```

mutastic reads each value in a rules file as text to the end of its line, where YAML would stop at a
`: ` or a leading backtick. Quote such a value, as the files mutastic ships do, and both read it the
same.

Within v1, these formats keep every key mutastic reads, and may gain new ones.
