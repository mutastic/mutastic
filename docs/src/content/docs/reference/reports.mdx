Besides what it prints, a run writes its results as files, for tools and for reading later: a
report viewer, a dashboard, a badge, a code-quality plugin. Every run writes them except a run of
one mutant (`--only`, and so `verify` and `explain`), which says nothing about the rest. The
summary's `Reports` line lists the files it wrote.

## Formats

| Kind | File | What it is |
|---|---|---|
| `json` | `mutation.json` | The open mutation-testing report schema, version 2, which report viewers, dashboards and badges read. |
| `html` | `mutation.html` | The same report in the schema's own viewer. Everything is in the one file, so it opens from disk with no network. |
| `xml` | `mutations.xml` | The `mutations.xml` format that many build-server and code-quality plugins read. |
| `sarif` | `mutation.sarif` | SARIF 2.1.0, which code scanning reads: GitHub's alerts on a pull request's lines, Azure DevOps, and SARIF viewers in an editor. |

`json` and `html` are written unless you choose otherwise.

## Code scanning

`--report=sarif` writes a result for each missed mutant, as a warning, and each one no test
reaches, as a note, on the line it's on, with the card's headline as its message: `no test checks
discount() at total == 100`. Caught and skipped mutants aren't results. Each operator that made a
result is a rule, described as `mutastic explain` describes it.

A result carries the mutant's id in `partialFingerprints` (`mutasticId/v1`), and the id stays the
same when code above it moves, so an alert follows its mutant from one run to the next instead of
closing and opening again. A result never suggests a fix: the fix is a test, never a change to the
code. Paths are relative to the git repository the project is in, which is what code scanning
resolves them against, so a project in a folder of the repository points at the right files.

On GitHub, upload it after the run. With `--since`, only the lines a pull request changed are
mutated, so its alerts are its own; `--threshold=0` keeps the job green, leaving the alerts to say
what's missed:

```yaml
    permissions:
      security-events: write
    steps:
      # … check out with fetch-depth: 0 and set up Java, as above
      - run: ./gradlew mutasticRun -Pmutastic.since=origin/${{ github.base_ref }} -Pmutastic.reports=sarif -Pmutastic.threshold=0
      - uses: github/codeql-action/upload-sarif@9b3254085494b55a0f7c4c2b3d2d52cc712ce370 # v4.39.1
        with:
          sarif_file: build/mutastic/mutation.sarif
          category: mutastic
```

## Where they go

| Build | Directory |
|---|---|
| Gradle | `build/mutastic/`, or `build/mutastic/<module>/` for a module (`:data` → `build/mutastic/data/`) |
| Maven | the module's own `target/mutastic/` |

The same goes for a run from the command line and from either build plugin. A file given a path
of its own goes there instead, relative to the project's directory.

## Choosing which

`--report=KIND[:PATH]` names one report. Given at all, it replaces the defaults, so name each one
you want; it can be given more than once.

- `--report=xml` writes only `mutations.xml`.
- `--report=json --report=xml` writes `mutation.json` and `mutations.xml`.
- `--report=json:reports/mutation.json` writes the JSON report to `reports/mutation.json`.
- `--report=none` writes nothing.

From a build plugin, `reports` takes the same values as a list, on the command line or in the
build file:
